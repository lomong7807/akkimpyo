# e2e — 끝에서 끝까지 테스트

Playwright로 web 화면을 실제 브라우저에서 돌린다. 무엇을 여기에 두는지는 [테스트 전략](../docs/qa/test-strategy.md)을 따른다.
핵심 흐름만 두고, 계산과 분기는 아래 층(`web/tests/`, `server/`)에서 본다.

| 프로젝트 이름 | 브라우저 | 화면 |
|---|---|---|
| `chromium` | Chromium (`Desktop Chrome`) | 1280×720. 넓은 화면(화면설계서 00-common 2.5, 1024px 이상) |
| `webkit-iphone` | WebKit (`iPhone 17`) | 402×681, 터치. Safari와 같은 엔진이지만 실제 아이폰은 아니다 |

## 실행

테스트는 web 개발 서버와 서버 jar를 함께 띄우고, 서버는 PostgreSQL에 붙는다. 그래서 먼저 셋을 준비한다.

1. DB: 레포 루트에서 `docker compose up -d`(포트 5433). 다른 DB를 쓰려면 `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`를 준다.
   테스트마다 새 사용자로 가입하므로 개발용 DB에 `e2e-…@example.com` 사용자가 쌓인다. 따로 두려면 다른 DB를 준다.
2. 서버 jar: `server/`에서 `./gradlew bootJar`. 서버를 고치면 다시 만든다. `PATH`의 `java`가 21이어야 한다.
3. web 의존성: `web/`에서 `npm ci`.

아래 명령은 `e2e/`에서 실행한다. 2026-11-27에 macOS(arm64), Node 24.3.0 / npm 11.4.2, JDK 21에서 실행해 확인했다.

| 할 일 | 명령 |
|---|---|
| 설치 | `npm ci` |
| 브라우저 설치 (처음 한 번, Playwright 버전을 올린 뒤에도) | `npx playwright install chromium webkit` |
| 전체 실행 (두 브라우저) | `npm test` |
| 한 브라우저만 | `npx playwright test --project=chromium` 또는 `npx playwright test --project=webkit-iphone` |

- 테스트를 시작하면 `playwright.config.ts`의 `webServer`가 둘을 띄우고, 끝나면 끈다.
  - 서버 jar를 포트 **8080**으로 띄운다. web 개발 서버가 `/api`를 8080으로 넘기기 때문이다(`web/vite.config.ts`).
    local 프로파일이다. refresh 쿠키의 Secure와 `__Secure-` 접두어가 local에서만 꺼져 http에서도 브라우저가 쿠키를 남긴다.
    가입 허용 목록은 `@example.com`이고, access token 서명 키는 실행마다 무작위로 새로 만든다(어디에도 남기지 않는다).
  - web 개발 서버를 포트 **5180**으로 띄운다. 개발할 때 쓰는 5173과 겹치지 않게 했다.
  - 8080이나 5180을 이미 다른 프로세스가 쓰고 있으면 이어 쓰지 않고 실패한다. 다른 작업의 `bootRun`이 8080을 쓰고 있으면 그것이 끝난 뒤에 돌린다.
- 서버 로그는 출력에 찍지 않는다(Playwright `webServer`의 기본값).
- 재시도는 0이다. 실패하면 다시 돌려서 덮지 말고 원인을 본다. 실패한 테스트의 기록(trace)은 `test-results/`에 남고,
  그것을 여는 명령은 실패 출력에 함께 찍힌다. trace에는 그 테스트 사용자의 비밀번호와 token이 들어 있다.
- 브라우저의 시간대는 `Asia/Seoul`이다(`timezoneId`). 실행하는 컴퓨터의 시간대에 따라 기기의 오늘이 달라지지 않게 한다.
- CI는 `.github/workflows/e2e.yml`이다. PostgreSQL 17 서비스 컨테이너에 붙여 같은 명령으로 돌리고, 실패하면 trace를 7일 동안 아티팩트로 남긴다.

## 쓰는 규칙

- 요소는 사용자가 보는 것으로 찾는다: `getByRole` → `getByLabel` → `getByText` 순서이고 `getByTestId`는 마지막이다.
  role로 찾지 못하면 테스트를 우회하지 말고 접근성 결함으로 보고한다.
- 기대 동작은 화면설계서(`docs/planning/05-screen-spec/`)와 기능정의서에서 가져오고, 테스트에 근거 위치를 적는다.
  화면이 다르게 동작하면 테스트를 화면에 맞추지 말고 버그로 보고한다.
- 기대 금액은 손으로 계산한 값을 화면에 보이는 글자 그대로("987,700원", "-5,000원") 적고, 계산을 주석으로 둔다.
- 테스트마다 새 이메일로 가입해 데이터를 따로 쓰고(`tests/support/ledger.ts`의 `newUser`), 다른 테스트의 결과에 기대지 않는다.
- 고정 대기(`waitForTimeout`)를 쓰지 않는다. 기다림은 `expect`의 자동 재시도에 맡긴다.
- 서버 응답을 `page.route`로 흉내 내지 않는다. 실제 서버로 돌린다.
- 날짜가 걸리는 기대값("이번 달")은 브라우저 시계를 고정하거나 거래 날짜를 명시해, 월말·자정에 돌려도 같게 한다.

## 더할 것

[테스트 전략](../docs/qa/test-strategy.md) 3절의 핵심 흐름 가운데 서버 API가 아직 없어 넣지 못한 것이다.

- 거래 목록 API(#15)가 생기면
  - 흐름 1의 "내역(D-01)에 보임"
  - 홈의 이번 달 합계(C-01 (2)): 흐름 1의 지출 12,300원, 흐름 4의 수입 50,000원, 이체가 수입·지출 합계에 들어가지 않음(F-203).
    "이번 달"이 걸리므로 브라우저 시계를 고정한다(`page.clock`). 지금은 이 구역이 "불러오지 못했어요."로 보인다.
- 거래 수정 API(#36)와 삭제·복원 API(#38)가 생기면 흐름 3: 거래 수정 → 삭제 → 되돌리기 뒤 합계가 원래대로 돌아옴

서버가 "로그인 필요"라고 답해야 볼 수 있는 것도 아직 넣지 않았다. 서버가 함께 뜨므로 이제 넣을 수 있다.

- 로그인 없이 보호된 주소(`/home`, `/transactions/new`)를 열면 로그인으로 간다(F-011, 00-common 4.1)
- 로그인 없이 없는 주소를 열면 로그인으로 가고, 로그인 뒤에는 찾을 수 없음(N-01)이 보인다(01-auth-home-settings.md N-01)
- 휴대폰 폭에서 하단 탭, 넓은 화면에서 사이드바가 보인다(B-01, 00-common 6.2)
