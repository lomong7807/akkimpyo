# ADR 008: 백업·복원 기준

- 상태: 제안됨 (2026-11-25)
- 보완: 2026-11-25, 복원할 백업을 고르는 기준, 지금 상태 덤프의 암호화와 삭제(결정 7), 서버 디스크의 삭제 기록 원본을 지우는 것과 탈퇴 취소의 기록(결정 8)을 더하고 "고칠 것" 표를 맞춘다(PR #147)
- 보완: 2026-11-25, 결정 7의 4번에서 저장소의 시각을 서버 자격으로 바꿀 수 없다는 것을 추정에서 security가 문서로 확인한 것으로 바꾼다. 실제 버킷은 미확인이다(PR #152)
- 보완: 2026-11-25, 전체 복원 때 거래의 `version`을 올리는 것을 결정 10에 더하고 검토한 대안, 받아들인 위험, "고칠 것" 표를 맞춘다. 결정 7의 7번이 "refresh token 행을 모두 지운다"에서 "refresh token 행을 모두 지우고 모든 거래의 `version`을 올린다"로 바뀐다(PR #156)
- 결정한 사람: owner(목표와 보관 기간, 2026-11-24), dba(설계), devops(실행 방식), architect(삭제 기록과 복원 순서). 검토: dba, devops

## 배경

- 매일 자동 백업은 1단계 범위다(F-910). 서버는 VM 한 대이고 복구는 백업에 달려 있다(ADR 005).
- owner가 2026-11-24에 정한 것은 다음과 같다(dba와 planner 전달).
  - 1단계는 시점 복구 없이 최대 유실 24시간, 복구 4시간이다.
  - 보관은 매일 7개와 매주 4개, 가장 오래된 것이 35일이다. 월 단위는 두지 않는다.
  - 탈퇴·영구 삭제된 데이터가 백업에 남는 기간은 최대 35일이다.
  - 백업 버킷은 춘천 리전이다.
  - 시점 복구는 2단계 시작 전에 시작한다.
- 설계는 dba(`docs/db/backup-restore.md`), 실행은 devops(#53, PR #129)다. 세부 기준은 그 문서가 갖고 이 ADR은 결정과 이유만 적는다.
- PR #129는 아직 머지 전이다(확인, 2026-11-25, 커밋 `c3035f7`). main `0dcb73c`에는 백업 스크립트가 없다(확인).
- 서버 권한을 객체 생성만으로 좁힐 수 있다는 것과 접두어별로 기간이 지난 객체를 지울 수 있다는 것은 devops가 Oracle 문서에서 확인했다(PR #129). 실제 Object Storage에 올리기와 권한의 효과는 미확인이다(PR #129).
- 기획 문서(F-910, P-229, 기능정의서 5장, 개요서)에는 백업 보관 위치가 아직 미결로 적혀 있다(확인).
- ADR 007 결정 8이 정한 것은 다음과 같다.
  - 백업에서 복원하면 그사이 지운 것(거래 완전 삭제, 장부 영구 삭제, 탈퇴)이 되살아난다.
  - 복원 절차에는 백업 시점 뒤의 정리 작업을 다시 적용하는 단계가 있어야 하고, 다시 적용이 끝난 뒤에 서비스를 연다.
  - 그러려면 정리 작업의 기록이 복원되는 DB 밖에 남아야 한다. 기록은 대상 id, 종류 네 가지, 시각이다. 그 일을 한 사람의 id와 내용 값은 없다. 방법은 이 ADR이 정한다.
- 거래 완전 삭제, 장부 영구 삭제, 탈퇴는 아직 구현되지 않았다(확인, main `0dcb73c`).

## 결정

### 1. 1단계의 목표

- 최대 유실 24시간, 복구 4시간 이내다.
- 시점 복구는 없다. 마지막 백업 뒤의 입력은 사라질 수 있다. owner가 받아들인 위험이다(2026-11-24).

### 2. 방식

- 매일 한 번과 배포 직전(교체하기 전)에 DB 전체의 논리 백업(`pg_dump`)을 받는다. 역할 정보도 같이 받는다.
- 백업은 올리기 전에 암호화하고 복호화 키는 owner만 가진다.
- 세부(도구 옵션, 성공 판정, 명세표)는 `docs/db/backup-restore.md`가 기준이다.

### 3. 보관하는 곳

- Oracle Cloud Object Storage, 춘천 리전이다.
- 서버(VM)의 자격으로는 새 객체를 올리기만 할 수 있고 읽기, 덮어쓰기, 지우기는 할 수 없게 한다. 서버가 뚫려도 지난 백업을 지우거나 바꿀 수 없게 하기 위해서다.
- 월 1회 복원 훈련 때 내려받은 암호화 파일 하나를 Oracle Cloud 계정 밖(owner의 기기)에도 둔다.
- owner 기기의 사본은 훈련 때마다 새것으로 바꾸고 앞의 것은 지운다. 훈련을 걸렀더라도 35일이 지난 사본은 지운다(운영 문서에 적는다, #54).

### 4. 보관 기간

- 매일 7개, 매주 4개이고 가장 오래된 것이 35일을 넘지 않는다. 월 단위 장기 보관은 두지 않는다(owner 결정).
- 지운 데이터가 백업에 남는 최장 기간도 35일이다. 이 값이 개인정보 처리방침에 들어간다(#23). 삭제 기록이 남는 기간은 이보다 며칠 길 수 있다(결정 8).
- 버킷의 수명 주기 설정 일수는 이 약속을 넘지 않게 devops가 정한다(PR #129).
- 35일은 클라우드의 수명 주기가 정상으로 돌 때의 값이다(Oracle은 실행을 best-effort로 적는다, PR #129). 처리방침의 문구는 planner와 owner가 정한다(#23).

### 5. 복원 훈련

- 첫 훈련은 owner가 운영 DB에 실제 지출을 넣기 전에 통과한다. 운영 백업으로 하는 훈련이므로 첫 배포 뒤이고 실제 지출 전이다. 첫 배포 전에 하는 스크립트 시험(devops, #102)은 이 훈련과 별개다.
- 주기(월 1회와 조각 1A, 1B, 1C가 끝날 때)는 dba 제안이고 owner 확인을 기다린다(#54).
- 운영과 떨어진 환경에 실제로 복원한다. 통과 조건은 복원 성공, 스키마 검증, 백업 때의 명세표와 일치, 무결성 점검 0건, 서버 기동, 걸린 시간 기록이다. `docs/db/backup-restore.md` 9절이 기준이다.
- 훈련하지 않은 백업은 백업으로 세지 않는다.

### 6. 실패를 아는 방법

- 백업이 실패하면 바로 알린다(#53, PR #129). 새 백업이 26시간 넘게 없으면 알린다. 직전보다 크기가 크게 줄어도 알린다.
- 이 알림은 서버 안에서 도므로 서버가 통째로 죽으면 나가지 않는다. 서버 밖에서 보는 감시는 devops가 정한다.

### 7. 복원 절차의 순서

1. 무엇이 망가졌는지 확인한다.
2. 쓰기를 막는다.
3. 지금 상태도 덤프로 남긴다. 이 덤프도 암호화하고 35일 안에 지운다.
4. 복원할 백업은 서버가 기록한 마지막 성공 객체 이름이나 owner가 알림으로 받은 이름과 대조해 고른다(어느 쪽인지는 실제 동작에 맞춰 #54가 정한다). 서버가 뚫렸을 수 있으면 두 값도 믿지 않고, 저장소가 기록한 올린 시각이 침해 시점보다 앞선 백업을 고른다. 저장소의 시각(`timeCreated`)을 서버 자격으로 바꿀 수 없다는 것은 security가 문서로 확인했고 실제 버킷은 미확인이다(PR #147 검토). SDK는 `timeCreated`를 객체가 만들어진 시각으로 설명하고(저장소가 찍는다고 직접 적은 문서는 미확인) PutObject에 시각을 정하는 요청 항목이 없다(OCI Go SDK의 요청 정의). 이름 바꾸기와 여러 조각 올리기에는 `OBJECT_CREATE`와 `OBJECT_OVERWRITE`가 모두, 이미 있는 이름에 올리기에는 `OBJECT_OVERWRITE`가 필요한데([Oracle 권한 표](https://docs.oracle.com/en-us/iaas/Content/Identity/policyreference/objectstoragepolicyreference.htm)) 서버에는 `OBJECT_CREATE`만 주므로(결정 3) 지난 객체의 시각을 바꿀 길이 없다.
5. 새 DB에 복원한다.
6. 점검한다.
7. refresh token 행을 모두 지우고 모든 거래의 `version`을 올린다(결정 10).
8. 백업 시점 뒤의 정리 작업과 탈퇴 신청, 탈퇴 취소를 다시 적용한다(2단계부터, 결정 8).
9. 토큰이 든 주소를 모두 폐기한다(2단계부터, 결정 10).
10. 서비스를 연다.
11. owner에게 보고한다. 2단계부터는 사용자에게도 알린다(결정 10).

- 복원은 사람이 시작하고 자동으로 하지 않는다(ADR 005 결정 4).
- "다시 적용이 끝나기 전에는 서비스를 열지 않는다"는 삭제 기록 장치가 있는 2단계부터의 규칙이다.
- 1단계에는 삭제 기록이 없어 다시 적용할 것이 없다. 복원하고 점검한 뒤(7번까지 하고) 서비스를 열고, 되살아난 삭제는 owner가 앱에서 직접 다시 지운다.

### 8. 삭제 기록(ADR 007 결정 8의 방법)

- 정리 작업(수동 완전 삭제, 자동 삭제, 장부 영구 삭제, 탈퇴)과 탈퇴 신청, 탈퇴 취소가 일어날 때 서버는 삭제 기록 한 줄(대상 id, 종류, 시각)을 DB가 아닌 서버 디스크의 추가 전용 파일에 쓴다. 내용 값과 그 일을 한 사람의 id는 쓰지 않는다.
- 탈퇴 신청과 탈퇴 취소는 정리 작업이 아니지만 종류에 더한다(결정 10). 신청만 다시 적용하면 취소한 계정이 다시 유예에 들어간다(#140). 탈퇴 기능을 만드는 출시 단계에 넣는다.
- 탈퇴, 탈퇴 신청, 탈퇴 취소 기록의 대상 id는 그 사람의 사용자 id일 수밖에 없다. 이메일과 이름은 없다. 이 id가 기록의 보관 기간만큼 남는 것을 받아들이고, 기간이 지나면 지운다. "그 일을 한 사람의 id는 쓰지 않는다"는 다른 사람의 대상을 지운 사람에 관한 말이다.
- 앱 서버 밖의 주기 작업(백업 스크립트와 같은 방식, devops)이 이 파일을 Object Storage의 별도 접두어에 올린다. 권한은 백업과 같이 올리기만이다. 주기 작업은 새 기록이 있을 때만 올린다. 주기, 접두어의 정책과 수명 주기는 devops가 정한다.
- 앱 서버는 Object Storage에 직접 붙지 않는다. 앱에 클라우드 의존성을 더하지 않기 위해서다.
- 삭제 기록은 그것이 필요한 백업보다 먼저 지워지지 않게 한다. 기록의 수명 주기 일수는 백업의 가장 긴 일수보다 길게 잡는다. 수명 주기 실행이 늦어질 수 있기 때문이다. 일수는 devops가 정한다.
- 그래서 삭제 기록(탈퇴한 사람의 사용자 id 포함)이 남는 최장 기간은 백업의 35일보다 며칠 길 수 있다. 개인정보 처리방침에 적히는 값이라 owner 확인이 필요하다(확인 대기 중).
- 서버 디스크의 삭제 기록 원본 파일도 올린 뒤 같은 기간이 지나면 지운다(#140).
- 다시 적용은 SQL을 직접 치지 않고 서버의 정리 작업과 같은 코드 경로를 부르는 관리 명령으로 한다. 변경 이력 처리(ADR 007)가 똑같이 적용되게 하기 위해서다. 다시 적용한 수동 완전 삭제 기록은 "누가"가 비어 있다(ADR 007의 받아들인 위험).
- 다시 적용은 자동으로 하지 않는다. 관리 명령이 백업 시점 뒤의 기록 목록(종류별 건수와 대상)을 보여 주고 owner가 확인한 뒤 실행한다. 기록의 대상이 복원된 DB에 없거나 종류가 맞지 않으면 건너뛰고 알린다.
- 위조된 기록으로 멀쩡한 데이터를 지우는 것을 막는 방법(기록의 서명이나 암호화 포함)은 이 장치를 만드는 구현 이슈에서 security 검토를 받아 정한다.
- 1단계에는 만들지 않는다. 1단계의 데이터는 owner 것뿐이고, 복원 뒤 되살아난 것은 owner가 앱에서 직접 다시 지운다(결정 7).
- 2단계 시작 전(다른 사람의 데이터가 들어오기 전)에 만든다. 시점 복구를 시작하는 때와 같다.

### 9. 2단계 전에 올리는 것

- 다른 사람의 데이터가 들어오기 전에 기본 백업과 WAL 보관으로 시점 복구를 시작한다.
- 그때의 목표는 dba 제안(유실 5분, 복구 1시간)이고 미결이다. 도구는 devops가 정한다.
- 그때 이 ADR을 보완한다.

### 10. 복원 뒤에 되돌아가는 폐기

- 복원하면 백업 시점 뒤에 한 폐기와 변경도 되돌아간다. refresh token 폐기, 열람 링크·초대·문자 전송 주소의 폐기, 구성원 내보내기, 권한 낮추기, 소유권 넘기기, 비밀번호 바꾸기, 탈퇴 신청, 탈퇴 취소가 그렇다.
- (가) 모든 refresh token 계열을 폐기해 모두 다시 로그인하게 한다. 1단계부터 한다. 복원한 DB에 서버를 붙이기 전에 refresh token 행을 모두 지운다. 코드 없이 복원 절차의 한 단계로 하고 절차는 운영 문서(#54)와 dba 문서 10절에 적는다.
- (나) 2단계부터는 서비스를 열기 전에 토큰이 든 주소 전부(열람 링크, 초대, 3단계의 문자 전송 주소)를 폐기한다.
- (다) 전체 복원을 하면 거래의 `version`도 과거로 돌아가, 복원 전 내용을 들고 있던 기기의 수정이 나중에 같은 `version`과 맞아 충돌 없이 덮을 수 있다(dba가 찾음, 추정). 그래서 앱을 붙이기 전에 모든 거래(휴지통 포함)의 `version`에 복원하는 시각의 epoch 초를 더한다. 1단계부터 하고 코드는 필요 없다.
- (다)는 명세표 대조(결정 7의 6번) 뒤에 한다. `updated_at`은 바꾸지 않고 이력도 남기지 않는다. 고정 값이 아니라 시각을 더하는 이유는 복원을 다시 해도 앞 복원 때의 `version`과 겹치지 않기 때문이다. 절차는 dba의 복원 절차서(`docs/db/restore-runbook.md`, PR #148)가 갖는다.
- 구성원 내보내기, 권한 낮추기, 소유권 넘기기, 비밀번호 바꾸기가 되돌아가는 것은 기록 없이는 다시 적용할 수 없어 받아들인 위험으로 둔다. 시점 복구(결정 9)가 이 틈을 24시간에서 분 단위로 줄인다.
- 탈퇴 신청이 되돌아가는 것은 받아들이지 않는다. 지우기로 한 계정이 지워지지 않기 때문이다. 삭제 기록의 종류에 탈퇴 신청과 탈퇴 취소를 더해 다시 적용한다(결정 8).
- 2단계부터는 복원한 사실과 그 시각을 사용자에게 알린다.

## 검토한 대안

| 내용 | 좋은 점 | 대가 | 판단 |
|---|---|---|---|
| 처음부터 시점 복구(기본 백업과 WAL 보관)를 한다 | 유실이 분 단위로 준다 | 운영할 것이 늘고 복원 훈련이 복잡해진다. 1단계 사용자는 owner 한 명이고 하루치 입력은 다시 적을 수 있다 | 지금은 채택하지 않음. 2단계 전에 한다 |
| 월 단위 장기 보관을 더한다 | 오래된 실수를 되돌릴 수 있다 | 지운 데이터가 백업에 남는 기간이 그만큼 길어져 삭제 약속(최대 35일)이 깨진다 | 채택하지 않음. owner가 두지 않기로 했다 |
| 디스크(블록 볼륨) 스냅샷만 쓴다 | 설정이 쉽다 | DB가 도는 중의 스냅샷이 일관된지 따로 보장해야 하고, 다른 환경에 복원해 내용을 점검하기 어렵고, 같은 클라우드 계정 안에만 남는다 | 채택하지 않음. 논리 백업에 더하는 것은 devops가 정할 수 있다 |
| 삭제 기록을 DB의 테이블에 둔다 | 구현이 가장 쉽다 | 복원하면 백업 시점 뒤의 기록도 같이 사라져 쓸모가 없다 | 채택하지 않음 |
| 서버가 삭제 기록을 Object Storage에 직접 올린다 | 유실 틈이 없다 | 앱에 클라우드 SDK와 자격이 들어간다. 저장소가 느리거나 죽으면 삭제 요청이 실패하거나 느려진다 | 채택하지 않음 |
| 삭제 기록 없이 복원 뒤 사람이 기억으로 다시 지운다 | 장치가 없다 | 다른 사람의 데이터가 들어온 뒤에는 삭제 약속을 지킬 수 없다 | 1단계에는 owner 데이터뿐이라 이것으로 충분해 그렇게 한다. 2단계부터 채택하지 않음 |
| 복원할 때 거래의 `version`에 고정 값(1000000)을 더한다 | - | 더 앞선 백업으로 다시 복원하면 앞 복원 때의 `version`과 겹친다 | 채택하지 않음 |
| 다시 로그인할 때 기기가 들고 있던 내용을 버리게 한다 | - | 화면 구현에 기대고 서버가 보장할 수 없다 | 채택하지 않음 |

## 결과

- 좋아지는 것: 서버나 DB를 잃어도 하루 안의 상태로 돌아갈 수 있고, 돌아갈 수 있다는 것을 훈련으로 확인한다. 서버가 뚫려도 지난 백업은 남는다. 다만 같은 자격으로 가짜 백업을 새로 올릴 수는 있고, 서버가 뚫렸을 수 있으면 대조할 이름도 믿을 수 없다. 그때는 침해 시점보다 먼저 올린 백업을 고른다(결정 7의 4번). 지운 데이터가 남는 기간에 상한이 있다.
- 대가: 암호화 키를 owner가 잃으면 백업 전체를 못 쓴다. 매달 복원 훈련에 시간이 든다. 2단계 전에 시점 복구와 삭제 기록 장치를 만들어야 한다.
- 받아들인 위험: 마지막 백업 뒤 최대 24시간의 입력을 잃을 수 있다. 매일 덤프만으로는 시점 복구가 되지 않는다.
- 받아들인 위험: 서버가 통째로 죽으면 백업 실패 알림이 나가지 않는다.
- 받아들인 위험: 1단계에서는 복원 뒤 되살아난 삭제를 owner가 직접 다시 지워야 한다.
- 받아들인 위험: 복원하면 백업 시점 뒤의 구성원 내보내기, 권한 낮추기, 소유권 넘기기, 비밀번호 바꾸기가 되돌아간다. 기록 없이는 다시 적용할 수 없다(결정 10).
- 받아들인 위험: 백업 뒤에 만들어져 복원으로 사라진 거래는 `version`을 올릴 행이 없다. 재전송으로 같은 id가 다시 만들어져 다시 고쳐지면, 사라지기 전 내용을 든 다른 기기와 `version`이 겹칠 수 있다(추정, 드물다).
- 받아들인 위험: 2단계의 삭제 기록은 올리는 주기 안에 서버 디스크까지 잃으면 그 사이의 기록을 잃는다.
- 받아들인 위험: 수명 주기 삭제는 클라우드가 하루 한 번 돌리고 더 걸릴 수 있어 지워지는 시각을 정확히 보장하지 않는다(devops가 Oracle 문서에서 확인, PR #129). devops는 올림과 실행 간격으로 생기는 최대 2일의 지연을 넣어도 백업이 35일을 넘지 않게 일수를 잡았다. 35일은 문서에 적힌 정상 동작 기준이고 실제 버킷에서는 미확인이다.
- 다시 검토할 조건: 2단계를 시작하기 전, 복원 훈련에서 복구 4시간을 넘겼을 때, 백업 크기가 서버 작업 폴더나 저장 한도에 가까워질 때.
