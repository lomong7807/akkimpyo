# ADR 006: 동시 수정과 오프라인 입력 정책

- 상태: 제안됨 (2026-11-25). iPhone 실기기 시험 결과는 첫 배포 뒤에 덧붙인다(결정 9)
- 보완: 2026-11-25, 전체 복원 뒤의 `version`을 ADR 008 결정 10과 맞추고(결정 3, 5) 검토한 대안에 거래 id의 유일성 범위를 더한다. 결정 3에서 200을 받았을 때 알리는 기준이 "200으로 받은 서버 자원이 보낸 내용과 다르거나, 휴지통에 있거나, 취소 상태이면"에서 "받은 자원의 `version`이 2 이상이거나, 휴지통에 있거나, 취소 상태이면"으로 바뀐다(이 PR)
- 결정한 사람: architect (검토: frontend, security). 실기기 시험의 판정은 owner가 한다

## 배경

- 목표는 "어느 기기에서 입력해도 같은 데이터"다(설계 2.1). 피해야 할 실패 (a)는 "표시 없이 데이터가 어긋나거나 사라지는 것"이다(설계 2.3). 로컬 우선 동기화 엔진은 조사 단계에서 탈락했다(설계 4.2).
- 오프라인에서는 새 거래 만들기만 기기에 쌓는다. 수정, 삭제, 승인취소, 복원은 연결이 있을 때만 한다(P-225). 서버가 거부한 입력은 자동으로 버리지 않는다(P-226). 수정 충돌은 거래의 `version`으로 거부한다(P-217).
- 거래 id는 기기가 만든 UUID다(P-225). 지금 만들기 코드는 같은 id가 있으면 같은 장부이고 같은 내용일 때 저장된 거래를 돌려주고, 아니면 `IdConflictException`을 던진다(확인, main `a913494`).
  - 비교 대상은 저장된 거래의 지금 내용이다.
  - 입력 검증(계좌와 카테고리 확인 포함)이 기존 거래 조회보다 먼저다.
  - 처음 만든 것과 다시 보낸 것을 구분하는 반환값이 없다.
- iPhone 홈 화면 웹앱은 백그라운드 전송이 없고, 저장 공간이 부족하면 기기 데이터가 지워질 수 있다(설계 3.3). 실기기 시험(설계 10.1)은 아직 하지 않았다(#72).
- 오프라인 입력은 1B다. 이 ADR의 결정 부분은 1B 시작 전에 끝낸다(planner 결정 2026-11-24).
- 다른 ADR과 이슈가 먼저 정한 것이 있다.
  - ADR 002의 처음 규칙: 만들기는 처음이면 201, 다시 보낸 것이면 200, 같은 id에 다른 내용이면 409 `ID_CONFLICT`다.
  - ADR 007: 완전히 지운 거래의 id는 다시 쓸 수 없다. 이때의 응답은 이 ADR이 정한다.
  - #21: 다른 장부에 있는 id로 만들 때 그 장부의 존재가 드러나면 안 된다.

## 결정

### 1. 기준 데이터는 서버 하나다

- 기기는 두 가지만 가진다. 보내지 않은 새 거래의 대기열, 그리고 읽기용 사본(계좌·카테고리 목록과 최근 한 달 내역, P-902)이다.
- 기기끼리 또는 기기와 서버 사이에 변경을 병합하는 장치는 두지 않는다.
- 읽기용 사본은 연결되면 서버에서 통째로 다시 받는다. 바뀐 것만 받는 동기화는 만들지 않는다.

### 2. 오프라인에서 되는 일은 새 거래 만들기뿐이다

- 수정, 삭제, 상태 변경은 연결이 있을 때 서버에 바로 보낸다. 대기열에 넣지 않는다.
- 이유: 새 거래는 다른 변경과 부딪히지 않는다. 수정을 쌓아 두면 보낼 때 충돌 해결이 필요해진다.

### 3. 만들기의 재전송 규칙

같은 id의 만들기 요청이 왔을 때 서버는 다음과 같이 답한다.

| 서버의 상태 | 응답 |
|---|---|
| 그 id의 거래가 없고 완전 삭제 기록도 없다 | 만든다. 201과 자원 |
| 같은 장부에 있고, 요청자가 만든 거래이고, 만든 뒤 고쳐진 적이 없고(`version` 1), 내용이 같다 | 200과 저장된 자원. 이력을 더하지 않는다 |
| 위와 같은데 내용이 다르다 | 409 `ID_CONFLICT`. `current`에 저장된 자원 |
| 같은 장부에 있고, 요청자가 만든 거래이고, 만든 뒤 고쳐졌다(휴지통에 있는 것 포함) | 재전송으로 본다. 내용을 비교하지 않고 200과 지금 자원 |
| 그 밖: 다른 장부의 id, 다른 사람이 만든 거래의 id, 완전히 지운 거래의 id(ADR 007) | 409 `ID_CONFLICT`. `current`가 없고 `detail`은 고정 문구다. 세 경우를 응답으로 구분할 수 없다 |

- 권한 검사(404, 403)가 표보다 먼저다. 저장된 뒤 권한을 잃고 다시 보낸 입력은 이미 저장돼 있어도 "보낼 수 없음"이 된다. 다른 장부로 바꿔 보낼 때는 새 id를 쓴다.
- 같은 id의 요청이 동시에 오면 한 건만 만들어지고 나머지는 표의 재전송 줄에 따라 답한다. 500이 되면 안 된다.
- "고쳐졌다"는 `version`이 2 이상이라는 뜻이다. 거래의 내용이나 상태를 바꾸는 서버 동작은 모두 `version`을 올리고 이력을 남긴다. 카테고리 삭제에 따른 이동도 그렇다(P-216). 예외로, 사람을 가리키는 값만 비우는 탈퇴 정리는 `version`을 올리지 않고 이력을 남기지 않는다(ADR 007 결정 5). 전체 복원 때 `version`을 올리는 것도 예외로, 내용이 바뀌지 않아 이력을 남기지 않는다(ADR 008 결정 10). 그래서 복원 뒤에는 고쳐지지 않은 거래의 재전송도 "고쳐졌다"로 판정돼 내용을 비교하지 않고 200이다. 화면이 알린다.
- 내용이 같은지 볼 때 비교하는 것은 요청이 정할 수 있는 값 전부다(유형, 날짜, 시각, 가맹점, 메모, 결제한 사람, 라인). 비교 전에 하는 값 맞추기(카테고리를 비운 요청을 미분류로 바꾸기 등)는 형식 검증 단계에 속한다. 결제한 사람이 구성원인지는 참조 검증이다.
- 이유: 응답을 받지 못한 채 다시 보내는 사이에 다른 기기가 그 거래를 고쳤을 수 있다. 지금 내용과 비교하면 이미 저장된 거래의 재전송이 충돌로 보인다. 고쳐진 뒤에는 "이미 만들어졌다"만 알리면 된다.
- 화면은 200을 받으면 대기열에서 지우고 서버가 준 자원으로 화면을 맞춘다. "이미 저장된 거래라 서버 내용으로 맞췄다"를 알릴지는 화면이 내용을 비교해서가 아니라 받은 자원으로 판단한다. 받은 자원의 `version`이 2 이상이거나, 휴지통에 있거나, 취소 상태이면 알린다. 조용히 넘기지 않는다. 내용이 다른 경우는 다른 기기가 고쳤거나, 서버에는 저장됐지만 응답을 받지 못한 입력을 사용자가 고쳐 다시 저장했고(화면설계서 00-common 4.3의 응답 지연) 그사이 다른 기기도 고친 때다.
- `current`가 있는 409 `ID_CONFLICT`(같은 장부, 내가 만든 거래, 내용이 다름)를 받으면 화면은 서버 내용과 내 입력을 나란히 보여 주고(수정 충돌 화면과 같은 방식, F-909) 사용자가 고른다. 유형이 다를 때를 빼고 새 id로 다시 만들지 않는다. 대기열이 아니라 입력 화면에서 바로 받은 409도 같다.
  - "서버 내용 그대로": 대기열에서 지운다.
  - "내 입력으로 고치기": 그 거래의 수정 요청을 `current`의 `version`과 함께 보낸다. 저장되면 대기열에서 지운다.
  - "새 거래로 저장": 내 입력의 유형이 서버 거래와 다르면 "내 입력으로 고치기"를 보이지 않고(유형은 수정할 수 없다, P-213) 이것을 보인다. 새 id로 만든다. 먼저 저장된 거래가 그대로 남아 있다는 것을 알린다. 지울지는 사용자가 정한다.
- `current`가 없는 409 `ID_CONFLICT`를 받은 입력은 "보낼 수 없음"이 된다. 고쳐서 다시 보낼 때는 새 id를 쓴다.
- 남의 장부에 관해 드러나는 것은 "이 id는 쓸 수 없다"뿐이다(#21). id는 추측할 수 없는 값이다.

### 4. 만들기의 검사 순서

1. 인증(401)
2. 장부 구성원(404)
3. 권한(403)
4. 요청 형식 검증(400): 필수 항목, 형식, 범위, 비교 전의 값 맞추기
5. 같은 id 조회(결정 3): 재전송이면 여기서 끝난다
6. 참조 검증(400): 계좌와 카테고리가 있는지, 종류가 맞는지, 결제한 사람이 구성원인지
7. 저장

- 이유: 이미 저장된 거래의 재전송이 그사이 지워진 카테고리 때문에 400이 되면 안 된다.
- ADR 002 5절의 검사 순서에서 "입력 검증"을 만들기에 한해 형식 검증과 참조 검증으로 나눈 것이다.

### 5. 수정 충돌

- 거래의 수정, 삭제, 상태 변경은 자기가 본 `version`을 보낸다. 다르면 409 `STALE_VERSION`과 `current`를 받는다(ADR 002).
- `version`에는 구멍이 있을 수 있다(ADR 008 결정 10). 클라이언트와 서버는 1씩 이어진다고 기대하지 않고, 충돌은 같은지만 비교한다.
- 서버는 조용히 덮어쓰지 않고 필드를 병합하지도 않는다.
- 공유 장부에서 두 사람이 같은 거래를 고치면 먼저 저장한 쪽이 반영되고 나중 쪽이 충돌을 받는다.
- "내 입력 다시 적용"은 화면이 최신 내용 위에 내가 바꾼 항목을 얹은 수정 화면을 열고 사용자가 다시 저장하는 것이다(F-909). 자동으로 다시 보내지 않는다.

### 6. 대기열의 규칙

- 항목마다 거래 id, 장부 id, 입력한 사용자 id, 쌓은 시각, 상태(대기, 보낼 수 없음과 이유)를 같이 저장한다.
- 다른 사용자로 로그인하면 앞 사용자의 대기 항목은 보내지 않고 지우지도 않는다. 로그인이 풀린 경우(토큰 만료 등, 화면설계서 00-common 4.1)에 한한 규칙이다.
- 항목은 서로 독립이다. 오래된 것부터 하나씩 보내고, 하나가 실패해도 다음 것을 보낸다.
- 항목을 보내고 받은 응답은 다음과 같이 처리한다.

| 응답 | 처리 |
|---|---|
| 201, 200 | 대기열에서 지운다 |
| problem+json이고 `code`가 있는 4xx(401과 429는 빼고, 405, 413, 415는 포함) | "보낼 수 없음"으로 바꾸고 자동으로 다시 보내지 않는다 |
| 연결 오류, 5xx, 429, 그 밖의 4xx(401 제외) | 대기로 남기고 다시 보낸다. 429는 `Retry-After`를 따른다 |
| 401 | 토큰을 갱신해 한 번 다시 보낸다. 갱신 요청이 401일 때만 대기로 남긴 채 로그인을 요구한다(ADR 002). 갱신이 연결 문제나 5xx로 실패하면 대기로 남기고 로그인을 요구하지 않는다 |

- 본문을 읽을 수 없는 응답(프록시가 직접 낸 4xx, 5xx 등)은 상태 코드와 무관하게 대기로 남긴다. 이유: 배포 사고 한 번에 대기열 전체가 "보낼 수 없음"이 되면 안 된다. 대기열에 한해 이 규칙이 ADR 002 7절(본문을 읽지 못하면 상태 코드로 처리한다)보다 우선이다.
- 보내는 때는 앱을 열 때, 연결이 돌아왔을 때, 앱이 열려 있는 동안 주기적으로, 사용자가 "지금 보내기"를 누를 때다(F-105, F-107). 백그라운드 전송에 기대지 않는다.
- "보내지 않은 입력 N건"은 0이 아니면 F-104가 정한 자리에 보인다.
- 대기열이 비워지는 경로는 보내기 성공, 사용자의 "버리기", 확인을 받은 로그아웃과 탈퇴 신청(F-016, F-017, M-05)이다. 결정 3의 선택에서 "서버 내용 그대로"는 버리기로, "내 입력으로 고치기"나 "새 거래로 저장"이 저장된 것은 보내기 성공으로 본다.
- "고쳐서 다시 보내기"(F-108)가 없는 동안에는 "보낼 수 없음"은 버리기만 된다. `current`가 있는 409의 선택(결정 3)은 F-108과 별개다.

### 7. 기기 저장

- 대기열과 읽기용 사본은 IndexedDB에 둔다. localStorage는 용량이 작고 동기 방식이라 쓰지 않는다.
- 앱은 브라우저에 저장 유지를 요청한다(`navigator.storage.persist()`). iPhone 홈 화면 웹앱에서 이 요청이 받아들여지는지는 미확인이다.
- 그래도 기기가 저장을 지울 수 있다(설계 3.3). 그래서 보내지 않은 입력이 있다는 것을 F-104가 정한 자리에 보이고, 연결되면 바로 보낸다.
- 기기에 둔 대기열과 읽기용 사본은 암호화하지 않는다. 열쇠를 둘 곳이 같은 기기뿐이다. 기기 잠금에 기댄다.
- 읽기용 사본은 계정별로 나눠 두고 로그인한 계정의 것만 보인다(화면설계서 00-common 4.1). 로그아웃하면 그 계정의 사본과 대기열을 지운다(결정 6).
- 라이브러리와 저장 구조는 frontend가 정한다.

### 8. 시각과 id

- id는 기기가 만드는 UUID v7이다(설계 6.2). 서버는 id에 든 시각을 재전송, 충돌, 권한의 판정에 쓰지 않는다.
- 목록에서 날짜와 시각이 같을 때 id로 순서를 정하는 것(ADR 002 3절)은 순서를 고정하기 위한 것이고 시각의 뜻으로 쓰는 것이 아니다.
- 거래의 날짜와 시각은 사용자가 입력한 값이고(P-202), 서버 기록 시각은 서버가 정한다.
- 기기 시계가 틀려도 판정과 서버 기록 시각은 영향받지 않는다. 사용자가 본 날짜와 시각의 기본값은 기기 값이라 틀릴 수 있다(P-202).

### 9. 실기기 시험은 뒤에 덧붙인다

- 첫 배포 뒤 owner의 iPhone 홈 화면 웹앱에서 세 가지를 재고 이 ADR의 "시험 결과" 절에 덧붙인다.
  - 아이콘을 누른 뒤 입력창이 뜨기까지의 시간
  - 비행기 모드에서 입력한 뒤 연결됐을 때 전송되는지
  - 며칠 둔 뒤에도 쌓아 둔 입력이 남아 있는지
- 판정은 owner가 한다. 결과가 나쁘면 네이티브 단계를 앞당길지 owner가 정한다(설계 10.1).

| 내용 | 좋은 점 | 대가 | 판단 |
|---|---|---|---|
| 나중에 저장한 쪽이 이긴다(충돌 검사 없음) | 구현이 가장 쉽다 | 먼저 고친 사람의 변경이 표시 없이 사라진다. 피해야 할 실패 (a)다 | 채택하지 않음(거래에 한해. 계좌 등은 P-217대로 이 방식이다) |
| 필드 단위 자동 병합 | 서로 다른 항목을 고친 경우 충돌이 줄어든다 | 금액과 카테고리처럼 함께 뜻을 갖는 값이 따로 합쳐져 아무도 입력하지 않은 거래가 생길 수 있다 | 채택하지 않음 |
| 오프라인에서 수정과 삭제도 쌓는다 | 연결 없이 더 많은 일을 할 수 있다 | 보낼 때의 충돌 해결 화면이 필요하고 대기 항목 사이에 순서 의존이 생긴다. 지금 필요한 것은 "밖에서 바로 적기"다 | 채택하지 않음. 다시 볼 조건: 연결 없이 고칠 수 없다는 불편이 실제로 보고될 때 |
| 로컬 우선 동기화 엔진(기기마다 전체 사본과 변경 기록 병합) | 연결과 무관하게 모든 기능이 된다 | 동기화 정합성 자체가 큰 프로젝트가 된다(설계 4.2의 사례) | 채택하지 않음 |
| 재전송을 저장된 거래의 지금 내용과 늘 비교한다(지금 코드) | 구현이 단순하다 | 다른 기기가 고친 뒤의 재전송이 충돌로 보여, 이미 저장된 입력이 "보낼 수 없음"이 된다 | 채택하지 않음 |
| 재전송을 만들 때의 내용과 비교한다(변경 이력의 첫 행이나 내용 해시 컬럼) | 판정이 가장 정확하다 | 만들기 경로가 변경 이력 형식에 묶이거나 컬럼이 하나 더 필요하다. 고쳐진 뒤의 재전송을 "이미 만들어짐"으로 보는 것으로 충분하다 | 채택하지 않음 |
| 거래 id의 유일성을 장부 안으로 좁힌다(장부 id와 거래 id의 조합) | 다른 장부의 id로 만들기가 그냥 성공하므로 "쓸 수 없는 id" 문제 자체가 없어진다 | 기본 키와 라인의 FK가 바뀐다. 지금 방식의 남는 위험은 낮다 | 채택하지 않음. 나중에 바꾸기 어려운 결정이라 검토한 기록을 남긴다(PR #121 security 검토) |

## 결과

- 좋아지는 것: 연결이 끊겨도 입력이 사라지지 않고, 여러 번 보내도 한 건만 생긴다. 충돌은 늘 사용자에게 보인다. 서버에 동기화 장치가 없어 서버 구조가 단순하게 남는다.
- 대가: 연결 없이 고치거나 지울 수 없다. 화면은 대기열, 응답별 처리, 충돌 화면을 구현해야 한다. 서버의 만들기는 검사 순서와 재전송 판정을 고쳐야 한다.
- 받아들인 위험: 기기가 저장을 지우면 보내지 않은 입력이 사라진다(시험으로 확인한다).
- 받아들인 위험: 서버에는 저장됐지만 응답을 받지 못한 입력을 사용자가 고쳐 다시 저장했고(화면설계서 00-common 4.3의 응답 지연) 그사이 다른 기기가 그 거래를 고친 경우, 내가 고친 내용은 반영되지 않고 알림만 뜬다.
- 받아들인 위험: 전체 복원 뒤에는 고쳐지지 않은 거래의 재전송도 내용을 비교하지 않고 200이 된다(ADR 008 결정 10). 내가 고쳐 다시 저장한 입력이면 고친 내용은 반영되지 않고 알림만 뜬다.
- 받아들인 위험: 저장된 뒤 권한을 잃은 입력을 다른 장부로 바꿔 보내면 같은 지출이 두 장부에 남을 수 있다. 앞 장부는 그 사람이 더는 볼 수 없거나, 보기 전용이 되어 고칠 수 없는 장부다.
- 받아들인 위험: 장부를 영구 삭제하면 완전 삭제 기록도 지워져 그 id를 다시 쓸 수 있게 된다. 예전 구성원이 알고 있던 id로 시험하면 영구 삭제 여부를 알 수 있지만, 그 사람은 장부가 404로 바뀌는 것으로도 알 수 있다(ADR 002의 `NO_LONGER_MEMBER` 행).
- 받아들인 위험: 참조 검증보다 id 조회가 먼저라 저장하지 않고도 어떤 id가 쓰였는지 시험할 수 있다. id는 무작위 74비트가 든 값이라 맞힐 수 없다고 본다. 서버는 UUID 형식만 검사한다.
- 다시 검토할 조건: 실기기 시험 결과가 나쁠 때, 네이티브 앱(4단계)을 기획할 때, 오프라인 수정 요구가 생길 때. 이벤트 자동 소속의 재계산이 결정 3의 "내용"에 해당하는지는 2단계에서 정한다.

지금 코드와 다른 점은 다음과 같다. 구현 이슈에서 맞춘다(확인, main `a913494`).

- `TransactionService.create`는 입력 검증(형식, 계좌, 카테고리, 결제한 사람)을 기존 거래 조회보다 먼저 한다. 형식 검증, 참조 검증, 저장할 내용 만들기가 `resolve` 한 곳에 섞여 있다.
- `replay`는 `version`과 관계없이 저장된 거래의 지금 내용과 늘 비교하고, 만든 사람(`createdBy`)을 보지 않는다.
- `create`는 처음 만든 것과 다시 보낸 것 모두 같은 값(`TransactionView`)을 돌려준다. 201과 200을 나눌 수 없다.
- 완전 삭제 기록을 확인하지 않는다. 완전 삭제는 아직 없다.
- 같은 id의 요청이 동시에 온 경우를 따로 처리하지 않는다.
- `IdConflictException`은 내용이 다를 때와 다른 장부의 id일 때를 구분하지 않고, 저장된 자원을 담지 않는다. `StaleVersionException`도 최신 자원을 담지 않는다.
- 웹에는 오프라인 입력 코드가 아직 없다.

이 결정으로 고칠 이슈와 문서는 다음과 같다. "지금"은 2026-11-25에 읽은 상태다(확인).

| 대상 | 지금 | 고칠 것 |
|---|---|---|
| #14 | "같은 id로 내용이 다른 요청이 오면 덮어쓰지 않고 거부된다" | 결정 3의 표와 결정 4의 검사 순서로 바꾼다 |
| #21 | 다른 장부의 id는 "내 장부에 없는 id로 실패할 때와 구분되지 않는 응답"이고, 같은 장부 안의 재전송은 그대로다 | 결정 3의 표로 바꾼다 |
| #3 | 옮겨진 거래마다 이력에 "카테고리 이동"이 남는다. `version`은 적혀 있지 않다 | 옮긴 거래의 `version`도 올린다는 기준을 더한다 |
| 오프라인 입력 web 이슈(F-103~F-109) | 아직 없다 | 등록할 때 이 ADR에 맞춘다 |
| 화면설계서(planner, designer) | B-05의 거부 이유 문구에 `ID_CONFLICT`가 없다. "서버 내용으로 맞췄다" 알림과 결정 3의 선택 화면이 없다 | B-05의 거부 이유 문구, 알림의 문구와 자리, 선택 화면을 더한다 |
