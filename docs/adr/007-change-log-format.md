# ADR 007: 변경 이력의 저장 형식과 삭제 때 처리

- 상태: 제안됨 (2026-11-24)
- 결정한 사람: owner(삭제 때 이력 처리 세 가지, 2026-11-24), dba(이력의 순서와 자동 삭제의 "누가", #60과 #102), architect(나머지). 검토: dba, security

## 배경

- `change_log`는 거래의 전후 값을 JSONB로 담는다. 지금 전후 값은 `TransactionView`를 Jackson으로 그대로 직렬화한 JSON이다(확인, main `48aa00e`).
- 전후 값에는 가맹점, 메모, 금액, 계좌·카테고리 id와 사람을 가리키는 `createdBy`, `paidBy`(사용자 id)가 있다. 사람 이름과 이메일은 없다(확인).
- `change_log`에는 FK가 없고 인덱스는 기본 키를 빼면 `(transaction_id, created_at)`뿐이다. `actor_id`는 NOT NULL이다(확인, V1). `ChangeAction`은 `CREATE`, `UPDATE`, `CANCEL`, `DELETE`, `RESTORE`다(확인).
- 거래 완전 삭제, 장부 영구 삭제, 탈퇴는 아직 구현되지 않았다(확인).
- Spring Boot 4.2 이전(PR #100, 2026-11-24 현재 머지 전)은 JSON 라이브러리를 Jackson 2에서 3으로 바꾼다. 같은 거래의 저장 JSON이 같다는 것은 ledger가 확인했다(PR #100 본문). 라이브러리를 바꿀 때 저장 형식을 확인해야 하는 것은 형식이 라이브러리와 `TransactionView`에 묶여 있기 때문이다.
- owner가 2026-11-24에 삭제 때 이력 처리를 정했다(결정 1). 기획 문서는 이 결정으로 고쳐졌다(P-110, P-215, P-216, P-308. PR #99). 30일 자동 영구 삭제의 "누가"를 어떻게 적을지는 P-215에 미정으로 남아 있다(확인. F-232에도 같은 문장이 있다).
- dba가 정한 것: 이력의 순서는 거래 `version`으로 한다(#60). 30일 자동 삭제의 이력 행은 `actor_id`를 NULL로 두고 사람이 한 완전 삭제와 다른 action 값으로 구분한다(#60, #102).
- 백업 보관은 최장 35일이다(owner 결정, dba 전달. P-229).

## 결정

### 1. 이력의 수명은 대상의 수명에 묶는다

owner 결정(2026-11-24)은 다음 세 가지다.

1. 장부 영구 삭제와 탈퇴 영구 삭제 때는 이력도 지운다.
2. 거래를 완전히 지우면 이력에는 "누가 언제 지웠다"만 남기고 내용 값은 지운다.
3. 탈퇴한 사람의 이름 자리는 비운다(`actor_id`는 NULL).

1번의 탈퇴는 혼자 쓰던 장부를 함께 지우는 경우다. 공유 장부에 남는 이력은 3번을 따른다(P-110, P-216).

### 2. "추가만 한다"의 범위

살아 있는 거래(휴지통에 있는 거래 포함)의 이력은 추가만 하고 고치거나 지우지 않는다. 이력 행을 고치거나 지우는 경로는 아래 정리 작업 세 가지뿐이다.

| 정리 작업 | 이력에 하는 일 | 남는 것 |
|---|---|---|
| 거래 완전 삭제 | 그 거래의 기존 이력 행은 남기고 `before_value`, `after_value`를 NULL로 바꾼다. 완전 삭제를 기록하는 행을 하나 더한다. 그 행에는 전후 값이 없다 | 행마다 무엇을 했는지(action), 누가, 언제 |
| 장부 영구 삭제(혼자 쓰던 장부의 탈퇴 포함) | 그 장부의 이력 행을 전부 지운다. 장부 삭제 작업이 이력을 먼저 지운다 | 없다 |
| 탈퇴(공유 장부에 남는 이력) | 행은 남기고 그 사람을 가리키는 값을 비운다(결정 5) | 비운 값을 뺀 나머지 |

### 3. 전후 값에 넣는 것과 넣지 않는 것

- 전후 값은 그 시점 거래의 값이다.
- 사람은 사용자 id로만 가리킨다. 이름, 이메일, 표시 이름은 넣지 않는다. 화면에 보이는 이름은 api가 응답을 만들 때 붙인다(ADR 002, ADR 004).
- 토큰, 기기 정보, 요청 정보는 넣지 않는다.

### 4. 형식을 이력 전용으로 고정한다

- 전후 값의 모양은 이력 전용 타입으로 정한다. API 응답 객체나 다른 용도의 읽기 모델을 그대로 직렬화하지 않는다. 응답 모양을 바꿔도 이력 형식이 따라 바뀌지 않게 하기 위해서다.
- 행마다 형식 버전(`format_version`, 1부터)을 둔다. 전후 값의 필드를 바꾸면 버전을 올리고, 읽는 쪽이 버전별로 해석한다. 지난 행은 다시 쓰지 않는다.
- 값 형식은 ADR 002를 따른다: 금액은 정수 원, 날짜는 `YYYY-MM-DD`, 시각은 `HH:mm`, 서버 기록 시각은 UTC `Z`다.
- 저장되는 JSON 모양을 고정하는 테스트를 둔다. 라이브러리를 올리거나 타입을 고쳤을 때 모양이 바뀌면 테스트가 알려 준다.
- 지금 있는 행(형식 버전이 없던 때의 것)은 버전 1로 본다.

버전 1은 지금 저장되는 모양이다(확인, main `48aa00e`에서 거래를 저장해 `before_value`와 `after_value`를 읽었다).

| 자리 | 필드 |
|---|---|
| 거래 | `id`, `ledgerId`, `type`, `occurredOn`, `occurredTime`, `payee`, `memo`, `status`, `createdBy`, `paidBy`, `version`, `deleted`, `createdAt`, `updatedAt`, `lines` |
| `lines`의 항목 | `accountId`, `categoryId`, `amount` |

- 값이 없는 필드는 빼지 않고 `null`로 넣는다. `CREATE` 행은 `before_value`가 NULL이다.
- `amount`는 부호가 있는 정수 원이다. `deleted`는 휴지통에 있는지를 나타내는 참·거짓 값이다.
- `occurredOn`은 `2026-11-18`, `occurredTime`은 `12:30:00`이다(밀리초가 있으면 `07:05:09.123`). `createdAt`과 `updatedAt`은 `2026-11-24T08:30:43.292603Z`처럼 마이크로초까지 적힌다. `occurredTime`과 두 기록 시각의 자릿수는 ADR 002의 형식(`HH:mm`, 밀리초 3자리)과 다르다(확인).

### 5. 사람을 가리키는 값과 탈퇴

- `actor_id`는 NULL을 허용한다.
- 탈퇴 정리 작업은 그 사람의 `actor_id`를 NULL로 바꾸고, 전후 값 JSON 안에서 그 사람을 가리키는 id(`createdBy`, `paidBy`)도 `null`로 바꾼다. 그 사람이 남긴 행의 기기 값(`device_id`)도 비운다.
- 탈퇴한 사람이 여럿이면 이력에서 서로 구분되지 않는다. 받아들인다. 화면에는 "탈퇴한 사용자"로 보인다(P-110).
- 거래 자체의 `created_by`, `paid_by`도 탈퇴 때 비울 수 있어야 한다. 컬럼을 어떻게 바꿀지는 dba가 정한다(#60 또는 탈퇴 구현 이슈).

### 6. 서버가 한 일의 "누가"

- 30일 자동 영구 삭제처럼 서버가 한 일은 `actor_id`를 NULL로 두고 action 값으로 구분한다(dba 결정).
- 따라서 `actor_id`가 NULL인 행은 action이 서버 동작이면 "자동", 사람 동작이면 "탈퇴한 사용자"다.
- 화면 문구는 planner가 정한다(P-215의 미정).

### 7. 순서와 장부 단위 처리

이력의 순서는 거래 `version`이다. `ledger_id`로 장부 단위 조회와 삭제를 할 수 있어야 한다. 컬럼, 제약, 인덱스는 #60이 정한다.

### 8. 백업과의 관계

- 지운 값은 백업에 보관 기간(최장 35일)만큼 남는다.
- 백업에서 복원하면 그사이 지운 것이 되살아난다. 복원 절차에는 백업 시점 뒤에 한 정리 작업(완전 삭제, 장부 영구 삭제, 탈퇴)을 다시 적용하는 단계가 있어야 한다.
- 그러려면 정리 작업의 기록(대상 id와 시각만)이 복원되는 DB 밖에도 남아야 한다. 방법은 ADR 008(#74)이 정한다.

### 9. 권한

공개 전에 DB 역할을 나눌 때, 일반 요청을 처리하는 경로는 `change_log`를 추가만 할 수 있게 하고 정리 작업만 고치고 지울 수 있게 한다. 시점과 방법은 dba가 정한다(#60의 범위 밖 항목).

## 검토한 대안

| 내용 | 좋은 점 | 대가 | 판단 |
|---|---|---|---|
| 이력을 영구 보관한다(처음의 P-216) | 가장 단순하고 감사 기록이 완전하다 | 지웠다고 안내한 지출 내용이 계속 남는다 | owner가 채택하지 않음(2026-11-24) |
| 완전 삭제 때 이력 행 자체를 지운다 | 구현이 가장 쉽다 | "누가 언제 지웠다"가 남지 않아 공유 장부에서 거래가 사라진 이유를 알 수 없다 | 채택하지 않음 |
| 전후 값을 암호화하고 키를 지워서 지운다 | 백업에 남은 값도 읽을 수 없게 된다 | 키 보관과 회전, 키를 잃으면 이력 전체를 잃는 위험. 지금 규모에 과한 장치다 | 채택하지 않음. 다시 볼 조건: 백업에 남는 기간을 줄여야 하는 요구가 생길 때 |
| 전후 값 전체 대신 바뀐 필드만 저장한다 | 저장량이 준다 | 어느 시점의 거래 모습을 보려면 처음부터 다시 쌓아야 하고 형식이 복잡해진다. 거래 한 건의 값은 작다 | 채택하지 않음 |
| 이력 형식을 `TransactionView` 직렬화 그대로 둔다(지금 방식) | 코드가 가장 적다 | 읽기 모델이나 라이브러리를 바꾸면 이력 형식이 모르는 사이에 바뀌고 지난 행과 달라진다 | 채택하지 않음 |

## 결과

- 좋아지는 것: 지웠다고 안내한 내용이 이력에 남지 않는다. 이력 형식이 다른 코드의 변경과 분리되고, 바뀔 때는 버전으로 드러난다.
- 대가: 이력 전용 타입 하나와 모양을 고정하는 테스트가 더해진다. 정리 작업 세 가지가 이력 행을 고치거나 지우므로 "한 번 쓰면 그대로"가 아니다. 탈퇴 정리는 그 장부의 이력 행을 훑어 JSON 안의 id를 바꿔야 한다.
- 받아들인 위험: 탈퇴한 사람이 여럿이면 구분되지 않는다. 지운 값이 백업에 최장 35일 남는다. 완전 삭제 뒤에는 그 거래에 무엇이 적혀 있었는지 되살릴 수 없다.
- 뒤집기 어려움: 이미 쌓인 이력의 형식은 고칠 수 없다. 형식 버전을 두는 이유다.
- 다시 검토할 조건: 감사 목적으로 이력을 더 오래 남겨야 하는 요구가 생길 때, 3단계에서 자동 입력(문자, 반복 거래)의 이력이 들어올 때.

이 결정으로 고칠 문서와 이슈는 다음과 같다. "지금"은 2026-11-24에 읽은 상태다(확인).

| 대상 | 지금 | 고칠 것 |
|---|---|---|
| #60 | 형식 버전, JSON 안의 사람 id, 기기 값이 없다 | 형식 버전 컬럼, JSON 안의 사람 id 정리, 기기 값 비우기를 더한다 |
| #9, #45 | 수용 기준이 아직 "변경 이력은 남는다"다. 기획 문서가 머지되면 고친다고 적혀 있고, 그 문서(PR #99)는 머지됐다 | 수용 기준을 P-215에 맞춘다 |
| P-215 | owner 결정이 들어갔다(PR #99). 자동 영구 삭제의 "누가"가 미정이다. planner는 화면 문구를 "자동 삭제"로 정해 #102에 적었다 | 미정 한 곳을 고친다(planner) |
| P-216 | owner 결정 세 가지가 들어갔다(PR #99) | 없다 |
| #23 | "변경 이력과 삭제" 항목이 체크되지 않았다 | PR #99와 이 ADR에 맞춰 그 항목을 정리한다(planner) |
