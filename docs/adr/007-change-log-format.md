## 배경

- `change_log`는 거래의 전후 값을 JSONB로 담는다. 이 ADR을 쓸 때 전후 값은 `TransactionView`를 Jackson으로 그대로 직렬화한 JSON이었다(확인, main `48aa00e`). 지금은 이력 전용 타입의 JSON이다(PR #179. 확인, main `e3376c3`).
- 전후 값에는 가맹점, 메모, 금액, 계좌·카테고리 id와 사람을 가리키는 `createdBy`, `paidBy`(사용자 id)가 있다. 사람 이름과 이메일은 없다(확인).
- 이 ADR을 쓸 때 `change_log`에는 FK가 없고 인덱스는 기본 키를 빼면 `(transaction_id, created_at)`뿐이었다. `actor_id`는 NOT NULL이었다(확인, V1). `ChangeAction`은 `CREATE`, `UPDATE`, `CANCEL`, `DELETE`, `RESTORE`였다(확인). 지금은 장부 FK, `(transaction_id, version)` 유니크, `(ledger_id, created_at)` 인덱스가 있고 `(transaction_id, created_at)` 인덱스는 없다. `actor_id`는 NULL을 허용하고 `ChangeAction`에 `PURGE`와 `AUTO_PURGE`가 있다(PR #175. 확인, main `e3376c3`).
- 거래 완전 삭제, 장부 영구 삭제, 탈퇴는 아직 구현되지 않았다(확인).
- Spring Boot 4.2 이전(PR #100, 2026-11-24 현재 머지 전)은 JSON 라이브러리를 Jackson 2에서 3으로 바꾼다. 같은 거래의 저장 JSON이 같다는 것은 ledger가 확인했다(PR #100 본문). 라이브러리를 바꿀 때 저장 형식을 확인해야 하는 것은 형식이 라이브러리와 `TransactionView`에 묶여 있기 때문이다.
- owner가 2026-11-24에 삭제 때 이력 처리를 정했다(결정 1). 기획 문서는 이 결정으로 고쳐졌다(P-110, P-215, P-216, P-308. PR #99). 30일 자동 영구 삭제의 "누가"를 어떻게 적을지는 P-215에 미정으로 남아 있다(확인. F-232에도 같은 문장이 있다).
- dba가 정한 것: 이력의 순서는 거래 `version`으로 한다(#60). 30일 자동 삭제의 이력 행은 `actor_id`를 NULL로 두고 사람이 한 완전 삭제와 다른 action 값으로 구분한다(#60, #102).
- 백업 보관은 최장 35일이다(owner 결정, dba 전달. P-229).

## 결정

### 1. 이력의 수명은 대상의 수명에 묶는다

owner 결정(2026-11-24)은 다음 세 가지다.

1. 장부 영구 삭제와 탈퇴 영구 삭제 때는 이력도 지운다.
2. 거래를 완전히 지우면 이력에는 "누가 언제 지웠다"만 남기고 내용 값은 지운다.
3. 탈퇴한 사람의 이름 자리는 비운다(`actor_id`는 NULL).

1번의 탈퇴는 혼자 쓰던 장부를 함께 지우는 경우다. 공유 장부에 남는 이력은 3번을 따른다(P-110, P-216).

### 2. "추가만 한다"의 범위

살아 있는 거래(휴지통에 있는 거래 포함)의 이력은 추가만 하고 고치거나 지우지 않는다. 이력 행을 고치거나 지우는 경로는 아래 정리 작업 세 가지뿐이다. 추가는 일반 경로, 삭제는 거래 완전 삭제와 장부 영구 삭제, 수정은 탈퇴 정리 하나뿐이다.

| 정리 작업 | 이력에 하는 일 | 남는 것 |
|---|---|---|
| 거래 완전 삭제 | 그 거래의 기존 이력 행을 모두 지우고 완전 삭제 기록 행 하나를 더한다. 거래 행 삭제, 기존 이력 삭제, 기록 행 추가는 한 트랜잭션이다(#9, PR #175) | 기록 행 하나 |
| 장부 영구 삭제(혼자 쓰던 장부의 탈퇴 포함) | 그 장부의 이력 행을 전부 지운다. 장부 삭제 작업이 이력을 먼저 지운다. 장부 삭제와 그 이력 삭제는 한 트랜잭션이다 | 없다 |
| 탈퇴(공유 장부에 남는 이력) | 행은 남기고 그 사람을 가리키는 값을 비운다(결정 5) | 비운 값을 뺀 나머지 |

- 완전 삭제 기록 행에는 거래 id, 장부 id, action, 누가(자동 삭제면 비운다), 언제, `version`만 있다. 전후 값과 기기 값은 없다.
- 이전 행들의 "누가 언제 고쳤다"는 남기지 않는다. owner 결정의 글자대로다.
- 완전 삭제는 이력 행을 고치지 않고 지우고 더하기만 한다.
- 정리 작업은 지우는 값을 애플리케이션 로그에 남기지 않는다. 건수와 대상 id만 남긴다.

### 3. 전후 값에 넣는 것과 넣지 않는 것

- 전후 값은 그 시점 거래의 값이다.
- 사람은 사용자 id로만 가리킨다. 이름, 이메일, 표시 이름은 넣지 않는다. 화면에 보이는 이름은 api가 응답을 만들 때 붙인다(ADR 002, ADR 004).
- 토큰, 기기 정보, 요청 정보는 넣지 않는다.

### 4. 형식을 이력 전용으로 고정한다

- 전후 값의 모양은 이력 전용 타입으로 정한다. API 응답 객체나 다른 용도의 읽기 모델을 그대로 직렬화하지 않는다. 응답 모양을 바꿔도 이력 형식이 따라 바뀌지 않게 하기 위해서다.
- 행마다 형식 버전(`format_version`, 1부터)을 둔다(PR #175에서 들어갔다). 전후 값의 필드를 바꾸면 버전을 올리고, 읽는 쪽이 버전별로 해석한다. 지난 행은 다시 쓰지 않는다.
- 이력의 저장 형식은 API 형식(ADR 002)과 별개다. 버전 1은 지금 저장되는 모양 그대로다(시각 `HH:mm:ss`, 서버 기록 시각은 마이크로초). 이력을 API로 내보낼 때 api가 ADR 002 형식으로 바꾼다. 저장 형식을 ADR 002에 맞추려고 버전을 올리지는 않는다.
- 저장되는 JSON 모양을 고정하는 테스트를 둔다. 라이브러리를 올리거나 타입을 고쳤을 때 모양이 바뀌면 테스트가 알려 준다.
- 형식 버전이 없던 때의 행은 버전 1로 본다. PR #175의 V13이 그 행에 1을 채웠다.

버전 1의 필드와 값은 다음과 같다(확인, main `48aa00e`에서 거래를 저장해 `before_value`와 `after_value`를 읽었다).

| 자리 | 필드 |
|---|---|
| 거래 | `id`, `ledgerId`, `type`, `occurredOn`, `occurredTime`, `payee`, `memo`, `status`, `createdBy`, `paidBy`, `version`, `deleted`, `createdAt`, `updatedAt`, `lines` |
| `lines`의 항목 | `accountId`, `categoryId`, `amount` |

- 값이 없는 필드는 빼지 않고 `null`로 넣는다. `CREATE` 행은 `before_value`가 NULL이다.
- `amount`는 부호가 있는 정수 원이다. `deleted`는 휴지통에 있는지를 나타내는 참·거짓 값이다.
- 전후 값의 `lines` 순서는 뜻이 없다. 비교하거나 보여 줄 때 순서를 쓰지 않는다(dba, PR #179. ADR 006 결정 3과 같다). 형식 버전은 1 그대로다.
- `occurredOn`은 `2026-11-18`, `occurredTime`은 `12:30:00`이다(밀리초가 있으면 `07:05:09.123`). `createdAt`과 `updatedAt`은 `2026-11-24T08:30:43.292603Z`처럼 마이크로초까지 적힌다. 소수 자릿수는 고정이 아니다. 기록 시각은 값에 따라 0, 3, 6자리이고 `occurredTime`은 끝의 0이 빠진다(`07:05:09.12`)(확인).

### 5. 사람을 가리키는 값과 탈퇴

- `actor_id`는 NULL을 허용한다.
- 탈퇴 정리 작업은 그 사람의 `actor_id`를 NULL로 바꾸고, 전후 값 JSON 안에서 그 사람을 가리키는 id(`createdBy`, `paidBy`)도 `null`로 바꾼다. 그 사람이 남긴 행의 기기 값(`device_id`)도 비운다. 그 사람의 행을 `actor_id`로 찾으므로 `actor_id`와 기기 값은 같은 문장에서 비운다.
- 탈퇴 정리의 대상은 그 사람이 구성원이었던 모든 공유 장부다. 이미 나갔거나 내보내진 장부도 포함하며, 지난 구성원 기록(ADR 002의 `NO_LONGER_MEMBER` 판정에 쓰는 기록)으로 찾는다.
- 탈퇴 정리 뒤 그 사용자 id가 `change_log`의 어느 컬럼과 전후 값에도 남아 있지 않다는 것을 전체 검색 테스트로 고정한다(구현 이슈에서).
- 탈퇴한 사람이 여럿이면 이력에서 서로 구분되지 않는다. 받아들인다. 화면에는 "탈퇴한 사용자"로 보인다(P-110).
- 거래 자체의 `created_by`, `paid_by`도 탈퇴 때 비울 수 있어야 한다. 탈퇴 작업이 직접 비우고 FK의 `ON DELETE SET NULL`에 기대지 않는다(정리가 빠지면 사용자 행 삭제가 실패해 드러나게). 컬럼과 구현은 탈퇴 구현 이슈에서 한다(dba).

### 6. 서버가 한 일의 "누가"

- 30일 자동 영구 삭제처럼 서버가 한 일은 `actor_id`를 NULL로 두고 action 값으로 구분한다(dba 결정). 완전 삭제의 action 값은 사람이 한 것이 `PURGE`, 30일 자동 삭제가 `AUTO_PURGE`다(PR #175).
- 따라서 `actor_id`가 NULL인 행은 action이 서버 동작이면 "자동", 사람 동작이면 "탈퇴한 사용자"다.
- 승인취소 되돌리기(F-226)의 action 값은 `UNCANCEL`이다. 사람 동작이고 거래 `version`을 올린 뒤의 값이며, 전후 값의 `status`가 취소에서 취소 직전 상태로 바뀐다(#7). 앱의 `ChangeAction`과 DB의 `ck_change_log_action_values`에 함께 더했다(V22).
- 화면 문구는 planner가 "자동 삭제"로 정했다([#102 댓글](https://github.com/lomong7807/akkimpyo/issues/102#issuecomment-7126144686)). P-215와 F-232의 미정 문장을 고치는 것은 planner의 몫이다.

### 7. 순서와 장부 단위 처리

- 이력의 순서는 거래 `version`이다. 완전 삭제 기록 행의 `version`은 거래 행의 `version` + 1이다. 순서 번호(`change_log.version`)는 PR #175에서 들어갔다. 그 전의 행은 `created_at` 순서가 아니라 `after_value`의 `version`으로 채웠다(#102 ledger, dba).
- 완전히 지운 거래의 id는 다시 쓸 수 없다. DB 제약이 아니라 만들기 경로가 완전 삭제 기록을 확인해서 지킨다(PR #175에서 들어갔다). 기록이 있는 id로 만들기 요청이 오면 새로 만들지 않고 거부한다. 응답 code와, 다른 장부의 id일 때 장부의 존재가 드러나지 않게 하는 방법은 ADR 006(#72)에서 #21, ADR 002와 함께 확정한다. 오프라인에서 쌓아 둔 입력이 지워진 거래를 되살리지 않게 하기 위해서다. 오프라인에 쌓였던 재전송은 화면에서 "보낼 수 없음"이 된다(P-226). 다시 보내기와의 관계와 세부는 ADR 006(#72)에서 이어 다룬다.
- `ledger_id`로 장부 단위 조회와 삭제를 할 수 있어야 한다. 장부 FK와 `(ledger_id, created_at)` 인덱스가 들어갔다(#60, PR #175).

### 8. 백업과의 관계

- 지운 값은 백업에 보관 기간(최장 35일)만큼 남는다.
- 백업에서 복원하면 그사이 지운 것이 되살아난다. 복원 절차에는 백업 시점 뒤에 한 정리 작업(완전 삭제, 장부 영구 삭제, 탈퇴)과 탈퇴 신청, 탈퇴 취소를 다시 적용하는 단계가 있어야 하고, 다시 적용이 끝난 뒤에 서비스를 연다. 다시 적용이 끝난 뒤에 여는 것은 삭제 기록 장치가 있는 2단계부터의 규칙이다(ADR 008 결정 7).
- 그러려면 정리 작업과 탈퇴 신청, 탈퇴 취소의 기록이 복원되는 DB 밖에도 남아야 한다. 기록은 대상 id, 종류(수동 완전 삭제, 자동 삭제, 장부 영구 삭제, 탈퇴, 탈퇴 신청, 탈퇴 취소), 시각만이다. 탈퇴 신청과 탈퇴 취소는 출시 단계에 더한다(ADR 008 결정 8). 그 일을 한 사람의 id와 내용 값은 넣지 않는다.
- 이 기록은 추가만 되게 하고, 보관 기간이 지나면 지운다. 보관 기간은 그것이 필요한 백업보다 먼저 지워지지 않게 백업의 가장 긴 보관 일수보다 길게 잡는다(ADR 008 결정 8). 개인정보 처리방침에 적히는 값이라 owner 확인을 기다린다. 방법과 값의 기준은 ADR 008이다.

### 9. 권한

- "정리 작업"은 코드 경로를 뜻한다. 수동 완전 삭제(F-231)는 사용자의 요청으로 시작되지만 정리 작업 경로에 속한다. 그 밖의 요청 처리 경로는 이력을 추가만 한다.
- 권한도 결정 2의 셋으로 나뉜다: 추가는 일반 경로, 삭제는 거래 완전 삭제와 장부 영구 삭제, 수정은 탈퇴 정리.
- DB 역할 나눔은 owner가 운영 DB에 실제 지출을 넣기 시작하는 날 전에 한다(dba, `docs/db/migration-standards.md` 3절). 어떻게 강제할지는 dba가 정한다(ADR 005 결정 4의 계정 나눔과 맞춘다).

### 10. 기기 값

- `device_id`에는 기기 하나하나를 구분하는 고유 식별자를 담지 않는다. 기기와 브라우저의 종류를 나타내는 짧은 값을 클라이언트가 보낸다(예: `iphone.safari`, `mac.chrome`. 형식은 #21: 1~64자, 영문·숫자와 `. _ : -`).
- 서버가 정한 목록에 있는 값만 받고 목록에 없으면 `unknown`으로 저장한다. User-Agent 원문은 저장하지 않는다. 목록은 frontend가 제안하고 서버가 고정한다(#21의 `deviceId` 제약을 그 목록으로 좁힌다).
- 요청에 기기 값이 없으면 `unknown`으로 저장하고, 형식이 틀린 값은 거부한다(#102 ledger, security 의견). 형식 검사는 PR #159에 들어갔다. 값이 없는 요청을 `unknown`으로 바꾸는 구현은 #14이고 지금 서비스는 `null`을 그대로 저장한다(ledger, PR #168 검토. 확인, main `e3376c3`).
- 화면이 이 값을 "iPhone · Safari"처럼 바꿔 보여 준다(화면설계서 D-07).
- 이유: 변경 이력은 어느 종류의 기기에서 했는지만 보이면 된다(P-216). 기기 목록과 기기별 로그아웃 기능은 두지 않는다(P-109). 고유 식별자는 개인을 따라다니는 값이라 남기지 않는 편이 낫다.

## 검토한 대안

| 내용 | 좋은 점 | 대가 | 판단 |
|---|---|---|---|
| 이력을 영구 보관한다(처음의 P-216) | 가장 단순하고 감사 기록이 완전하다 | 지웠다고 안내한 지출 내용이 계속 남는다 | owner가 채택하지 않음(2026-11-24) |
| 완전 삭제 때 기록 행도 남기지 않고 이력을 모두 지운다 | 구현이 가장 쉽다 | "누가 언제 지웠다"가 남지 않아 공유 장부에서 거래가 사라진 이유를 알 수 없다 | 채택하지 않음 |
| 완전 삭제 때 기존 행을 남기고 전후 값만 NULL로 바꾼다(#60의 처음 안) | 이전에 누가 언제 고쳤는지가 남는다 | owner 결정의 글자("누가 언제 지웠다"만)보다 많이 남는다 | 채택하지 않음 |
| 전후 값을 암호화하고 키를 지워서 지운다 | 백업에 남은 값도 읽을 수 없게 된다 | 키 보관과 회전, 키를 잃으면 이력 전체를 잃는 위험. 지금 규모에 과한 장치다 | 채택하지 않음. 다시 볼 조건: 백업에 남는 기간을 줄여야 하는 요구가 생길 때 |
| 전후 값 전체 대신 바뀐 필드만 저장한다 | 저장량이 준다 | 어느 시점의 거래 모습을 보려면 처음부터 다시 쌓아야 하고 형식이 복잡해진다. 거래 한 건의 값은 작다 | 채택하지 않음 |
| 이력 형식을 `TransactionView` 직렬화 그대로 둔다(PR #179 전의 방식) | 코드가 가장 적다 | 읽기 모델이나 라이브러리를 바꾸면 이력 형식이 모르는 사이에 바뀌고 지난 행과 달라진다 | 채택하지 않음 |

## 결과

- 좋아지는 것: 지웠다고 안내한 내용이 이력에 남지 않는다. 이력 형식이 다른 코드의 변경과 분리되고, 바뀔 때는 버전으로 드러난다.
- 대가: 이력 전용 타입 하나와 모양을 고정하는 테스트가 더해진다. 정리 작업 세 가지가 이력 행을 지우거나(거래 완전 삭제, 장부 영구 삭제) 고치므로(탈퇴) "한 번 쓰면 그대로"가 아니다. 탈퇴 정리는 그 장부의 이력 행을 훑어 JSON 안의 id를 바꿔야 한다.
- 받아들인 위험: 탈퇴한 사람이 여럿이면 구분되지 않는다. 지운 값이 백업에 최장 35일 남는다. 완전 삭제 뒤에는 그 거래에 무엇이 적혀 있었는지, 그 전에 누가 언제 고쳤는지 되살릴 수 없다.
- 받아들인 위험: 복원 뒤 다시 적용한 수동 완전 삭제 기록 행은 action은 맞고 "누가"만 비어 있다. DB 밖 기록에 그 일을 한 사람의 id를 두지 않기 때문이다.
- 받아들인 위험: 전후 값은 계좌와 카테고리를 id로만 담는다. 지운 카테고리나 계좌는 이력에서 이름을 찾을 수 없고 화면은 "삭제된 카테고리"처럼 보인다. 이름을 전후 값에 넣지 않는 것은 이름을 바꿨을 때 이력과 어긋나지 않게 하기 위해서다.
- 받아들인 위험: 메모와 가맹점은 자유 입력이라 탈퇴한 사람의 이름이 다른 구성원이 쓴 값에 들어 있을 수 있다. 이 ADR로는 지울 수 없다.
- 뒤집기 어려움: 이미 쌓인 이력의 형식은 고칠 수 없다. 형식 버전을 두는 이유다.
- 다시 검토할 조건: 감사 목적으로 이력을 더 오래 남겨야 하는 요구가 생길 때, 3단계에서 자동 입력(문자, 반복 거래)의 이력과 합치기(F-239)가 들어올 때. 합치기에서 지우는 거래가 완전 삭제에 해당하는지와 엑셀 행 원문을 이력에 남기는 방식은 3단계 기획 때 이 ADR을 보완해 정한다.
