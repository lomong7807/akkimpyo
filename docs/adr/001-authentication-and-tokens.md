# ADR 001: 인증과 토큰 방식

- 상태: 제안됨 (2026-11-25)
- 결정한 사람: owner(토큰 방식과 기한, 2026-11-23), architect(나머지. 검토: security, ledger)

## 배경

- owner가 2026-11-23에 정한 것은 다음과 같다(#22).
  - 로그인 유지는 JWT로 한다. access token은 15분 동안 유효하고 Authorization 헤더로 보낸다.
  - refresh token은 서버에 저장하고 HttpOnly 쿠키로 준다. 회전하고 폐기할 수 있다.
  - 로그인은 마지막 통신부터 30일로 연장되고, 처음 로그인부터 180일이 지나면 절대 만료된다(P-106).
  - 비밀번호 해시는 Argon2id다. 비밀번호는 최대 72자를 유지한다(P-101).
  - 비밀번호를 바꾸면 다른 기기의 refresh token은 바로 폐기하고, 이미 나간 access token은 만료(최대 15분)까지 둔다. 이것을 P-108의 "모두 로그아웃"으로 본다.
  - 요청 횟수 제한은 출시 단계에 넣는다.
- 웹과 API는 같은 출처다(ADR 005). refresh 쿠키의 속성과 쿠키로 인증하는 요청의 CSRF 방어 조건은 ADR 005 결정 6에 있고, 세부는 이 ADR이 확정한다.
- 서버는 Spring Boot 모놀리스 하나이고 토큰을 만들고 검증하는 곳도 그 하나다. 인증 코드는 auth 모듈에, 보안 필터 설정과 401·403 응답 작성은 api 모듈에 둔다(ADR 004 결정 6).
- 클라이언트는 웹앱이고 4단계에 네이티브 앱이 같은 API를 쓴다. 인증은 브라우저와 네이티브 앱에서 모두 동작해야 한다(설계 5.4).
- 앞선 ADR이 이 ADR로 넘긴 것은 세 가지다.
  - 로그인 잠금 응답이 계정의 존재를 드러내지 않게 하는 방법(ADR 002 5절). 결정 8이 정한다.
  - 로그인과 가입처럼 인증 전에 받는 요청을 다른 출처에서 보냈을 때의 처리(ADR 005 결정 5). 결정 5가 정한다.
  - 네이티브 앱의 refresh token 방식(ADR 005 결정 6). 결정 9가 방향만 적는다.
- auth와 api 패키지, Spring Security 의존성은 아직 없다(확인, main `37813af`).

## 결정

### 1. access token

- JWT이고 15분 동안 유효하다. `Authorization: Bearer` 헤더로만 받는다. 쿠키나 쿼리로는 받지 않는다.
- 담는 값은 사용자 id(`sub`), 발급 시각, 만료 시각뿐이다. 이메일, 이름, 권한은 넣지 않는다. 권한은 요청마다 DB의 장부 구성원 정보로 판단한다.
- 토큰의 사용자가 없으면(탈퇴로 지워짐) 401이다. 서버는 요청마다 사용자가 있는지 확인한다. 권한 판단에 어차피 DB 조회가 필요해 더 드는 비용이 작다(추정).
- 서버는 access token을 저장하지 않고 개별로 폐기하지 않는다. 폐기가 늦어지는 최대 시간은 15분이다.
- 웹앱은 access token을 메모리에만 둔다. localStorage 같은 기기 저장소에 넣지 않는다. 화면을 새로 열면 갱신 요청으로 새 access token을 받는다.

### 2. 서명

- HS256(대칭 키)을 쓴다. 만드는 곳과 검증하는 곳이 같은 서버 하나이기 때문이다.
- 키는 환경 변수로만 받는다. 없거나 256비트보다 짧으면 서버가 뜨지 않는다(HS256 키의 하한은 RFC 7518 3.2절, 확인). 테스트용 키는 테스트 설정에만 둔다.
- 검증은 알고리즘을 HS256 하나로 고정한다. `alg=none`이나 다른 알고리즘의 토큰은 거부한다(RFC 8725 3.1절과 3.2절, 확인).
- 키를 바꾸면 그때까지 나간 access token이 모두 무효가 된다. 클라이언트는 401을 받고 갱신 요청으로 새 토큰을 받는다. refresh token은 서명한 값이 아니라 영향이 없다. 그래서 키 식별자(`kid`)와 여러 키를 함께 쓰는 장치는 두지 않는다.

### 3. refresh token

- 추측할 수 없는 무작위 값(256비트 이상)이다. JWT가 아니다. 서버는 해시만 저장한다.
- 로그인할 때 "계열" 하나가 생긴다(기기 하나의 로그인 하나). 갱신할 때마다 새 토큰으로 바꾸고(회전) 앞 토큰은 쓸 수 없게 된다.
- 기한: 갱신할 때마다 그때부터 30일이다. 계열의 절대 만료는 처음 로그인부터 180일이다. 절대 만료는 계열의 시작 시각으로 계산하고, 회전해도 바뀌지 않으며 연장되지 않는다.
- 재사용 감지: 이미 회전된 토큰이 다시 오면 그 계열 전체를 폐기한다. 그 기기는 다시 로그인해야 한다. 회전과 재사용 감지는 RFC 9700 4.14.2절에 있는 방식이다(확인).
- 회전 직후의 허용 시간: 회전 직후 짧은 시간 안에 온 바로 앞 토큰은 재사용으로 보지 않고 같은 계열의 새 토큰을 준다. 탭 두 개가 동시에 갱신하거나 응답을 못 받고 다시 보낸 경우를 위해서다. 이 시간의 값은 security가 정한다(초안 10초).
- 같은 refresh token으로 동시에 온 요청은 한 건만 회전을 일으킨다. 나머지는 허용 시간 규칙으로 같은 계열의 새 토큰을 받는다.
- 폐기되는 때는 다음과 같다.

| 때 | 폐기하는 계열 |
|---|---|
| 로그아웃 | 그 계열 |
| 비밀번호 바꾸기(P-108) | 지금 기기의 계열을 뺀 그 사용자의 모든 계열 |
| 모든 기기에서 로그아웃(출시 단계, P-109) | 그 사용자의 모든 계열 |
| 재사용 감지 | 그 계열 |
| 탈퇴(P-110) | 그 사용자의 모든 계열을 지운다 |

- 정리: 만료되거나 폐기된 행은 재사용 감지를 위해 계열의 절대 만료까지 남기고, 그 뒤 서버 안의 매일 도는 정리 작업이 지운다. 새 기술(큐, 외부 스케줄러)은 쓰지 않는다.
- 테이블과 컬럼은 #26에서 dba 검토를 받아 정한다.

### 4. refresh 쿠키

- 속성은 `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`다. Domain은 두지 않는다. 이름에 `__Secure-` 접두어를 붙인다. 유효 기간은 refresh token의 기한과 같다(ADR 005 결정 6).
- 운영 설정에서는 이 속성이 늘 켜져 있고 테스트로 고정한다.
- 로컬 개발(http)에서 브라우저가 Secure 쿠키를 받지 않는 경우(추정: 브라우저마다 다르다)를 위해 로컬 프로파일에서만 `Secure`와 접두어를 끌 수 있게 한다.
- refresh token은 응답 본문에 넣지 않는다.

### 5. 쿠키로 인증하는 요청과 다른 출처

- 쿠키로 인증하는 요청은 갱신과 로그아웃 둘뿐이다. 이 둘은 아래 두 조건을 모두 지켜야 하고, 하나라도 어긋나면 거부한다.
  - (가) `Origin` 헤더가 있으면 우리 출처와 같아야 한다.
  - (나) 전용 요청 헤더가 있어야 한다. 헤더의 이름은 #26에서 정한다.
- 로그인과 가입 등 `/api/v1/auth` 아래의 나머지 요청도 `Origin` 헤더가 있으면 우리 출처와 같아야 한다. 다른 출처에서 피해자를 공격자의 계정으로 로그인시키는 것(OWASP CSRF Prevention Cheat Sheet, 확인)을 막기 위해서다. 본문은 `application/json`만 받는다(ADR 002의 415).
- `Origin` 헤더가 없는 요청(브라우저가 아닌 클라이언트)은 (나)의 전용 헤더로만 걸러진다. 브라우저의 다른 사이트 양식은 전용 헤더를 붙일 수 없다. 다른 출처의 스크립트가 붙이면 늘 사전 요청을 거치는데(RFC 10017 6.1.3.3.2절, 확인), CORS 허용 설정이 없다(ADR 005 결정 5).
- Spring Security의 CSRF 기능은 끈다(세션이 없다). 위 방어를 테스트로 고정한다.

### 6. 로그인 응답과 화면의 흐름

- 로그인하면 access token을 응답 본문으로, refresh token을 쿠키로 준다.
- access token이 만료돼 401 `UNAUTHENTICATED`를 받으면 화면은 갱신 요청을 한 번 하고 원래 요청을 다시 보낸다. 갱신 요청이 401이면 로그인이 풀린 것이다(ADR 002, ADR 006).

### 7. 비밀번호

- Argon2id로 해시한다. 매개변수의 하한과 로그인 한 번의 해시 시간 상한은 security 제안을 따르고 #20에서 정한다.
- 사용자가 없어도 해시 비교를 해서 응답 시간으로 가입 여부가 드러나지 않게 한다(#12. OWASP Authentication Cheat Sheet에 있는 방식이다, 확인).
- 비밀번호는 8~72자다(P-101).

### 8. 로그인 잠금과 계정 노출

- 출시 단계에서 구현한다.
- 잠금(P-105)의 횟수 계산과 잠금 응답(429 `LOGIN_LOCKED`)은 가입된 이메일과 가입되지 않은 이메일에 똑같이 적용한다. 그래야 잠금 응답으로 가입 여부를 알 수 없다(추정).
- 로그인 실패 응답은 이메일이 없을 때와 비밀번호가 틀릴 때가 같다(P-105).

### 9. 네이티브 앱(4단계)

- 지금은 만들지 않는다. 방향만 적는다.
- 네이티브 앱은 쿠키 대신 refresh token을 요청 본문으로 주고받는 별도 경로를 쓰고 기기의 보안 저장소에 둔다. 계열, 회전, 재사용 감지, 기한은 웹과 같다.
- 4단계를 기획할 때 이 ADR을 보완한다.

### 10. 로그에 남기지 않는 것

- 비밀번호, access token, refresh token, 쿠키 값은 로그와 오류 응답에 남기지 않는다.
- 사용자는 이메일이 아니라 사용자 id로 적는다.

## 결과

- 좋아지는 것: 훔친 access token은 15분이면 끝난다. 훔친 refresh token은 다음 갱신 때 드러난다(훔친 쪽과 사용자가 모두 쓸 때다. RFC 9700 4.14.2절, 확인). 비밀번호를 바꾸면 다른 기기가 15분 안에 끊긴다. CSRF를 막아야 하는 곳이 `/api/v1/auth` 아래로 좁다.
- 대가: refresh token 테이블과 정리 작업이 필요하다. 화면은 401에서 갱신하고 다시 보내는 흐름을 구현해야 한다. 화면을 새로 열 때마다 갱신 요청이 한 번 나간다.
- 받아들인 위험: 폐기가 access token에는 최대 15분 늦게 닿는다.
- 받아들인 위험: 회전 직후의 허용 시간 동안은 훔친 바로 앞 토큰이 통한다.
- 받아들인 위험: 응답을 못 받고 허용 시간이 지난 뒤 다시 보내면 정상 사용자가 로그아웃된다.
- 되돌리기: 토큰 방식을 바꾸면 모든 사용자가 다시 로그인해야 한다. 데이터는 잃지 않는다.
- 다시 검토할 조건: 네이티브 앱을 기획할 때(결정 9), 공개 출시로 요청 횟수 제한과 잠금을 넣을 때(결정 8), 토큰을 검증하는 서비스가 늘 때.

이 결정으로 고칠 문서와 이슈는 다음과 같다. "지금"은 2026-11-25에 읽은 상태다(확인).
