# ADR 001: 인증과 토큰 방식

- 상태: 제안됨 (2026-11-25)
- 보완: 2026-11-25, 로그인할 때와 백업에서 복원할 때의 refresh token 폐기(결정 3), 비밀번호의 NFKC 정규화(결정 7)를 더하고 고칠 이슈 표의 정리 작업 행을 맞춘다(PR #147)
- 보완: 2026-11-25, 결정 7에서 NFKC를 쓰는 곳에 탈퇴 신청(F-018)을 더하고, 로그인이 쓰는 비밀번호 입구와 트랜잭션의 범위, 저장값을 다시 보는 것, 해시 자리를 기다리는 요청의 상한, 정규화 전 입력의 상한을 적는다(PR #167)
- 보완: 2026-11-26, 결정 3에 로그아웃의 처리와 폐기의 단위, 갱신의 401과 쿠키를, 결정 6에 탭 사이 잠금을 못 얻었을 때와 웹 로그아웃의 순서, 되살아난 화면을, 결정 7에 비밀번호 재설정을, 받아들인 위험 셋을 더하고 고칠 이슈 표의 #26, #28, #81 행을 맞춘다(PR #183)
- 결정한 사람: owner(토큰 방식과 기한, 2026-11-23), architect(나머지. 검토: security, ledger)

## 배경

- owner가 2026-11-23에 정한 것은 다음과 같다(#22).
  - 로그인 유지는 JWT로 한다. access token은 15분 동안 유효하고 Authorization 헤더로 보낸다.
  - refresh token은 서버에 저장하고 HttpOnly 쿠키로 준다. 회전하고 폐기할 수 있다.
  - 로그인은 마지막 통신부터 30일로 연장되고, 처음 로그인부터 180일이 지나면 절대 만료된다(P-106).
  - 비밀번호 해시는 Argon2id다. 비밀번호는 최대 72자를 유지한다(P-101).
  - 비밀번호를 바꾸면 다른 기기의 refresh token은 바로 폐기하고, 이미 나간 access token은 만료(최대 15분)까지 둔다. 이것을 P-108의 "모두 로그아웃"으로 본다.
  - 요청 횟수 제한은 출시 단계에 넣는다.
- 웹과 API는 같은 출처다(ADR 005). refresh 쿠키의 속성과 쿠키로 인증하는 요청의 CSRF 방어 조건은 ADR 005 결정 6에 있고, 세부는 이 ADR이 확정한다.
- 서버는 Spring Boot 모놀리스 하나이고 토큰을 만들고 검증하는 곳도 그 하나다. 인증 코드는 auth 모듈에, 보안 필터 설정과 401·403 응답 작성은 api 모듈에 둔다(ADR 004 결정 6).
- 클라이언트는 웹앱이고 4단계에 네이티브 앱이 같은 API를 쓴다. 인증은 브라우저와 네이티브 앱에서 모두 동작해야 한다(설계 5.4).
- 앞선 ADR이 이 ADR로 넘긴 것은 네 가지다.
  - 로그인 잠금 응답이 계정의 존재를 드러내지 않게 하는 방법(ADR 002 5절). 결정 8이 정한다.
  - 로그인과 가입처럼 인증 전에 받는 요청을 다른 출처에서 보냈을 때의 처리(ADR 005 결정 5). 결정 5가 정한다.
  - `Origin` 헤더가 없는 요청의 처리(ADR 005 결정 6). 결정 5가 정한다.
  - 네이티브 앱의 refresh token 방식(ADR 005 결정 6). 결정 9가 방향만 적는다.
- auth와 api 패키지, Spring Security 의존성은 아직 없다(확인, main `37813af`).

## 결정

### 1. access token

- JWT이고 15분 동안 유효하다. `Authorization: Bearer` 헤더로만 받는다. 쿠키나 쿼리로는 받지 않는다.
- 담는 값은 사용자 id(`sub`), 발급 시각, 만료 시각, 발급자(`iss`), 대상(`aud`)뿐이다. 검증할 때 발급자와 대상도 확인한다(#12). 이메일, 이름, 권한은 넣지 않는다. 권한은 요청마다 DB의 장부 구성원 정보로 판단한다.
- 토큰의 사용자가 없으면(탈퇴로 지워짐) 401이다. 서버는 요청마다 사용자가 있는지 확인한다. 권한 판단에 어차피 DB 조회가 필요해 더 드는 비용이 작다(추정).
- 만료 판정에 허용 오차를 두지 않는다. 서버가 하나라 시계 차이가 없다. 라이브러리 기본값이 60초이면 0으로 설정한다(#12).
- 서버는 access token을 저장하지 않고 개별로 폐기하지 않는다. 폐기가 늦어지는 최대 시간은 15분이다.
- 웹앱은 access token을 메모리에만 둔다. localStorage 같은 기기 저장소에 넣지 않는다. 화면을 새로 열면 갱신 요청으로 새 access token을 받는다.

### 2. 서명

- HS256(대칭 키)을 쓴다. 만드는 곳과 검증하는 곳이 같은 서버 하나이기 때문이다.
- 키는 환경 변수로만 받는다. 없거나 256비트보다 짧으면 서버가 뜨지 않는다(HS256 키의 하한은 RFC 7518 3.2절, 확인). 테스트용 키는 테스트 설정에만 둔다.
- 검증은 알고리즘을 HS256 하나로 고정한다. `alg=none`이나 다른 알고리즘의 토큰은 거부한다(RFC 8725 3.1절과 3.2절, 확인).
- 키를 바꾸면 그때까지 나간 access token이 모두 무효가 된다. 클라이언트는 401을 받고 갱신 요청으로 새 토큰을 받는다. refresh token은 서명한 값이 아니라 영향이 없다. 그래서 키 식별자(`kid`)와 여러 키를 함께 쓰는 장치는 두지 않는다.

### 3. refresh token

- 추측할 수 없는 무작위 값(256비트 이상)이다. JWT가 아니다. 서버는 해시만 저장한다.
- 로그인할 때 "계열" 하나가 생긴다(기기 하나의 로그인 하나). 갱신할 때마다 새 토큰으로 바꾸고(회전) 앞 토큰은 쓸 수 없게 된다. 한 계열에서 유효한 refresh token은 언제나 가장 마지막에 준 하나뿐이다.
- 로그인(가입 직후의 로그인 포함)이 성공했을 때 요청에 refresh 쿠키가 있고 그 쿠키가 가리키는 계열을 찾을 수 있으면, 지금 토큰이든 이미 회전된 토큰이든, 누구의 계열이든 그 계열을 폐기하고 새 계열을 만든다. 로그인이 실패하면 아무것도 폐기하지 않는다(architect 결정, #102, #26).
  - 같은 브라우저의 쿠키는 새 로그인으로 덮여 옛 계열을 폐기할 길이 없어지기 때문이다.
- 기한: 갱신할 때마다 그때부터 30일이다. P-106의 "마지막 통신부터 30일"은 "마지막 갱신부터 30일"로 구현한다. 차이는 access token의 유효 시간(15분) 이내다.
- 절대 만료: 처음 로그인부터 180일이다. 계열의 시작 시각으로 계산하고, 회전해도 바뀌지 않으며 연장되지 않는다.
- 재사용 감지: 이미 회전됐거나 무효가 된 토큰이 다시 오면 그 계열 전체를 폐기한다. 그 기기는 다시 로그인해야 한다. 회전과 재사용 감지는 RFC 9700 4.14.2절에 있는 방식이다(확인).
- 회전 직후의 허용 시간: 회전 직후 허용 시간 안에 바로 앞 토큰이 다시 오면 재사용으로 보지 않는다. 같은 계열의 새 토큰을 주고, 그 전에 준 토큰은 무효가 된다. 탭 두 개가 동시에 갱신하거나 응답을 못 받고 다시 보낸 경우를 위해서다.
  - 훔친 쪽이 허용 시간에 앞 토큰을 써도, 사용자가 자기 토큰으로 다음 갱신을 하는 순간 재사용으로 드러나 계열이 폐기된다.
  - 같은 refresh token으로 동시에 온 요청은 한 건만 회전을 일으킨다. 나머지는 허용 시간 규칙으로 같은 계열의 새 토큰을 받는다.
  - "바로 앞 토큰"은 가장 최근의 정상 회전에서 교체된 토큰 하나다. 허용 시간 안의 재발급은 회전으로 세지 않는다.
  - 허용 시간은 그 정상 회전의 시각부터 재고, 재발급으로 늘어나지 않는다.
  - 허용 시간은 10초다(security 결정).
- 폐기되는 때는 다음과 같다.

| 때 | 처리 |
|---|---|
| 로그아웃 | 그 계열을 폐기한다 |
| 로그인 성공(가입 직후의 로그인 포함) | 요청의 refresh 쿠키가 가리키는 계열을 찾을 수 있으면 그 계열을 폐기한다 |
| 비밀번호 바꾸기(P-108) | 지금 기기의 계열을 뺀 그 사용자의 모든 계열을 폐기한다 |
| 비밀번호 재설정(출시 단계, P-107) | 그 사용자의 모든 계열을 폐기한다 |
| 모든 기기에서 로그아웃(출시 단계, P-109) | 그 사용자의 모든 계열을 폐기한다 |
| 재사용 감지 | 그 계열을 폐기한다 |
| 탈퇴 신청(출시 단계, F-018) | 그 사용자의 모든 계열을 폐기한다 |
| 탈퇴 영구 삭제(출시 단계, F-020) | 그 사용자의 행을 지운다 |
| 백업에서 복원 | 모든 사용자의 refresh token 행을 지운다(ADR 008 결정 10) |

- 로그아웃은 refresh 쿠키만으로 처리하고 access token을 요구하지 않는다. 이미 회전된 토큰이어도 그 계열을 폐기하고 204다. 쿠키가 없거나 모르는 값이거나 이미 폐기된 계열이어도 204이고 쿠키를 지운다. 만료되거나 잘못된 `Authorization`이 붙어도 204다. 출처 조건(결정 5)에 어긋난 403은 쿠키를 지우지 않는다(#28).
- 폐기는 계열 단위다. 회전은 계열 행을 잠그거나 조건부로 바꿔 폐기되지 않은 계열에만 새 토큰을 만든다. 토큰 행 단위로 폐기하면 동시에 진행 중인 갱신이 넣은 새 토큰이 살아남기 때문이다(security 결정 2026-11-25, #26).
- 갱신의 401은 refresh 쿠키를 지우지 않는다. 늦게 온 401이 다른 탭의 새 로그인을 지우지 않게 하기 위해서다(security 결정 2026-11-25, #26).
- 비밀번호 바꾸기의 경로는 `/api/v1/auth` 아래에 둔다(ADR 004에서 이 동작은 auth 모듈이다). 요청에는 access token과 refresh 쿠키가 함께 온다. 서버는 쿠키의 계열을 "지금 기기의 계열"로 보고 남긴다. 쿠키가 없거나 유효하지 않으면 모든 계열을 폐기한다.
- 정리: 만료되거나 폐기된 행은 재사용 감지를 위해 계열의 절대 만료까지 남기고, 그 뒤 서버 안의 매일 도는 정리 작업이 지운다. 새 기술(큐, 외부 스케줄러)은 쓰지 않는다.
- 테이블과 컬럼은 #26에서 dba 검토를 받아 정한다.

### 4. refresh 쿠키

- 속성은 `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`다. Domain은 두지 않는다. 이름에 `__Secure-` 접두어를 붙인다. 유효 기간은 refresh token의 기한과 같다(ADR 005 결정 6).
- 쿠키는 `/api/v1/auth` 아래의 모든 요청에 온다. 비밀번호 바꾸기는 이 쿠키로 지금 기기의 계열만 알아낸다(결정 3). 인증은 access token으로 한다.
- 운영 설정에서는 이 속성이 늘 켜져 있고 테스트로 고정한다.
- 로컬 개발(http)에서 브라우저가 Secure 쿠키를 받지 않는 경우(추정: 브라우저마다 다르다)를 위해 로컬 프로파일에서만 `Secure`와 접두어를 끌 수 있게 한다.
- refresh token은 응답 본문에 넣지 않는다.

### 5. 쿠키로 인증하는 요청과 다른 출처

- 쿠키로 인증하는 요청은 갱신과 로그아웃 둘뿐이다.
- `/api/v1/auth` 아래의 모든 요청은 아래 두 조건을 지켜야 한다. 로그인과 가입도 같다.
  - (가) `Origin` 헤더가 있으면 우리 출처와 같아야 한다.
  - (나) 전용 요청 헤더 `X-Akkimpyo-Client`가 있어야 한다. 값은 클라이언트의 종류다(웹앱은 `web`). 서버는 헤더가 있는지만 보고 값으로 판단하지 않는다.
- 하나라도 어긋나면 403이고 `code`는 `ORIGIN_NOT_ALLOWED`다(ADR 002 5절).
- `/api/v1/auth` 아래의 요청은 모두 쓰기 메서드(POST 등)로 둔다. GET으로 상태를 바꾸거나 토큰을 주는 경로를 만들지 않는다.
- 로그인과 가입까지 넣은 것은 다른 출처에서 피해자를 공격자의 계정으로 로그인시키는 것(OWASP CSRF Prevention Cheat Sheet, 확인)을 막기 위해서다. 본문은 `application/json`만 받는다(ADR 002의 415).
- `Origin` 헤더가 없는 요청(브라우저가 아닌 클라이언트)은 (나)로 걸러진다. ADR 005 결정 6이 이 ADR로 넘긴 "Origin 헤더가 없는 요청의 처리"는 이것으로 정한 것이다. 네이티브 앱의 refresh token 방식(결정 9)은 여전히 4단계 전에 보완한다.
- 브라우저의 다른 사이트 양식은 전용 헤더를 붙일 수 없다. 다른 출처의 스크립트가 붙이면 늘 사전 요청을 거치는데(RFC 10017 6.1.3.3.2절, 확인), CORS 허용 설정이 없다(ADR 005 결정 5).
- 우리 출처의 값은 환경 변수로 받는다. 없으면 서버가 뜨지 않는다. 운영은 출처 하나, 로컬은 화면 개발 서버의 출처(예: `http://localhost:5173`)다.
- Spring Security의 CSRF 기능은 끈다(세션이 없다). 위 방어를 테스트로 고정한다.

### 6. 로그인 응답과 화면의 흐름

- 로그인하면 access token을 응답 본문으로, refresh token을 쿠키로 준다. 토큰이 든 응답에는 `Cache-Control: no-store`를 붙인다.
- access token이 만료돼 401 `UNAUTHENTICATED`를 받으면 화면은 갱신 요청을 한 번 하고 원래 요청을 다시 보낸다. 갱신 요청이 401이면 로그인이 풀린 것이다(ADR 002, ADR 006).
- 화면은 탭 사이에 갱신 요청을 한 번에 하나만 보내도록 맞춘다. 방법은 frontend가 정한다.
- 탭 사이 잠금을 15초 동안 못 얻으면 로그인은 빼앗고 갱신은 지연 오류로 끝낸다(architect 결정 2026-11-25, #102, #78).
- 연결 없이 로그아웃한 기기: 화면은 기기에 "로그아웃 대기"를 남기고 대기가 있는 동안 갱신 요청을 하지 않는다. 연결되면 다른 요청보다 먼저 로그아웃 요청을 보내 쿠키와 계열을 지운다.
- 웹의 로그아웃은 204만 성공으로 보고 다음을 따른다(architect, security, frontend가 정함, 2026-11-26, #102). 구현의 자세한 조건은 #81에 있다.
  - 대기는 기기에 둔 "끝난 로그아웃의 값"이 로그아웃 값과 다른 것이다. 대기 키를 지우는 방식이 아니다(security, 2026-11-26, #102).
  - 대기가 있는 채 로그인하면 로그인을 먼저 보내고 성공하면 대기를 끝낸다(그사이 새 로그아웃이 있으면 로그아웃이 이긴다). "다른 요청보다 먼저"의 예외다. 로그인이 쿠키의 계열을 폐기하기 때문이다(결정 3).
  - 로그아웃 요청은 탭 사이 잠금 안에서 대기를 다시 보고 남아 있을 때만 보낸다.
  - 사용자가 누른 로그아웃은 15초 뒤 잠금을 빼앗고 자동 재시도는 빼앗지 않는다.
  - 되살아난 화면(뒤로 가기)은 갱신하지 않고 기기에 둔 값(로그아웃 값, 로그인 값)이 떠날 때와 같은지로 확인한다.

### 7. 비밀번호

- Argon2id로 해시한다. 매개변수는 라이브러리 기본값에 맡기지 않고 직접 설정한다. 하한은 메모리 19MiB, 반복 2, 병렬 1이다(security 제안. OWASP Password Storage Cheat Sheet의 최소, 확인). Spring Security 7.2.0의 기본값은 메모리 16MiB로 이보다 낮다(확인).
- 로그인 한 번의 해시 시간 상한은 security 제안을 따르고 #20에서 정한다.
- 동시에 도는 비밀번호 해시의 수에 상한을 둔다. 해시 하나가 메모리를 19MiB 이상 쓰고 가입되지 않은 이메일에도 해시를 하기 때문이다. 상한을 넘는 요청은 잠깐 기다리고, 기다림이 길어지면 429 `TOO_MANY_REQUESTS`로 답한다. 상한의 값은 서버 메모리 상한(#52)에 맞춰 security와 devops가 정하고 #20에서 넣는다. 요청 횟수 제한(출시 단계)과는 별개이며 1단계부터 둔다.
- 값은 동시 해시 수의 상한 4, 기다림 최대 2초, 해시 한 번 0.5초 이하다(security 제안. 상한 4는 devops가 서버 메모리 상한 초안과 맞는다고 확인했다, #20). 값이 바뀌면 #20이 기준이다.
- 해시 자리를 기다리는 요청은 16개까지다. 그다음 요청은 기다리지 않고 바로 429다(security 결정 2026-11-25, #20, PR #166 검토).
- 해시보다 싼 검사(형식, 길이, 전용 헤더와 `Origin`)를 해시보다 먼저 한다.
- 사용자가 없어도 해시 비교를 해서 응답 시간으로 가입 여부가 드러나지 않게 한다(#12. OWASP Authentication Cheat Sheet에 있는 방식이다, 확인).
- 로그인이 쓰는 입구는 user의 공개 메서드 하나다. 이메일과 비밀번호가 맞으면 사용자 id(와 나중에 다시 볼 확인 결과)를 준다. 이메일 정규화, 조회, 해시 비교가 그 안에 있고 auth는 해시를 모른다. 정규화와 시간 맞추기를 한 곳에 모으기 위해서다(architect 결정 2026-11-25, #102).
- 그 메서드는 사용자가 없을 때와 저장값이 비교할 수 없는 모양일 때도 가짜 해시와 비교한다(#102).
- 비밀번호의 확인과 해시는 트랜잭션 밖에서 한다. 해시가 DB 연결을 잡지 않게 하기 위해서다. 비밀번호 바꾸기는 저장과 refresh token 폐기만 auth가 여는 한 트랜잭션이다. ADR 004 결정 6의 "auth가 user를 불러 한 트랜잭션으로 처리한다"는 이 저장과 폐기를 뜻한다(#102).
- 확인과 저장이 다른 트랜잭션이므로, 로그인이 새 계열을 만드는 트랜잭션과 비밀번호 바꾸기의 트랜잭션은 사용자 행을 잠그고 확인할 때 본 저장값이 그대로인지 다시 본다. 달라졌으면 로그인은 실패(`INVALID_CREDENTIALS`), 바꾸기는 현재 비밀번호 오류로 끝낸다. 해시 자리를 기다리는 동안 비밀번호가 바뀌면, 옛 비밀번호로 확인한 로그인의 계열이 폐기 뒤에 생겨 남기 때문이다(architect 결정 2026-11-25, #102). #26과 #31에서 구현한다.
- 비밀번호 재설정(출시 단계, P-107)도 저장값을 바꾸므로 같은 잠금 안에서 저장과 모든 계열의 폐기를 한다(security, PR #167 검토).
- 이 비교는 user 안에서 하고 auth는 저장값을 모른다. auth는 user가 준 확인 결과를 그대로 user에 돌려준다(architect 결정 2026-11-25).
- 비밀번호는 8~72자다(P-101).
- 비밀번호는 규칙 검사와 해시보다 먼저 NFKC로 정규화한다. 비밀번호를 받는 모든 곳(가입, 로그인, 비밀번호 바꾸기, 출시 단계의 재설정과 탈퇴 신청(F-018))이 같은 함수를 쓴다. 길이와 "영문과 숫자"는 정규화한 값으로 센다(security 결정, PR #143과 #147 검토, #20).
- 정규화 전 입력이 512자(UTF-16 단위)를 넘으면 정규화도 해시도 하지 않고 거부한다. 정규화한 뒤 72자를 다시 본다(security 결정 2026-11-25, #20, #12).
- 정규화는 뒤집기 어렵다. 저장된 해시는 다시 만들 수 없다. 가입 API(#29)와 로그인(#12)을 열기 전에 넣는다.

### 8. 로그인 잠금과 계정 노출

- 출시 단계에서 구현한다.
- 잠금(P-105)의 횟수 계산과 잠금 응답(429 `LOGIN_LOCKED`)은 가입된 이메일과 가입되지 않은 이메일에 똑같이 적용한다. 그래야 잠금 응답으로 가입 여부를 알 수 없다.
- 로그인 실패 응답은 이메일이 없을 때와 비밀번호가 틀릴 때가 같다(P-105).

### 9. 네이티브 앱(4단계)

- 지금은 만들지 않는다. 방향만 적는다.
- 네이티브 앱은 쿠키 대신 refresh token을 요청 본문으로 주고받는 별도 경로를 쓰고 기기의 보안 저장소에 둔다. 계열, 회전, 재사용 감지, 기한은 웹과 같다.
- 4단계를 기획할 때 이 ADR을 보완한다. 4단계에 owner 확인이 필요하다.

### 10. 로그에 남기지 않는 것

- 비밀번호, access token, refresh token, 쿠키 값은 로그와 오류 응답에 남기지 않는다.
- 사용자는 이메일이 아니라 사용자 id로 적는다. 가입되지 않은 이메일의 로그인 실패는 사용자 id 없이 "알 수 없는 계정"으로 적는다. 입력된 이메일은 로그에 적지 않는다.

## 검토한 대안

| 내용 | 좋은 점 | 대가 | 판단 |
|---|---|---|---|
| 서버 세션(세션 id 쿠키) | 가장 단순하고 바로 폐기할 수 있다 | 모든 API가 쿠키로 인증돼 CSRF 방어 범위가 전체로 넓어진다. 네이티브 앱에서 쿠키를 다뤄야 한다 | 채택하지 않음. owner가 JWT로 정했다(2026-11-23) |
| refresh token도 JWT로 하고 서버에 저장하지 않는다 | 테이블이 필요 없다 | 폐기와 재사용 감지를 할 수 없다. 비밀번호를 바꿔도 다른 기기가 180일까지 남는다 | 채택하지 않음 |
| access token을 쿠키로 보낸다 | 화면이 토큰을 다루지 않아도 된다 | 상태를 바꾸는 모든 API가 CSRF 대상이 된다 | 채택하지 않음 |
| access token을 localStorage에 둔다 | 새로 열 때 갱신 요청이 필요 없다 | 화면에 스크립트가 끼어들면 토큰을 그대로 가져갈 수 있다(RFC 10017 8.5절, 확인). 메모리에 두면 가져가도 15분짜리이고 refresh token은 스크립트가 읽을 수 없다 | 채택하지 않음 |
| 비대칭 서명(RS256, EdDSA) | 검증만 하는 다른 서비스에 공개 키를 줄 수 있다 | 키 쌍을 관리해야 한다. 서버가 하나라 얻는 것이 없다 | 채택하지 않음. 다시 볼 조건: 토큰을 검증하는 서비스가 하나 더 생길 때 |
| 회전 직후의 허용 시간을 두지 않는다 | 규칙이 가장 엄격하다 | 탭 두 개나 불안정한 연결에서 정상 사용자가 로그아웃된다 | 채택하지 않음 |
| 비밀번호를 정규화하지 않는다 | 가장 단순하다 | 같은 글자가 조합형과 분해형으로 들어와 맞는 비밀번호가 틀렸다고 나온다 | 채택하지 않음 |

## 결과

- 좋아지는 것: 훔친 access token은 15분이면 끝난다. 훔친 refresh token은 다음 갱신 때 드러난다(훔친 쪽과 사용자가 모두 쓸 때다. RFC 9700 4.14.2절, 확인). 비밀번호를 바꾸면 다른 기기가 15분 안에 끊긴다. CSRF를 막아야 하는 곳이 `/api/v1/auth` 아래로 좁다.
- 대가: refresh token 테이블과 정리 작업이 필요하다. 화면은 401에서 갱신하고 다시 보내는 흐름, 탭 사이의 갱신 맞추기, 로그아웃 대기를 구현해야 한다. 화면을 새로 열 때마다 갱신 요청이 한 번 나간다.
- 받아들인 위험: 폐기가 access token에는 최대 15분 늦게 닿는다.
- 받아들인 위험: 회전 직후의 허용 시간 동안은 훔친 바로 앞 토큰이 통한다. 사용자가 다음 갱신을 하면 드러난다.
- 받아들인 위험: 응답 순서가 바뀌어 무효가 된 토큰이 쿠키에 남은 탭은 다음 갱신에서 로그아웃될 수 있다.
- 받아들인 위험: 응답을 못 받고 허용 시간이 지난 뒤 다시 보내면 정상 사용자가 로그아웃된다.
- 받아들인 위험: 연결 없이 로그아웃하면 연결되기 전까지 쿠키는 브라우저에 유효한 채로 있고, 기기를 만질 수 있는 사람은 "로그아웃 대기" 표시를 지우고 갱신을 요청할 수 있다. 기기 접근이 전제이고 30일(그 사이 갱신하지 않을 때)로 끝나므로 받아들인다.
- 받아들인 위험: 늦게 온 로그아웃 응답이 새 로그인의 쿠키를 지울 수 있다.
- 받아들인 위험: 다른 곳에서 한 폐기를 이 기기가 모르는 동안, 되살아난 화면에 같은 사용자의 내용이 보일 수 있다(결정 6).
- 받아들인 위험: Safari는 7일 동안 쓰지 않은 사이트의 localStorage를 지울 수 있다(추정. 홈 화면에 추가한 웹앱은 면제라고 설계 문서 3.3에 적혀 있다). 서버에 닿지 못한 로그아웃의 대기가 그렇게 사라지면, 다음에 열 때 남은 쿠키로 로그인이 되살아날 수 있다. 그 사이 갱신하지 않으면 쿠키의 기한(30일)에, 갱신하면 절대 만료(처음 로그인부터 180일)에 끝나므로 받아들인다(security).
- 받아들인 위험: 화면에 스크립트가 끼어들면 쿠키를 읽지 못해도 화면이 열려 있는 동안 사용자의 요청을 대신 보낼 수 있다(RFC 10017 5.1.4절, 확인). CSP로 줄인다(ADR 005).
- 되돌리기: 토큰 방식을 바꾸면 모든 사용자가 다시 로그인해야 한다. 데이터는 잃지 않는다.
- 다시 검토할 조건: 네이티브 앱을 기획할 때(결정 9), 공개 출시로 요청 횟수 제한과 잠금을 넣을 때(결정 8), 토큰을 검증하는 서비스가 늘 때.
