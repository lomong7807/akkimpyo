# 큰 장부 잔액 진단 (2026-11-25)

> **한계를 먼저 읽는다.**
> - 맥 로컬 Docker에서 **DB 실행 시간만** 잰 것이다. API 지연이 아니다(네트워크, Hibernate, 권한 확인 쿼리가 빠져 있다).
> - **운영 서버 수치가 아니다.** Apple M5 Pro에서 CPU 상한 없이 쟀다. 운영은 Ampere A1(4 OCPU), 메모리 24GB다. Docker Desktop VM(CPU 10개, 메모리 7.7GB) 안에서는 이 컨테이너 말고도 Docker Desktop의 Kubernetes(kind)가 돌고 있었다(`docker info`의 실행 중 컨테이너 22개). 다른 사용자 컨테이너는 `docker ps`에 없었다.
> - 쿼리를 한 번에 하나씩 돌렸다. 동시 요청은 재지 않았다.
> - 컨테이너의 페이지 캐시가 메모리 한도(1GB) 안에서만 쌓이게 맞추고 쟀다(3장 "캐시 상태를 맞춘 방법"). 처음에는 컨테이너째 재시작해 잰 값이 있었는데 그 값은 첫 실행의 블록 장치 읽기가 0에 가깝고 크게 빨랐다(3장). 그 방식으로 잰 값은 결과에 넣지 않았다.
> - E2의 (나) Docker VM 전체 캐시 비우기는 하지 않았다. 같은 VM에서 다른 컨테이너(Docker Desktop의 Kubernetes)가 돌고 있기 때문이다. 대신 측정용 DB 파일만 OS 페이지 캐시에서 내린 값을 같이 잰다(`posix_fadvise`의 DONTNEED). 맥 호스트가 VM 디스크 파일을 캐시하고 있는지는 확인하지 못했다.
> - 시간은 `EXPLAIN (ANALYZE, BUFFERS)`의 `Execution Time`이다. 노드마다 시간을 재는 비용이 들어 있고 계획 시간은 빠져 있다(E2의 첫 실행만 계획 시간을 따로 적었다).
> - 표본은 7개다. 백분위가 아니다. E2와 E7의 식은 캐시는 첫 실행을 세 번씩 재고 모두 적는다.
> - 통계는 `ANALYZE`의 표본이라 DB를 다시 만들면 예상 행 수가 조금씩 다르다. 같은 쿼리라도 계획이 병렬과 비병렬 사이에서 바뀔 수 있다. 실제로 5만 건 DB의 보통 장부 계좌 하나 잔액(리터럴)은 2차에서 병렬(작업자 1)이고 중앙값 2.4ms다(1차의 값은 1.139ms, 1차의 보통 장부 계획은 기록하지 않았다).
> - 데이터의 한계(날짜 순 입력, 수정 흔적 없는 테이블, 휴지통 2%, `change_log` 없음 등)는 [1차 문서](2026-11-24-query-baseline.md)의 한계와 같다. 다만 E7의 `1% 수정 뒤`만 UPDATE를 했다.
> - E7의 `ledger_id` 열과 후보 인덱스 A, B는 측정용 DB에 손으로 넣은 것이다. FK는 만들지 않았고 `ledger_id`에 NOT NULL만 걸었다. 앱 코드와 마이그레이션은 바꾸지 않았다.

## 1. 결과 요약

- **기준 다시 재기**(`perf_mix_50k`, `perf_mix_200k`, 큰 장부 = 1001): 큰 장부의 장부 전체 잔액 중앙값(리터럴)은 5만 건 1,923.4ms, 20만 건 2,473.5ms다(1차 2,637.4 / 2,894.2, 1,876.0 / 2,633.0). 모두 상한 200ms 밖이다. 계획은 중첩 루프이고 `transaction`·`transaction_line` 전체 훑기는 없다(`account`는 훑는다). 보통 장부는 5.6ms(5만 건과 20만 건)로 상한 안이다. 끝에 같은 방법으로 다시 잰 중앙값은 5만 건 1,987.5ms, 20만 건 2,103.4ms이고 모든 조건에서 계획 모양이 처음과 같다(4장 "기준 다시 재기").
- **E1 읽기 시간**(`track_io_timing=on`): 큰 장부의 장부 전체 잔액은 5만 건에서 실행 1,978.8ms 가운데 I/O 읽기가 1,473.9ms(74.5%), 20만 건에서 실행 2,489.1ms 가운데 1,834.9ms(73.7%)다. 보통 장부와 5만 건 계좌 하나는 읽기 시간이 0이다(캐시에 있다). 기준과 계획 모양은 모두 같다.
- **E2 식은 캐시 첫 실행**: (가) PostgreSQL만 재시작한 직후의 첫 실행에서, 큰 장부의 장부 전체 잔액은 5만 건 1,934.5 / 1,920.1 / 1,875.5ms(버퍼 read 129,995개), 20만 건 2,365.4 / 2,477.7 / 2,494.0ms(read 203,222개)이고 데운 뒤 기준과 같은 수준이다. 보통 장부는 5만 건 52.0 / 35.4 / 35.0ms, 20만 건 79.1 / 35.3 / 33.6ms로 상한 200ms 안이다. DB 파일의 OS 캐시까지 내린 첫 실행은 보통 장부가 5만 건 231~266ms, 20만 건 247~257ms로 상한 200ms 밖이다. 큰 장부는 5만 건 2,107.8~2,161.2ms, 20만 건 1,670.2~1,715.2ms다(4장 E2 표).
- **E3 캐시 크기**(`shared_buffers` 2GB, 컨테이너 메모리 4g): 읽기(버퍼 read)가 0이 되면서 계획은 그대로다. 큰 장부의 장부 전체 잔액 중앙값은 5만 건 115.5ms, 20만 건 380.0ms다. 5만 건은 상한 안, 20만 건은 상한 밖이다(20만 건은 읽기 없이도 380ms다).
- **E4 계획 선택**(`plan_cache_mode=auto`, psql의 `PREPARE` 뒤 10번): 큰 장부 값으로 10번이면 네 쿼리 모두 1~5번째는 값에 맞춘 계획, 6번째부터 일반 계획이다. 장부 전체 잔액은 두 계획의 모양이 같다. 20만 건 큰 장부의 계좌 하나 잔액은 5번째까지 약 284ms(281~290), 6번째부터 1,788~1,962ms다. 보통 장부 값으로 10번이면 장부 전체 잔액과 휴지통 목록, 20만 건의 계좌 하나 잔액은 10번 내내 값에 맞춘 계획이고, 5만 건의 계좌 하나 잔액과 월별 통계는 6번째부터 일반 계획이다. 보통 장부 5번 뒤 큰 장부 5번은 쿼리마다 다르다(E4 표). pgJDBC 42.7.11로 같은 문장을 돌리면 서버 쪽 준비된 문장은 5번째 실행에서 만들어지고(prepareThreshold 5, 프로젝트에 설정 없음), 값에 맞춘 계획 5번 뒤 10번째 실행부터 일반 계획이다.
- **E5 `random_page_cost=1.1`**: 큰 장부의 장부 전체 잔액은 5만 건 1,923.4ms에서 1,328.3ms, 20만 건 2,473.5ms에서 2,271.3ms다. 모두 상한 밖이다. 장부 전체 잔액의 여덟 조건 모두 `transaction_line`을 읽는 노드가 Bitmap Heap Scan에서 Index Scan으로 바뀐다(쓰인 인덱스는 같다). `account`는 여전히 훑는다(4장). 20만 건 큰 장부의 계좌 하나 잔액 리터럴은 병렬 해시 조인에서 중첩 루프로 바뀌어 285.4ms에서 806.7ms가 된다.
- **E6 통계 대상 수 1000**: 큰 장부의 장부 전체 잔액은 5만 건 1,964.5ms, 20만 건 2,402.8ms로 기준과 같은 수준이고 상한 밖이다. 조인 결과의 예상은 기준과 같다(5만 건 1,445행 대 실제 53,326행, 20만 건 1,515행 대 실제 213,272행). 계획 모양이 기준과 다른 것은 5만 건 보통 장부 계좌 하나 잔액 리터럴 하나뿐이다(병렬에서 비병렬).
- **E7 후보**(모두 같은 라인 `ledger_id` 값과 기준 조건, 큰 장부 리터럴 중앙값):
  - (0) 열만: 5만 건 1,698.9ms, 20만 건 4,980.1ms(버퍼 read 약 11만 7천, 31만 9천).
  - (가) 쿼리만: 5만 136.6ms(read 약 10만), 20만 225.5ms(read 약 12만). 상한은 5만 건에서 안, 20만 건에서 밖(최댓값 245.6ms)이다. `transaction_line`을 병렬로 훑는다.
  - (나) 쿼리 + A: 5만 83.4ms, 20만 144.1ms. 상한 안.
  - (다) 쿼리 + B: 5만 57.7ms, 20만 90.0ms. 상한 안. 5만·20만 큰 장부 리터럴에서 `transaction_line`을 훑는다.
  - (라) 쿼리 + A + B: 5만 24.4ms, 20만 51.4ms(버퍼 read 0). 상한 안.
  - 보통 장부(장부 전체 잔액 리터럴 중앙값): (0) 5.6 / 5.5ms, (가) 7.5 / 7.9, (나) 3.4 / 3.5, (다) 5.5 / 5.5, (라) 2.4 / 2.3 (5만 / 20만)로 모두 상한 안이다.
  - 일반 계획 강제에서는 큰 장부가 (가) 5만 649.6 / 20만 735.1ms, (나) 111.9 / 344.9, (다) 126.1 / 414.3, (라) 38.6 / 174.9ms다. 계좌 하나 잔액 일반 계획은 20만 건 큰 장부에서 (다)만 6,421.4ms, (0)과 (가)는 4,639.3 / 4,267.4ms다.
  - B의 대신 여부: 옛 인덱스를 지우고 B만 있을 때 월별 통계에는 B가 쓰인다(여덟 조건 모두 Index Only Scan, Heap Fetches 0). 휴지통 목록에는 쓰이지 않고 `transaction`을 Seq Scan으로 읽는다(여덟 조건 모두). 휴지통 목록 중앙값은 보통 장부가 1.1ms(5만) / 1.1ms(20만)에서 48.2ms / 49.6ms, 큰 장부 리터럴이 55.8 / 129.5ms에서 48.5 / 55.7ms다.
  - 대가: A는 247MB / 259MB, B는 193MB / 202MB. 라인을 포함한 거래 1,000건 넣기는 후보가 없을 때 중앙 102.7 / 99.2ms, A+B가 있을 때 138.4 / 150.3ms다(5만 / 20만).
- **거래 목록 50건**: 쿼리가 없어 재지 않았다.

## 3. 방법

명령과 절차는 [`perf/README.md`](../../../perf/README.md)의 "진단 측정"에 있다. 요약은 다음과 같다.

```sh
OUT=~/akkimpyo-perf-out perf/run-diagnosis.sh up seed base e1 e2 e3 e4 e5 e6 e7 base-again sleep-log
node perf/summarize-diagnosis.mjs ~/akkimpyo-perf-out
```

- 쿼리는 10번씩 한 psql 세션에서 돌리고 뒤의 7번을 센다(1차와 같다). 최솟값, 중앙값, 최댓값을 적는다. 시간은 밀리초다.
- 큰 장부는 장부 번호 1001, 보통 장부는 1이다. "리터럴"은 값을 문장에 넣은 것이고, "일반 계획"은 `PREPARE` 뒤 `plan_cache_mode = force_generic_plan`으로 `EXECUTE`한 것이다(E4만 `auto`).
- 계획 모양은 노드 이름, 테이블, 인덱스를 이어 비교한 것이다. 조인 예상/실제의 "조인"은 집계나 정렬 직전의 조인이고, `×`는 loops(병렬이면 프로세스 수)다.
- 버퍼는 실행 전체에서 찾은 8KB 블록 수다(hit = `shared_buffers`에 있던 것, read = 없어서 OS에서 읽은 것). 7번이 서로 다르면 범위로 적었다. "블록 장치 읽기(MB)"는 실행 하나가 컨테이너의 cgroup `io.stat`에서 실제로 읽은 바이트(중앙값)다. `read` 버퍼 가운데 OS 페이지 캐시에 있던 것은 0으로 나온다.
- "기준"은 아무 설정도 바꾸지 않은 상태다. 실험마다 한 가지만 바꾼다. E5와 E6는 기준의 리터럴과 일반 계획을 모두 다시 잰다.
- 시간대는 맥의 AC 전원, 절전 방지(`caffeinate -dims`)이고 절전 기록(`pmset -g log`)은 없다. 측정한 시각과 load average는 다음과 같다.

### 캐시 상태를 맞춘 방법

1차와 같은 설정이지만 다음은 다르게 했다. 근거는 이 측정에서 얻은 값이다.

- **같은 컨테이너에서만 캐시가 쌓이게 한다.** 컨테이너의 페이지 캐시는 컨테이너의 cgroup 메모리 한도(1GB)를 같이 쓴다. 준비 측정(표에는 넣지 않은 값)에서, 컨테이너째 다시 시작한 직후의 첫 실행은 2번째와 3번째에서 블록 장치 읽기가 0MB였다. 5만 건 큰 장부의 장부 전체 잔액이 세 번에 걸쳐 2,048.8 / 298.1 / 299.9ms(블록 장치 읽기 723 / 0 / 0MB)였고, 20만 건은 636.7 / 606.2 / 612.3ms(0 / 0 / 0MB)였다. 컨테이너를 다시 만든 뒤 잰 E4(기준 절차와 다른 상태)의 5만 건 큰 장부 장부 전체 잔액 10번은 230.9~266.1ms였다. 같은 준비 측정의 컨테이너 시작 직후 기준은 5만 건 2,410.8ms, 20만 건 3,105.1ms였다. 이전 컨테이너가 쓴 페이지 캐시가 새 cgroup의 한도에 들어가지 않고 남은 것으로 보인다(추정, 확인하지 않음). 이런 상태는 1차의 측정 상태와 다르므로, 준비 측정의 이 방법으로 잰 값(E4 일부와 E2의 컨테이너 재시작)은 버리고 아래 방식으로 전부 다시 쟀다.
- **PostgreSQL만 재시작한다.** 측정용 컨테이너는 셸이 PostgreSQL을 감싸 띄운다(`perf/compose.diag.yaml`). `pg_ctl restart`가 컨테이너를 유지하므로 같은 cgroup 안에서 캐시가 쌓인다. (가)는 이 방법으로 잰다.
- **실험마다 시작할 때 상태를 맞춘다.** PostgreSQL을 재시작한 뒤(`shared_buffers`가 빈다), 측정용 DB 파일을 OS 페이지 캐시에서 내린다(`dd iflag=nocache count=0`, `posix_fadvise` DONTNEED. 같은 파일에만 해당하고 VM 전체 캐시는 건드리지 않는다). 그런 다음 세 번을 버리고 7번을 센다. 이 상태는 캐시가 처음에는 비어 있고 1GB 한도 안에서만 쌓인다(세 번을 버리고 일곱 번을 센다).
- E7에서는 열을 넣은 뒤 `VACUUM (ANALYZE)`를 하고, 인덱스를 만들 때마다 `VACUUM (ANALYZE)`를 한 뒤 같은 방식으로 맞춘다. 1% 수정 뒤의 측정도 같은 방식으로 맞춘다(맞추는 데 쓴 재시작은 VACUUM을 하지 않는다).

### E3 캐시 크기 (`shared_buffers` 2GB, 컨테이너 메모리 4g)

앱(pgJDBC)이 실제로 서버 쪽 준비된 문장을 쓰는지 확인했다.

- pgJDBC 기본값: `prepareThreshold=5`, `preparedStatementCacheQueries=256`, `preferQueryMode=extended`(드라이버 42.7.11의 코드). pgJDBC 문서(jdbc.postgresql.org의 "Server Prepared Statements")는 "내부 카운터가 문장의 실행 횟수를 세고, `prepareThreshold`(기본 5)에 닿으면 이름 있는 문장으로 바꾸어 Prepare와 Execute를 쓴다"고 설명한다. 문장의 캐시는 연결마다 256개다.
- 이 프로젝트: `application.yml`에 `prepareThreshold`를 비롯한 pgJDBC 설정과 HikariCP 설정이 없다(연결 URL에 매개변수 없음). HikariCP(6.3.3)는 자신이 문장을 캐시하지 않는다(README의 "Statement Cache"). 따라서 pgJDBC 기본값이 쓰인다.
- `perf/PrepareThresholdCheck.java`(Hibernate처럼 실행할 때마다 `PreparedStatement`를 만들고 닫음)로 장부 전체 잔액을 같은 연결에서 14번 돌린 결과(DB 두 개에서 같다, psql에서 잰 시간이 아니라 서버 쪽 `pg_prepared_statements`의 값이다): 1~4번째 실행은 서버에 준비된 문장이 없다. 5번째 실행에서 이름 `S_1`(타입 `uuid`, `varchar`)이 만들어졌고 값에 맞춘 계획으로 실행됐다. 9번째까지 값에 맞춘 계획 5번이고, 10번째 실행부터 일반 계획이다. psql의 `PREPARE`(위 표)는 첫 `EXECUTE`부터 세어 6번째부터 일반 계획이었다. pgJDBC에서는 5번째 실행에 이름 있는 문장이 만들어져, 그 문장의 값에 맞춘 계획 5번(5~9번째 실행) 뒤 10번째부터 일반 계획이었다.

### E7 dba 후보

#### 넣은 내용과 확인

```sql
ALTER TABLE transaction_line ADD COLUMN ledger_id uuid;
UPDATE transaction_line l SET ledger_id = t.ledger_id FROM transaction t WHERE t.id = l.transaction_id;
ALTER TABLE transaction_line ALTER COLUMN ledger_id SET NOT NULL;
VACUUM (FULL, ANALYZE) transaction_line;
```

- 위 네 문장 뒤 `VACUUM (ANALYZE)`와 `CHECKPOINT`를 더 했다(`VACUUM FULL`이 visibility map을 만들지 않기 때문이다. 인덱스를 만든 뒤에도 매번 같은 명령을 했다).
- 결과 동일 확인: 두 DB 모두에서 (1) 모든 장부의 (장부, 계좌, 합) 행을 지금 쿼리와 후보 쿼리로 구한 두 결과가 같다(행 수 7,510 / 7,510, 한쪽에만 있는 행 0 / 0). (2) 장부 1001과 장부 1의 장부 전체 잔액, 계좌 하나 잔액을 지금 문장과 후보 문장으로 각각 실행해 결과를 비교했다(장부 1001의 계좌 10개, 장부 1의 계좌 6개, 장부 전체 잔액 2개로 18번). 모두 같다.

## 8. 확인과 추정

- 확인: 이 문서의 시간, 행 수, 버퍼, 크기, 계획 모양은 모두 직접 잰 값이다. 계획 원문은 10장에 있다.
- 추정: 3장의 "이전 컨테이너가 쓴 페이지 캐시가 남은 것으로 보인다"는 확인하지 않은 설명이다. 데이터 크기와 거래 종류 비율은 정해 둔 가정이다.

## 9. 못 잰 것

- Docker VM 전체 캐시 비우기(E2 (나)): 같은 VM에서 Docker Desktop의 Kubernetes가 돌고 있어 하지 않았다. 측정용 DB 파일만 내리는 방법으로 대신했고 맥 호스트의 캐시까지는 확인하지 못했다.
- API 지연, 화면 지표, 동시 요청, 운영과 같은 사양: 이번 범위가 아니다.
- E4의 실제 앱(Hibernate를 거친 쿼리 경로) 전체는 재지 않았다. 드라이버 수준의 확인(`PrepareThresholdCheck`)까지다. 앱이 같은 연결에서 같은 쿼리를 5번 넘게 되풀이하는지는 확인하지 않았다(HikariCP의 풀 크기와 요청 분포는 재지 않았다).
- 후보 쿼리를 실제 앱(Hibernate가 만든 바인드 변수 문장)으로 돌린 값은 없다. 후보의 일반 계획은 Hibernate처럼 바인드마다 다른 `$n`으로 잰 값이다(`ledger_id`를 `$1`, `$2`로 두 번).
- E7의 앱 쪽 변경과 함께 쓰는 쿼리(권한 확인, 계좌 목록 등)와 INSERT 이외의 쓰기(수정, 삭제)의 비용은 재지 않았다. 거래 넣기 비용은 순서를 바꿔 재지 않았다.
- 데이터의 한계(지난 날짜를 늦게 넣은 거래, 죽은 행, `change_log`, 30일 자동 삭제 뒤의 휴지통)는 1차와 같다.
