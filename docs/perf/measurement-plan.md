> **실측은 아직 하나도 없다.** 이 문서는 어떻게 잴지를 정한다. 결과가 생기면 6장의 양식으로 `docs/perf/results/`에 남긴다.

- 상태: 초안, 실측 전
- 작성일: 2026-11-24
- 목표는 [README](README.md), 위험은 [risks.md](risks.md)에 있다.

## 1. 시점별 계획

| 시점 | 무엇을 | 무엇으로 | 도구 |
|------|--------|----------|------|
| 1A(지금) | 통계·잔액 쿼리의 실행 계획과 시간 | 로컬 PostgreSQL 17, `EXPLAIN (ANALYZE, BUFFERS)`로 예상 행 수와 실제 행 수 비교 | 추가 없음 |
| 1A(지금) | 서비스 호출당 SQL 수 | Hibernate 통계를 쓰는 테스트 | 추가 없음 |

| 1C(화면이 생기면) | LCP, INP, CLS, 번들 크기 | 휴대폰·맥 조건을 나눈 시험, 빌드 산출물 크기 | Lighthouse (소유자 승인 2026-11-24) |
| 공개 뒤 | 실제 사용자의 화면 지표 | 화면에서 수집 | web-vitals (미결정, architect 검토 필요) |

## 2. 시험 데이터 (dba와 합의)

- 크기
  - 장부 1개에 거래 1만 2천 건(보통)
  - 장부 1개에 거래 5만 건(architect 기준)
  - 장부 1,000개에 거래 300만 건
  - 잔액 기준선은 계좌 하나에 라인 1만 / 5만 / 20만 건
- 분포: 여러 해에 걸친 날짜, 계좌 5~10개, 카테고리 30개 안팎, 삭제 2%, 취소 1%.
- SQL 스크립트로 만들고, 넣은 뒤 `ANALYZE`를 한다.
- 실제 카드 내역은 쓰지 않는다(CLAUDE.md 규칙).

## 3. 부하 테스트 방법

- 순서: 아주 작은 확인 → 평소 부하(초당 20건) → 한계 찾기. 모양은 단순하게 유지한다.
- 정해진 속도로 요청을 보내고, 지연은 "보내기로 한 시각"부터 잰다. 응답을 기다렸다 다음을 보내는 방식은 느린 구간을 빼먹는다.
- 도는 동안 CPU, 메모리, 디스크, 네트워크, DB 연결의 사용률·포화·오류를 같이 보고, 결과에 "왜 이 수치인지"를 적는다.
- 한 번 잰 값으로 판단하지 않는다. 개선을 적용한 뒤에는 같은 방법으로 다시 재고, 오류율 같은 부작용도 본다.

## 4. CI에 넣을 것 (제안, devops 검토 필요)

- SQL 수 테스트(서버 테스트의 일부)와 번들 크기 검사. 두 가지뿐이다.
- 부하 테스트는 CI 장비에서 수치가 흔들리므로 넣지 않는다. 조각(1A, 1B, 1C)이 끝날 때 손으로 돌린다.

## 5. pg_stat_statements (미결정)

- 볼 쿼리를 총 실행 시간 순으로 고르는 데 쓴다.
- 로컬 측정용으로 켜는 것에 dba는 동의했다. 조건은 두 가지다.
  - 공용 `compose.yaml`이 아니라 측정용 덮어쓰기 파일에 넣는다.
  - `CREATE EXTENSION`은 Flyway 마이그레이션에 넣지 않는다.
- devops 의견을 받은 뒤 소유자가 정한다.

## 6. 다시 재는 시점

- Spring Boot 4.2 이전(이슈 #17) 앞뒤.
- `transaction_line`에 `ledger_id`를 넣는 결정이 난 뒤.
- 조각(1A, 1B, 1C)이 끝날 때마다.

## 7. 결과 기록 양식

측정마다 다음을 적는다.

- 날짜
- 커밋
- 환경(장비, DB 버전, 데이터 크기)
- 방법(명령)
- 결과(p50/p95/p99/최댓값, 오류율)
- 측정 중 한계였던 자원
- 왜 이 수치인지
- 목표 대비 판정
- 확인/추정 구분

결과 파일은 `docs/perf/results/YYYY-MM-DD-주제.md`에 둔다. 이번 PR에서는 이 폴더를 만들지 않는다.
