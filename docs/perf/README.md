## 2. 목표

소유자가 2026-11-24에 채택했다.

| 대상 | 지표 | 초기 | 공개 뒤 |
|------|------|------|---------|
| 거래 목록 50건 | p95 / p99 | 200ms / 500ms | 같은 값을 초당 20건에서 |
| 월별·카테고리 통계, 잔액 | p95 / p99 | 300ms / 800ms | 같은 값을 초당 20건에서 |
| 거래 저장 1건 | p95 / p99 | 200ms / 500ms | 같은 값을 초당 20건에서 |
| 목록 | 호출당 SQL 수 | 4회 이하, 목록 건수와 무관 | 같음 |
| 통계 | 호출당 SQL 수 | 3회 이하 | 같음 |
| 저장 | 호출당 SQL 수 | 지금 값을 세어 상한으로 고정 | 같음 |
| 쿼리(DB 실행 시간) | 상한 | 거래 목록 50건 50ms, 월별 통계 100ms, 장부 전체 잔액 200ms. 세 쿼리의 실행 계획에 transaction, transaction_line 전체 훑기 없음 | 같음 |
| 화면 | LCP / INP / CLS | 시험 환경에서 2.5초 / 200ms / 0.1 | 실제 사용 75번째 백분위로 같은 값 |
| 화면 | 초기 경로 JS / CSS (gzip) | 150KB / 30KB | 같음 |
| 홈 화면 아이콘에서 입력창까지 | 걸린 시간 | 처음 열 때 2초 | 같음 |

### 2.1 표를 읽는 법

- API 시간은 서버가 잰 시간이다. 초기에는 사용자가 적어 실제 요청의 백분위가 의미 없으므로, 시험 데이터에 1,000회 이상 요청을 보내 판정한다.
- 지연은 평균이 아니라 p50, p95, p99, 최댓값으로 보고한다. 오류 응답의 지연은 따로 본다.
- 200ms의 근거(추정): INP 200ms 안에 저장 반응이 보여야 하고, LCP 2.5초에서 휴대폰 망 왕복과 화면 그리기를 빼면 API 몫이 이 정도다.
- 쿼리 상한은 dba가 architect에 제안한 값이며, 재서 고칠 값이다.
- 화면은 휴대폰(iPhone 홈 화면 앱)과 맥을 따로 잰다. iPhone Safari가 LCP와 INP를 보고하는지는 **미확인**이다.
- JS 150KB의 근거(추정): react와 react-dom만으로 약 60KB로 본다. 빌드해서 재지 않았다.
- "홈 화면 아이콘에서 입력창까지"는 설계 문서 10.1의 스파이크와 기능 F-120에 연결된다. 설계 10.1은 이 시간을 사용자가 자기 iPhone에서 직접 써 보고 판정한다고 정했다. 위 2초는 그 판정을 돕는 기준 값이다.
- 기획 문서에 이미 있는 성능 관련 정책은 다음과 같다.
  - 목록은 50건씩 불러온다(P-232).
  - 홈 최근 거래는 10건이다(F-113).
  - 일괄 수정은 최대 500건이다(F-243).

## 3. 개발자 점검표 (ledger, frontend)

기능을 만들거나 고칠 때 PR에서 확인한다.

1. 목록 API는 호출당 SQL 수를 테스트로 고정한다. 건수에 따라 늘면 안 된다.
2. 페이지 나누기와 라인 함께 읽기를 한 쿼리에 섞지 않는다. id를 먼저 자르고 라인은 한 번에 읽는다.
3. 페이지는 OFFSET이 아니라 마지막 값 기준으로 넘긴다. 정렬 키 끝에 id를 붙인다.
4. 목록에는 건수 제한을 반드시 둔다(휴지통, 이력 포함).
5. 합계와 집계는 DB가 계산한다. 행을 가져와 자바에서 더하지 않는다.
6. 새 조회 조건을 추가하면 PR에 실행 계획을 붙이고 dba를 부른다.
7. 화면 하나가 여는 API 호출 수를 적는다. 같은 요청을 두 번 보내지 않는다.
8. 초기 경로 JS는 150KB(gzip) 안에서 쓴다. 통계 그래프처럼 무거운 것은 그 화면에서만 불러온다.
9. 그림과 목록 자리는 크기를 미리 잡아 화면이 밀리지 않게 한다.
10. 캐시는 잰 수치와 함께 제안한다.
