## 5. 구현 방식 (frontend와 합의)

- `web/src/styles/tokens.css` 하나에 CSS 변수로 토큰을 두고, 컴포넌트마다 CSS Modules를 쓴다. CSS 프레임워크와 UI 라이브러리는 쓰지 않는다.
- 변수 이름은 설계서 토큰 이름 앞에 `--`를 붙인다(`--color-bg`, `--text-body`). 크기는 rem으로 쓴다(16px = 1rem).
- 색, 글자 크기, 간격, 모서리, 그림자 값은 `tokens.css` 밖에서 직접 쓰지 않는다. 인라인 `style`도 쓰지 않는다. 예외는 막대 폭처럼 계산한 값을 CSS 변수로 넘기는 것 하나다.
- 아이콘은 Phosphor Regular의 SVG를 레포에 넣고 `Icon` 컴포넌트 하나로 쓴다. 크기는 20px과 24px만, 색은 `currentColor`다.
- 글꼴은 Pretendard Variable woff2를 직접 호스팅한다.
- 컴포넌트를 만들 때 상태(기본, 눌림, 키보드 초점, 비활성, 처리 중)를 같이 만든다. 화면에서 컴포넌트 모양을 덮어쓰지 않는다.
- 화면 PR은 올리기 전에 designer 검토를 받는다. frontend가 보낼 것은 다음과 같다.

| 보낼 것 | 내용 |
|---------|------|
| 실행 방법 | worktree 경로, 브랜치, 명령, 주소 |
| 스크린샷 | 390x844와 1280x800, 밝은 화면과 어두운 화면. 상태별: 기본, 비어 있음, 불러오는 중, 오류, 연결 없음, 보기 전용, 긴 값, 글자 200% |
| 새로 넣은 값 | 새로 넣은 값과 그 이유 |
| 단계 수 | 자주 하는 일의 단계 수 |

## 6. 기준을 바꾸는 절차

1. 새 색, 새 글자 크기, 새 간격 값, 새 컴포넌트 변형이 필요하면 이유를 적어 owner에게 묻는다.
2. 승인되면 이 폴더에 먼저 추가하고, 그다음에 코드에서 쓴다.
3. 기존 값을 바꿀 때는 모든 화면에 같이 적용할 방법을 함께 낸다. 옛 값과 새 값이 한 화면에 섞이지 않게 한다.
4. 설계서(`docs/planning`)와 다른 값이 필요하면 설계서를 고치지 않고 owner에게 질문한다(레포 CLAUDE.md).

## 7. 검토 방법

| 항목 | 방법 |
|------|------|
| 범위 | 한 번에 과업 하나, 화면 묶음 하나, 기기 하나 |
| 머리 | 화면의 목적과 사용자 과업을 한 줄로 먼저 적는다 |
| 지적 | 지적마다 NN/g 사용성 원칙 번호(아래 표)와 심각도(아래 표)를 붙이고, 빈도, 영향, 반복 여부를 근거로 쓴다 |
| 측정과 판단 | 측정(스크린샷, 대비 수치, 단계 수, 값 개수)과 판단을 나눠 적는다. 각 내용이 확인, 추정, 미확인 중 무엇인지 구분한다 |
| 객관 점검 | `npx impeccable detect`를 돌려 결과를 함께 적는다 |

- 검토 한 번에 적어도 세 가지를 같이 쓴다: `npx impeccable detect` 결과(390x844와 1280x800 두 폭), 디자인 스킬(impeccable, frontend-design, design-taste-frontend) 중 두 개 이상의 점검, 실제로 띄워 찍은 스크린샷과 측정값.
- 검토 보고에 "어느 도구가 무엇을 찾았는지" 표를 넣는다. 도구끼리 의견이 다르면 더 덜어내는 쪽을 고르고, 두 개 이상이 같이 짚은 것은 심각도를 한 단계 올린다.
- 스킬이 새 색, 새 글꼴, 새 레이아웃 방향, 움직임, 장식을 권하면 따르지 않고 "스킬 제안(채택 안 함)"으로 적는다. 화면을 만드는 쪽도 같다: 스킬이 자동으로 켜져도 토큰 밖의 값을 만들지 않는다.

## 8. 넣지 않는 것

AI가 만든 티가 나는 다음 요소는 넣지 않는다. 검토에서 발견하면 지적한다.

- 뜻 없는 그라데이션
- 보라색 계열 테마
- 빛나는 효과
- 이모지 아이콘
- 장식용 일러스트와 마스코트
- 과한 그림자와 둥근 모서리
- 카드 안의 카드
- 아무 데나 붙는 애니메이션
- 뜻 없는 배지와 태그
- 영어 마케팅 문구
- 가운데 정렬한 큰 소개 영역
