## 이 문서를 읽는 법

이 문서는 누가 정한 내용인지를 항목마다 표시한다. 절 제목에 표시가 붙어 있으면 그 절 전체에 적용되고, 항목에 따로 표시가 있으면 항목의 표시가 우선한다.

| 표시 | 뜻 |
|---|---|
| [사용자] | 사용자가 직접 정했다. |
| [사용자 승인] | 설계자가 제안했고 사용자가 승인했다. |
| [설계자] | 설계자가 정했다. 사용자는 아직 확인하지 않았다. |
| [설계자·요약 설명] | 설계자가 정했고 사용자에게 요약해 설명했다. 사용자 확인은 받지 않은 상태로 본다. |
| [사실] | 조사나 환경 확인으로 얻은 사실이다. 결정이 아니다. |
| [미결] | 아직 논의하지 않았고 사용자가 정해야 한다. |

조사 근거를 인용할 때는 [R1], [R2]와 해당 부록을 함께 적는다. 원문과 출처 링크는 두 기록에 있다.

## 1. 의도와 배경

### 1.1 의도 [사용자]

- 맥북과 아이폰 어느 쪽에서 입력해도 서로 보이는 가계부를 만든다.
- 혼자도 쓰고, 사람을 초대해 함께도 쓴다.
- 대상 플랫폼은 웹, macOS, iOS다. 안드로이드는 고려하지 않는다.
- 공개 출시를 목표로 한다. 지금 넣지 않는 기능은 출시 후 하나씩 추가한다.

### 1.2 배경

[사실] 사용자는 Java/Spring 백엔드와 DevOps 개발자다. Swift 경험은 확인되지 않았다.

[사실] 기존 앱 조사([R1] 부록 B)에서 확인한 상황은 다음과 같다.

- 아이폰과 PC/Mac을 함께 쓸 수 있는 국내 앱은 적고, 그중 편한가계부는 실시간 동기화를 유료 구독에서만 제공한다.
- 국내 앱에는 여러 사람이 같은 장부를 쓰는 기능이 사실상 없다. 뱅크샐러드의 '우리집돈관리'는 2025-07-31에 종료되었고, 남은 방식은 편한가계부와 후잉의 계정을 같이 쓰는 방식 정도다. 계정을 같이 쓰면 "배우자 내꺼 구분이 자동으로 안돼서" 불편하다는 후기가 있다.
- 여행이나 데이트처럼 기간이 있는 지출을 따로 보려는 사람들은 날짜 필터로 모아 태그를 달거나, 여행 통장을 따로 두거나, "여행비 빼면 이번 달 얼마"를 손으로 계산하고 있다([R2] 부록 B-1).

## 2. 목표 / 하지 않는 것 / 피해야 할 실패

### 2.1 목표 [사용자]

1. **기기 간 동일 데이터.** 어느 기기에서 입력해도 모든 기기에서 같은 데이터가 보인다.
2. **초대 기반 공유.** 장부를 여러 개 두는 방식(모임, 데이트)과 장부 하나를 통째로 공유하는 방식(부부 살림)을 둘 다 지원한다.
3. **이벤트.** 기간으로 지출을 묶는다.

### 2.2 하지 않는 것 [사용자 승인]

아래 다섯 가지는 이번 범위에서 하지 않는다. 모두 출시 후 후보다.

- 은행·카드 직접 연동
- 안드로이드
- 정산 계산(누가 누구에게 얼마를 줘야 하는지)
- 영수증 인식
- 다중 통화

범위 밖이지만 데이터 모델에는 통화 코드 컬럼을 두고(6.3), 자동 입력 입구는 출처에 무관하게 만든다(7.3).

### 2.3 피해야 할 실패 [설계자, 조사 근거]

**(a) 표시 없이 데이터가 어긋나거나 사라지는 것.** 해외 앱 조사에서 사용자를 가장 화나게 한 것은 동기화 방식과 관계없이 아무 표시 없이 일어나는 불일치였다. Monarch 사용자는 "missing… worse… since you can't see it's missing"라고 썼고, Banktivity에서는 "no error or warning" 상태로 동기화가 실패한 사례가 있었다([R1] 부록 C 요약). 이 설계에서 관련된 부분은 낡은 쓰기 거부와 소프트 삭제(6.3), 변경 이력(7.5), 보내지 않은 입력 건수와 마지막 동기화 시각 표시(7.4)다.

**(b) 자동 처리가 사용자가 직접 고친 값을 덮어쓰는 것.** 여기서 자동 처리는 문자 파서, 자동 분류, 이벤트 자동 묶기를 말한다. 조사에서는 사용자가 수동으로 정한 카테고리를 자동 분류가 몇 달 뒤 다시 바꾼다는 Copilot과 Monarch 사용자 글이 확인되었다([R1] 부록 C 요약). 이 설계에서 자동 분류는 따로 만드는 기능이 아니다. 한 줄 입력이 같은 가맹점의 지난 카테고리를 기본값으로 제안하는 것만 있으며, 이 제안은 거래를 만들 때만 적용되고 저장된 거래를 바꾸지 않는다. 이 설계에서 관련된 부분은 이벤트 소속 방식(event_mode, 7.1)과 "자동 입력은 사용자가 입력하거나 고친 값을 바꾸지 않는다"는 규칙(7.3)이다.

**(c) 입력이 번거로워 쓰지 않게 되는 것.** 입력의 번거로움은 국내 앱의 이탈 1순위 이유다. 국내 앱 리뷰에서 이탈 이유로 가장 직접적으로 언급되었고, "예전에 사용하다가 입력이 귀찮아서 안쓰게 됐어요" 같은 후기가 있다. 복식부기 웹 가계부인 후잉에는 "복식부기를 몰라서....매번 시도 실패"라는 후기가 있다([R1] 부록 A, 부록 B). 이 설계에서 관련된 부분은 단식처럼 단순한 입력 화면(6.2), 한 줄 입력(8장 1단계), 휴대폰 폭의 빠른 입력 화면(5.3), 자동 입력 입구(7.3)다.

**(d) 이체가 수입·지출 합계를 부풀리는 것.** 두 은행 내역을 각각 가져오면 이체 한쪽은 지출, 다른 쪽은 수입으로 잡혀 합계가 부풀려진다(Firefly III 이슈, [R1] 부록 C). 토스에서는 주식 거래가 전부 지출로 잡혀 "3천 7백만 원 소비"로 보였다는 후기가 있다([R1] 부록 B). 이 설계에서 관련된 부분은 카테고리가 있는 라인만 합산하는 규칙과 카드대금을 이체로 다루는 규칙(6.2)이다.

## 3. 제약 [사실]

### 3.1 자동 입력 경로

- 마이데이터는 금융위원회 허가(최소 자본금 5억원 등)가 필요하고, 오픈뱅킹은 금융결제원과 이용계약을 맺고 심사를 거친 핀테크 기업 등만 쓸 수 있다. 그래서 개인 개발자는 쓸 수 없다. 반면 "개인신용정보를 저장·접근하지 못하는 단순 가계부 어플 개발"은 허가가 필요 없다고 금융위 자료에 명시되어 있다([R1] 부록 D-1).
- Apple FinanceKit은 미국과 영국만 지원하고 한국은 지원하지 않는다([R1] 부록 D-2).
- iOS 앱은 문자를 직접 읽을 수 없다. 서드파티 앱은 메시지 데이터베이스에 접근할 수 없다([R1] 부록 D-3).
- 그래서 현실적인 자동 입력 경로는 두 가지다. 하나는 단축어의 '메시지' 자동화가 문자 본문을 서버로 POST하는 방법이고(국내 앱 '함쓰'가 이 방식을 쓴다), 다른 하나는 카드사 홈페이지에서 받은 엑셀을 가져오는 방법이다. 카드사 엑셀 제공 여부는 2차 출처로만 확인되었고, 카드사마다 열 구성이 다를 것으로 추정된다([R1] 부록 D-3, D-4).
- 단축어 자동화가 확인 없이 실행되는지는 iOS 버전과 설정에 따라 보고가 엇갈린다. 실기기 검증이 필요하다(10.2).

### 3.2 개발 환경

- 이 Mac에는 Xcode와 코드 서명 인증서가 없다. 2026-11-04에 `xcodebuild -version`은 실패했고 코드 서명 인증서는 0개였다([R1] 작업 보고). Command Line Tools만으로는 iOS 앱을 빌드할 수 없다([R1] 부록 D-8).
- 따라서 네이티브 단계(8장 4단계) 전에 Xcode 설치와 Apple Developer Program 가입(연 $99, 2차 출처)이 필요하다. 무료 개인 계정은 프로비저닝 프로파일이 7일 뒤 만료된다([R1] 부록 D-5).

### 3.3 iPhone 홈 화면 웹앱

- 홈 화면에 추가한 웹앱은 Safari의 7일 데이터 삭제 정책에서 면제된다.
- Background Sync는 지원하지 않는다(2차 출처).
- 저장 공간이 부족하면 기기에 저장한 로컬 데이터가 삭제될 수 있다. 저장은 기본적으로 best-effort이고, 조사 출처도 서버 백업을 권한다.

출처는 [R1] 부록 D-9다. 이 설계에서 관련된 부분은 오프라인 입력(7.4)과 일찍 검증할 위험(10.1)이다.

## 4. 검토한 접근과 선택

| 접근 | 내용 | 결과 |
|---|---|---|
| 1 | 웹앱 하나만 만든다 | 선택하지 않음 |
| 2 | 처음부터 웹과 SwiftUI 네이티브 앱을 함께 만든다 | 선택하지 않음. 다만 최종 형태는 이것과 같아진다 |
| 3 | 웹앱을 먼저 만들고 네이티브 앱은 나중에 추가한다 | **선택** |
| iCloud 전용 | SwiftUI와 iCloud(SwiftData/CloudKit)만으로 만든다 | 탈락 |
| 로컬 우선 동기화 엔진 | 기기별 로컬 DB와 동기화 서버로 로그를 병합한다 | 조사 단계에서 탈락 |
| 파일 공유 | 파일 하나를 iCloud Drive나 Dropbox로 공유한다 | 조사 단계에서 탈락 |

### 4.1 선택과 이유 [사용자]

사용자는 3번을 골랐다. 웹앱으로 시작해 나중에 네이티브 앱을 더하므로, 최종 형태는 2번(웹과 네이티브 앱이 같은 서버를 쓰는 형태)이 된다. 조사에서도 SwiftUI 앱과 직접 운영 서버를 함께 쓰는 구조를 "첫 버전이 아니라 출시 단계 진화형"으로 평가했다([R1] 부록 A).

3번을 고른 이유는 네 가지다. 첫째, 화면 한 벌로 웹, macOS, iOS 세 플랫폼에서 바로 쓸 수 있다. 둘째, 초대받은 사람이 앱을 설치하지 않고 링크로 들어올 수 있다. 셋째, 핵심 기능에는 네이티브 기능이 필요하지 않다. 넷째, 서버를 API로 만들어 두면 네이티브 앱을 추가할 때 버리는 것이 없다.

### 4.2 탈락한 방식 [설계자]

iCloud 전용 방식은 웹에서 쓸 수 없고 초대 기능을 만들기 어려워 탈락했다. 조사에서도 SwiftData와 CloudKit 조합은 공유(CKShare)를 지원하지 않는다는 Apple 답변이 확인되었다([R1] 부록 D-6).

로컬 우선 동기화 엔진은 동기화 정합성 자체가 큰 프로젝트가 되기 때문에 탈락했다. 이 방식을 쓰는 Actual Budget에서는 다른 기기의 변경이 되돌아가거나 한 달 동안 동기화 오류가 이어진 사례가 있었다. 파일 공유 방식은 기기마다 다른 버전이 생기거나 파일이 손상되고 복구 수단이 없어서 탈락했다([R1] 부록 A, 부록 C 요약).

## 5. 구조 [설계자]

```
  [웹앱 (React + TypeScript, PWA)]     [iPhone·Mac 앱 (SwiftUI, 4단계)]     [단축어 자동화 (3단계)]
     휴대폰 폭: 빠른 입력·확인              같은 API 사용                       문자 본문을 POST
     넓은 화면: 표 형태 정리
                 │                                │                                │
                 └───────────────── REST API (JSON, /api/v1) ────────────────────────┘
                                                  │
                                  Spring Boot 3 / Java 21 서버
                                                  │
                                  PostgreSQL (기준 데이터, Flyway, 매일 백업)
```

### 5.1 기준 데이터와 API

- 기준 데이터는 서버의 PostgreSQL 하나다.
- 모든 클라이언트는 같은 REST API(JSON, `/api/v1` 접두)를 쓴다.
- 웹 전용 지름길 API는 만들지 않는다. 나중에 네이티브 앱이 같은 API를 쓸 것이기 때문이다.
- [사용자, 2026-11-23] API 명세는 OpenAPI로 만든다. 운영 환경에서는 명세 문서 화면을 끈다.

### 5.2 서버

- Spring Boot 3, Java 21, PostgreSQL을 쓴다. 스키마 마이그레이션은 Flyway로 한다.
- Docker Compose로 배포할 수 있어야 한다.
- [사용자, 2026-11-23] 서버는 Oracle Cloud의 국내 리전(서울 또는 춘천)에 둔다. 계정의 홈 리전은 사용자가 확인 중이며, 홈 리전이 해외여서 무료 자원을 국내에 만들 수 없으면 다시 정한다(9장 6번).

### 5.3 클라이언트

- React와 TypeScript로 만든 단일 페이지 앱이다. iPhone 홈 화면과 Mac Dock에 설치할 수 있는 PWA로 제공한다.
- 화면은 폭에 따라 역할을 나눈다. 휴대폰 폭에서는 빠른 입력과 확인에 맞추고, 넓은 화면에서는 표 형태의 정리 작업(검색, 일괄 수정, 가져오기)에 맞춘다. 조사한 해외 앱 공식 문서에서도 "iPhone은 입력과 확인, 큰 화면은 정리"라는 흐름이 반복해서 나왔다([R1] 부록 C 요약).

### 5.4 로그인

- 이메일과 비밀번호로 로그인한다.
- 인증 방식은 브라우저와 이후의 네이티브 앱에서 모두 동작해야 한다.
- [사용자, 2026-11-23] 로그인 유지는 JWT를 쓴다. access token은 15분 동안 유효하다. refresh token은 서버에 저장하고 HttpOnly 쿠키로 전달한다. 로그인 상태는 마지막으로 서버와 통신한 때부터 30일 동안 유지되고, 계속 쓰더라도 처음 로그인한 때부터 180일이 지나면 다시 로그인해야 한다(기능정의서 P-106).
- [사용자, 2026-11-23] 비밀번호는 Argon2id로 저장한다. 비밀번호 길이 규칙(8자 이상 72자 이하, 기능정의서 P-101)은 그대로다.
- [사용자, 2026-11-23] 비밀번호 조합 규칙(영문과 숫자 필수, 기능정의서 P-101)은 지금 그대로 두고 출시 준비 때 다시 본다. NIST SP 800-63B-4는 조합을 강제하지 않고 길이 위주로 정하기를 권한다.
- [사용자, 2026-11-23] 로그인과 가입 요청 횟수 제한은 기획대로 출시 준비 단계에 넣는다(기능정의서 P-104, P-105). 바뀐 것은 없다.

## 6. 데이터 모델 [설계자·요약 설명]

### 6.1 전체 관계

```
user ── ledger_member (OWNER | MEMBER | VIEWER) ── ledger (시간대)
                                                     ├── account (은행 | 카드 | 현금)
                                                     ├── category (수입 | 지출, 분류 > 소분류)
                                                     ├── event (starts_at ~ ends_at)
                                                     └── transaction (거래 헤더)
                                                           ├── transaction_line (account, category, amount)
                                                           └── change_log (생성·수정·삭제 전후 값)
```

거래, 계좌, 카테고리, 이벤트는 모두 장부에 속한다. 사용자는 장부 구성원(ledger_member)을 통해 장부에 접근한다. 구성원 역할은 OWNER, MEMBER, VIEWER(보기 전용) 세 가지다(2026-11-18 기능정의서 P-301로 확정).

### 6.2 엔터티

**user.** 로그인하는 계정이다. 이메일과 비밀번호로 로그인한다(5.4).

**ledger(장부).**
- 가입하면 개인 장부 1개가 자동으로 생긴다.
- 사용자는 장부를 여러 개 가질 수 있다.
- 장부마다 시간대를 가진다. 기본값은 Asia/Seoul이다.
- [설계자] 거래의 occurred_on·occurred_time과 이벤트의 starts_at·ends_at은 사용자가 입력한 값을 시간대 변환 없이 그대로 저장하고 비교한다. 장부 시간대는 서버가 "오늘"을 정해야 하는 일(휴지통 30일 계산, 반복 거래와 이벤트 회차 생성)에만 쓴다(2026-11-18 기능정의서 P-202로 확정).

**ledger_member(장부 구성원).**
- 장부, 사용자, 역할(OWNER, MEMBER, VIEWER 중 하나)을 가진다(2026-11-18 기능정의서 P-301로 확정).
- 혼자 쓰는 장부도 구성원이 1명인 같은 구조다. 1단계부터 이 구조로 저장한다. [R1] 부록 A는 단일 사용자 스키마를 나중에 여러 사용자 구조로 바꾸는 작업을 가장 비싼 작업으로 보았다.

**account(계좌).**
- 장부에 속한다. 종류는 은행, 카드, 현금이다.
- [설계자] 초기 잔액과 그 기준일을 가진다.
- [설계자] 잔액은 초기 잔액에 기준일 이후(기준일 포함) 거래 라인의 합을 더한 값이다. 기준일 이전 날짜의 거래는 통계에는 들어가지만 잔액에는 반영하지 않는다. 계좌 화면에 기준일을 보여준다.
- 카드는 부채 계좌로 본다. 카드로 결제하면 카드 계좌의 지출이 되고, 카드대금 납부는 은행 계좌에서 카드 계좌로의 이체가 된다. 이렇게 하면 결제와 대금 납부가 이중으로 집계되지 않는다([R1] 부록 A).

**category(카테고리).**
- 장부에 속한다. 수입과 지출을 구분한다.
- 2단계(분류, 소분류)로 구성된다.
- [설계자] 장부마다 수입과 지출에 각각 "미분류" 기본 카테고리가 있고, 이 카테고리는 지울 수 없다. 카테고리를 고르지 않은 지출과 수입은 미분류로 저장되어 합계에 들어간다.

**transaction(거래 헤더).**

| 필드 | 뜻 |
|---|---|
| id | 클라이언트가 만든 UUID v7 |
| ledger_id | 거래가 속한 장부 |
| 종류 | 지출, 수입, 이체 |
| occurred_on | 사용자가 고른 날짜. 집계 기준이 된다 |
| occurred_time | 시각. 없을 수 있다 |
| 가맹점/내용 | 어디에 무엇을 썼는지 |
| 메모 | 자유 메모 |
| status | PENDING, POSTED, CANCELED |
| reviewed | 자동 입력 초안인지 여부. false이면 "미확인"이다(7.3) |
| source | MANUAL, SMS, IMPORT, RECURRING |
| raw_text | 자동 입력의 원문. 엑셀 가져오기 행은 그 행의 원래 내용이다. [사용자, 2026-11-23] 문자로 들어온 거래는 원문을 저장하지 않는다(7.3) |
| source_key | 자동 입력 중복 방지 키(7.3) |
| created_by | 거래를 적은 사람 |
| paid_by | 결제한 구성원. [설계자] 기본값은 입력한 사람이다. 수입에서는 받은 사람을 뜻한다. 이체에는 paid_by가 없다 |
| event_id | 소속 이벤트 |
| event_mode | AUTO, INCLUDED, EXCLUDED(7.1) |
| installment_months, 청구 시작월 | 할부 개월 수와 청구가 시작되는 달 |
| refund_of | 환불일 때 원 거래를 가리킨다 |
| version | 낡은 쓰기를 거부하기 위한 버전 |
| deleted_at | 소프트 삭제 시각 |

**transaction_line(분개 라인).**

| 필드 | 뜻 |
|---|---|
| 거래 id | 어느 거래의 라인인지 |
| account_id | 돈이 움직인 계좌 |
| category_id | 카테고리. 이체 라인에는 없다 |
| amount | 부호 있는 정수 원. [설계자] 계좌 잔액을 늘리면 양수, 줄이면 음수다 |

거래 헤더와 분개 라인의 관계는 다음과 같다.

- 지출과 수입은 라인 1개다. 한 거래를 여러 카테고리로 나누는 분할 거래는 라인이 여러 개다. 이체는 라인 2개다.
- 입력 화면은 단식 가계부처럼 단순하게 두고, 저장만 이 구조로 한다. 조사에서 완전한 복식 입력은 입력 부담을 키운다고 보았다([R1] 부록 A).
- 통계는 카테고리가 있는 라인만 합산한다. 이체 라인에는 카테고리가 없으므로 이체는 수입·지출 합계에 들어가지 않는다.
- [설계자] 지출과 수입 라인에는 항상 카테고리가 있으므로(미분류 포함), 위 규칙은 "이체 라인을 뺀 모든 라인을 합산한다"는 뜻이다.
- [설계자] 지출 라인은 계좌 잔액을 줄이므로 음수다. 카테고리 통계에서는 이 부호를 뒤집어 지출액으로 센다.
- 거래 헤더를 지우면 라인이 함께 지워진다. 그래서 이체의 한쪽만 남는 일이 없다.

**event(이벤트).**
- ledger_id, 이름, starts_at, ends_at, exclude_recurring을 가진다.
- starts_at과 ends_at은 시·분까지 저장한다.
- exclude_recurring의 기본값은 true다.
- 동작 규칙은 7.1에 있다.

**recurring_rule(반복·고정지출), budget(월 예산).** 3단계에서 추가한다.

**change_log(변경 이력).**
- 거래의 생성, 수정, 승인취소와 되돌리기, 삭제, 복원, 확인, 합치기, 카테고리 삭제에 따른 이동, 가져오기 되돌리기 때 전후 값을 기록한다(2026-11-18 기능정의서 P-216으로 확정). 추가만 하고 고치거나 지우지 않는다.
- 누가, 언제, 어느 기기에서 바꿨는지를 남긴다.

### 6.3 금액과 거래 상태 규칙

- **금액.** 정수 원(long)으로 저장한다. 부동소수점은 쓰지 않는다. 통화 코드 컬럼은 두되 KRW만 쓴다.
- **환불.** 원 거래를 참조(refund_of)하는 지출 거래로 기록하고, 원 거래와 같은 카테고리를 쓴다. 수입으로 기록하지 않는다. [설계자] 환불 라인은 계좌 잔액을 늘리므로 양수이고, 지출 카테고리를 가지므로 그 카테고리의 지출을 줄인다. [설계자] 원 거래 연결(refund_of)은 3단계에 넣는다(8장). 1단계에서 환불은 지출 카테고리로 양수 금액을 입력하는 방식으로만 할 수 있다.
- **승인취소.** 거래를 삭제하지 않고 status를 CANCELED로 바꾼다. 취소된 거래는 목록에는 보이고 통계에서는 빠진다.
- **할부.** 거래 1건(총액)에 할부 개월 수와 청구 시작월을 붙인다. 월별 금액 행을 미리 만들지 않고, 월별 금액은 계산해서 보여준다. [설계자] 기본 보기는 발생 기준이다. 월별 통계와 카드 잔액에는 구매한 달에 총액이 들어간다. 청구 기준 보기로 바꾸면 월별 청구액으로 나눠 보여준다.
- **삭제.** 소프트 삭제(deleted_at)로 한다.
- **수정.** version으로 낡은 쓰기를 거부하고 사용자에게 알린다. 조용히 덮어쓰지 않는다.

[설계자, 2026-11-18] 메모: 구성원 역할에 VIEWER가 추가되고 열람 링크, 초대, 가져오기 기록, 이벤트 반복 규칙을 담을 구조가 필요하다. 테이블 설계는 해당 단계의 구현 계획에서 한다.

## 7. 핵심 동작 규칙

### 7.1 이벤트 묶기

#### 사용자가 정한 것 [사용자]

- 데이트나 여행처럼 기간이 있는 지출을 하나로 묶는다.
  - 예: 11-19 10:00~20:00 데이트
  - 예: 11-19 10:00~11-25 16:00 여행
- 그 기간의 지출은 자동으로 묶인다.
- 자동결제나 미리 한 온라인 주문 같은 예외는 뺄 수 있다.
- 기간이 겹치는 이벤트는 필요 없다. 여행 중의 데이트는 여행으로 묶는다.

#### 설계 규칙 [설계자]

**소속과 겹침.** 이벤트는 장부에 속한다. 같은 장부 안에서는 기간이 겹치는 이벤트를 만들 수 없다. 겹침은 일시(시·분)로 판정한다. 그래서 같은 날이라도 시간이 겹치지 않는 이벤트 두 개는 만들 수 있다. 다른 장부의 이벤트와는 겹쳐도 된다. 예를 들어 개인 장부의 여행과 데이트 장부의 데이트는 기간이 겹쳐도 된다.

**카테고리와의 관계.** 이벤트는 카테고리와 별개의 축이다. 지출 하나는 "식비"이면서 동시에 "제주 여행"에 속할 수 있다.

**소속 방식(event_mode).**

| 값 | 뜻 | 자동 재계산이 바꾸는가 |
|---|---|---|
| AUTO | 기간 규칙에 따라 자동으로 소속이 정해진다 | 바꾼다 |
| INCLUDED | 사용자가 직접 넣었다. 기간 밖의 항공권·숙소, 귀국 후 청구 등 | 절대 바꾸지 않는다 |
| EXCLUDED | 사용자가 직접 뺐다 | 절대 바꾸지 않는다 |

EXCLUDED는 "이 거래는 어떤 이벤트에도 자동으로 묶지 않는다"는 뜻이다. 사용자가 다른 이벤트에 직접 넣을 수는 있고, 그러면 INCLUDED가 된다.

**이벤트 삭제.** 이벤트를 삭제하면 그 이벤트의 거래는 이벤트 없음이 되고, INCLUDED였던 거래는 AUTO로 돌아간다. EXCLUDED 거래는 그대로 둔다.

**자동 소속 조건.** 거래는 다음 조건을 모두 만족할 때 이벤트에 자동으로 소속된다.

1. 지출 거래다. 이체와 수입은 자동 소속 대상이 아니다.
2. 시각이 있으면 그 시각이 starts_at~ends_at 안에 있다. 시각이 없으면 날짜가 이벤트의 날짜 범위 안에 있다. 기간은 시작을 포함하고 종료를 포함하지 않는다(starts_at 이상, ends_at 미만). 비교는 입력한 날짜·시각 값 그대로 한다(6.2 ledger)(2026-11-18 기능정의서 P-202, P-405로 확정).
3. exclude_recurring이 켜져 있으면 source가 RECURRING인 거래는 제외한다.

시각이 없는 거래의 날짜에 이벤트가 둘 이상 걸리면 자동으로 묶지 않고 이벤트 없음으로 둔다. 사용자가 이벤트를 직접 고르며, 고른 거래는 INCLUDED가 된다.

**재계산.** 이벤트를 나중에 만들어도 이미 있는 거래가 묶인다. 이벤트 기간, exclude_recurring 설정, 거래 날짜·시각·유형이 바뀌면 AUTO 거래만 다시 계산한다(2026-11-18 기능정의서 P-406으로 확정). 재계산을 저장 시점에 할지 조회 시점에 할지는 구현자가 정하되, 결과는 이 규칙과 같아야 한다(11장).

**이벤트 화면의 숫자.**
- 총액
- 카테고리별 금액
- 하루 평균. 기간 밖에서 넣은 거래는 평균에서 제외한다. 일수는 이벤트가 걸친 달력 날짜 수(최소 1일)다. 예를 들어 10시간 데이트는 1일, 11-19 10:00~11-25 16:00 여행은 7일이다.
- 통계 화면에는 "이벤트 제외" 보기를 두어 평소 지출을 보여준다.

이벤트 숫자에서 CANCELED 거래는 빼고 미확인 거래는 넣는다. 전체 합계 규칙과 같다. 환불은 원 거래의 이벤트를 따른다.

#### 규칙 적용 예

아래는 "데이트" 이벤트(11-19 10:00~20:00, exclude_recurring 켜짐)에 위 규칙을 그대로 적용한 결과다.

| 거래 | 결과 | 이유 |
|---|---|---|
| 11-19 13:10 점심(지출) | 묶임(AUTO) | 시각이 기간 안에 있다 |
| 11-19 21:30 지출 | 묶이지 않음 | 시각이 기간 밖에 있다 |
| 11-19 카페(지출, 시각 없음) | 묶임(AUTO) | 시각이 없고 날짜가 범위 안에 있다 |
| 11-19 15:00 구독료(지출, source=RECURRING) | 묶이지 않음 | exclude_recurring이 켜져 있다 |
| 11-19 14:00 이체 | 대상 아님 | 이체는 자동 소속 대상이 아니다 |
| 11-12 영화 예매(사용자가 넣음) | 묶임(INCLUDED) | 사용자가 직접 넣었다. 기간 밖이므로 하루 평균에서는 빠진다 |
| 11-19 16:00 온라인 주문(사용자가 뺌) | 빠짐(EXCLUDED) | 사용자가 직접 뺐다. 재계산이 바꾸지 않는다 |

#### 근거 [사실]

- 조사에서 Lode라는 앱이 여행에 한정해 유사한 기능을 제공하는 것이 확인되었다. 다녀와서 만든 여행도 이미 있는 거래를 가져오고, 정기 청구 제외가 기본으로 켜져 있고, 기간 밖 지출을 넣을 수 있고, 여행끼리 날짜가 겹칠 수 없다. 사용자 반응은 확인되지 않았다([R2] 부록 B).
- 조사한 국내 가계부 앱에서는 수동 태그 방식만 확인되었다([R2] 부록 A-3).
- 기간 묶기에서 실제로 문제가 된 사례로는 기간 전에 결제한 항공권·숙소, 기간 안이지만 무관한 지출(선물, 장보기), 귀국 후 청구(호텔 추가 청구, 기내면세점)가 확인되었다([R2] 부록 B-3).
- 사람들이 묶음에서 보고 싶어 한 숫자는 총액이 가장 많았고, 그 밖에 카테고리별 금액, 1일 평균, 여행을 뺀 평소 지출 등이 있었다. 출발 전에 산 항공권이 하루 평균을 바꾼다는 불만도 있었다([R2] 부록 B 요약).

### 7.2 공유

**[사용자]** 장부 여러 개(모임, 데이트)와 장부 하나 통째 공유(부부 살림)를 모두 지원한다.

**[설계자]**

- **두 방식은 같은 구조다.** 통째 공유는 내 개인 장부에 상대를 초대하는 것이고, 모임이나 데이트는 새 장부를 만들어 초대하는 것이다.
- **지출 하나는 장부 하나에만 속한다.** 장부 사이에 거래를 복사하지 않는다. 대신 "내 전체 지출" 화면이 내가 속한 모든 장부에서 paid_by가 나인 거래를 합쳐 보여준다.
- **초대.** 링크 또는 코드로 초대하며, 초대에는 만료가 있다. 초대받은 사람도 계정이 필요하다. [사용자, 2026-11-18] 단 열람 링크는 예외로, 링크를 가진 사람은 계정 없이 읽기 전용으로 본다.
- **권한.** OWNER는 구성원을 내보낼 수 있다. MEMBER는 그 장부의 거래를 추가, 수정, 삭제할 수 있다. 누가 바꿨는지는 change_log에 남는다. MEMBER는 계좌, 카테고리, 이벤트도 만들고 고칠 수 있다. 구성원 관리, 장부 이름 변경, 장부 삭제는 OWNER만 한다.

  [사용자, 2026-11-18] 보기 전용 권한을 추가해 세 가지가 되었다. 초대, 열람 링크, 소유권 넘기기를 포함한 세부 규칙은 [docs/planning/03-feature-spec.md](../../planning/03-feature-spec.md) 의 정책을 따른다.
- **구성원이 나갈 때.** 그 사람이 적은 거래는 장부에 남는다.
- **결제한 사람별 합계.** 공유 장부에서는 결제한 사람(paid_by)별 합계를 보여준다. 정산 계산은 하지 않는다.

### 7.3 자동 입력 입구 [설계자]

문자(단축어 자동화)나 카드사 엑셀 가져오기처럼 자동으로 들어오는 거래는 모두 이 입구를 지난다. 두 경로 모두 3단계에서 만든다.

- **미확인 상태.** 자동으로 들어온 거래는 reviewed=false("미확인")로 저장된다. 미확인 거래도 합계에는 포함되며, 검토 목록에 모인다. 사용자가 확인하면 reviewed=true가 된다. 단 하나의 예외는 계좌를 정하지 못한 문자 입력이다(아래 "문자 입력의 장부와 계좌").
- **사용자가 정한 값은 바꾸지 않는다.** 자동 입력은 사용자가 입력하거나 고친 값(금액, 카테고리, 메모, 이벤트 소속 등)을 바꾸지 않는다. 예외로 status 전환만 허용하며, 그 대상은 자동 입력으로 생긴 거래뿐이다.
- **생성 시 status.** 문자로 들어온 승인은 PENDING으로 생성한다. 수기 입력과 엑셀 가져오기 행은 POSTED로 생성한다.
- **승인취소 문자.** 같은 계좌, 금액, 가맹점의 자동 입력 거래와 맞으면 그 거래를 CANCELED로 바꾼다. 맞는 거래가 없으면 검토 목록에 미확인 항목으로 남긴다.
- **문자와 엑셀이 같은 결제일 때.** 문자로 들어온 PENDING 거래와 엑셀 행이 같은 결제로 보이면(같은 계좌, 같은 금액, 날짜 하루 이내) 자동으로 합치지 않고 검토 목록에서 합치기를 제안한다. 사용자가 합치면 POSTED가 된다.
- **중복 방지.**
  - 자동 입력은 source_key가 장부 안에서 유일해야 한다. source_key는 계좌, 금액, 분 단위 시각, 정규화한 가맹점으로 만든 해시다. 발신자는 넣지 않는다.
  - 수기 입력은 같은 장부에 같은 날짜, 같은 금액, 같은 가맹점의 거래가 있으면 경고만 한다(2026-11-18 기능정의서 P-218로 확정).
- **문자 입력의 장부와 계좌.**
  - 문자 자동 입력은 사용자별 전송 주소(토큰 포함)로 들어온다. 사용자는 설정에서 문자 입력을 받을 장부를 하나 지정한다.
  - 계좌는 계좌 설정에 등록한 카드 식별 문구(카드 이름이나 끝자리)로 맞춘다.
  - 맞는 계좌가 없으면 계좌가 비어 있는 미확인 항목으로 검토 목록에 들어간다. 이 거래는 계좌를 정하기 전에는 잔액과 합계에 반영하지 않는다. 이것이 "미확인 거래도 합계에 포함한다"는 규칙의 유일한 예외다.
- **문자 원문.** [사용자, 2026-11-23] 서버가 해석에 성공한 문자는 원문을 저장하지 않고 버린다. 읽지 못한 문자만 숫자열(카드 끝자리, 잔액, 누적 금액)과 이름을 가린 뒤 검토 목록에 짧게 보관한다. 보관 기간은 미정이다. 엑셀 가져오기 행의 원문은 이 결정에 들어가지 않는다.
- **출처 무관.** 이 입구는 나중에 스크래핑 API(CODEF 등) 같은 다른 출처가 같은 방식으로 들어올 수 있도록 출처에 무관하게 만든다. 은행·카드 직접 연동 자체는 범위 밖이다(2.2).

위의 status 전환, 승인취소 처리, source_key 구성, 합치기 제안 규칙은 3단계 범위다. 10장의 실제 문자·엑셀 검증(10.2, 10.3) 결과에 따라 고칠 수 있다.

### 7.4 오프라인 입력 [설계자]

- 웹앱은 연결이 없을 때 새 거래 생성만 기기에 쌓아 두었다가, 연결되면 서버로 보낸다. 수정과 삭제는 온라인에서만 한다.
- 연결이 없어도 앱이 열린다. 계좌·카테고리 목록과 최근 한 달 내역을 기기에 저장해 두고 읽기 전용으로 보여준다.
- 거래 id는 클라이언트가 만든 UUID이므로 서버 저장은 멱등하다. 같은 거래를 다시 보내도 중복되지 않는다.
- 화면에는 "보내지 않은 입력 N건"과 마지막으로 서버와 맞춘 시각을 항상 보여준다.

### 7.5 복구 [설계자]

- change_log로 거래 단위의 변경 이력을 볼 수 있다.
- 사용자는 장부를 엑셀 또는 CSV로 내보낼 수 있다. 1단계에 포함한다.
- 서버 DB는 매일 자동으로 백업한다. 이것은 운영 항목이다.

조사에서는 사용자가 직접 복구할 수단이 있는지가 앱 평가를 크게 갈랐다([R1] 부록 C 요약).

## 9. 출시 전에 정해야 할 것 [미결]

아래 항목 중 2, 3, 4번은 2026-11-18에 결정되었고(기능정의서 P-114, P-110, P-111로 확정), 1번의 웹 공개 시점과 6번은 2026-11-23에 결정되었다. 남은 것은 1번의 App Store 등록 시점과 5번의 개인정보 처리방침 내용, 백업 보관 위치와 기간이다. 간편 로그인(기능정의서 P-116)도 미결이며 기능정의서 5장에 있다. 이 문서는 남은 항목의 답을 정하지 않고 질문으로만 적는다.

1. **공개 출시 시점.** 어느 단계가 끝났을 때 공개 출시하는가? 웹을 공개하는 시점과 App Store에 등록하는 시점을 각각 언제로 하는가? 결정 [사용자, 2026-11-23]: 2단계(이벤트와 공유)와 출시 준비가 끝난 뒤, 3단계(입력 줄이기) 전에 웹을 공개한다. App Store 등록 시점은 정하지 않았다(미결).
2. **유료화.** 유료화를 하는가? 한다면 어떤 방식으로 하는가? 결정 [사용자, 2026-11-18]: 출시 때 전부 무료이고 결제 기능은 없다. 유료화는 출시 후 사용 현황을 보고 정한다.
3. **회원 탈퇴 시 데이터 처리.** 유예 기간을 두는가? 무엇을 언제 삭제하는가? 탈퇴한 사람이 공유 장부에 적은 거래는 어떻게 되는가? OWNER가 탈퇴하면 그 장부는 어떻게 되는가? 결정 [사용자, 2026-11-18]: 30일 유예 뒤 영구 삭제하고, 유예 중 로그인하면 탈퇴가 취소된다. 혼자 쓰던 장부는 함께 삭제한다. 공유 장부에 적은 거래는 남기고 작성자와 결제한 사람의 이름만 "탈퇴한 사용자"로 바꾼다. 다른 구성원이 있는 장부의 OWNER는 소유권을 넘기거나 장부를 삭제해야 탈퇴할 수 있다(2026-11-18 기능정의서 P-110으로 확정).
4. **비로그인 상태.** 로그인하지 않은 사람에게 어디까지 보여주는가? 결정 [사용자, 2026-11-18]: 소개 페이지, 로그인, 가입과 이메일 인증, 비밀번호 재설정, 약관, 개인정보 처리방침, 초대 링크 화면만 보여준다(2026-11-18 기능정의서 P-111로 확정). 가계부 내용은 로그인해야 보인다. 예외는 열람 링크로 여는 읽기 전용 화면이다(7.2).
5. **개인정보와 데이터 보관 책임.** 개인정보 처리방침은 어떻게 하는가? 타인의 금융 데이터를 서버에 보관하는 책임을 어떻게 지는가(암호화, 백업 보관 기간)? 조사에서도 공개 출시 구조를 가르는 기준으로 "타인의 금융 데이터를 내 서버에 둘 책임"을 꼽았다([R1] 부록 A). 결정 일부 [사용자, 2026-11-23]: 결제 문자 원문은 해석에 성공하면 버리고, 읽지 못한 문자만 숫자열과 이름을 가려 짧게 보관한다(7.3, 보관 기간은 미정). 개인정보 처리방침 내용과 백업 보관 위치와 기간은 남았다.
6. **호스팅 위치.** 서버를 어디에서 운영하는가? 결정 [사용자, 2026-11-23]: 서버는 Oracle Cloud의 국내 리전(서울 또는 춘천)에 둔다. 계정의 홈 리전은 사용자가 확인 중이며, 홈 리전이 해외여서 무료 자원을 국내에 만들 수 없으면 다시 정한다. 백업 보관 위치는 이 결정에 들어가지 않으며 5번과 함께 남았다. [설계자] 개발과 초기 검증은 로컬 Docker로 한다. iPhone 검증(10.1) 전까지는 HTTPS로 접근할 수 있는 곳이 필요하다.

**진행 순서 [사용자].** 사용자는 설계와 계획이 끝나면 승인 없이 가능한 간단한 부분부터 작업을 시작하라고 했다. 그래서 저장소, 프로젝트 뼈대, Docker 구성, 1단계 데이터 구조와 그 테스트는 기획 문서보다 먼저 시작한다. 화면이 들어가는 작업과 위 미결 항목에 걸린 작업은 기획 문서(프로젝트 개요서, IA, 기능정의서, 와이어프레임, 화면설계서)에서 확정된 뒤에 한다.

## 10. 일찍 검증할 위험 [설계자]

### 10.1 iPhone 홈 화면 웹앱의 입력 경험과 데이터 생존

- **확인할 것.**
  - 홈 화면 아이콘을 눌러 입력창이 뜨기까지의 체감 시간
  - 비행기 모드에서 입력한 뒤 연결이 돌아왔을 때 전송되는지
  - 며칠 방치한 뒤에도 쌓아 둔 입력이 살아 있는지
- **관련 제약.** 오프라인 전송과 데이터 생존은 3.3의 제약(Background Sync 미지원, 저장 공간 부족 시 로컬 데이터 삭제 가능)과 관련된다.
- **시점.** 1단계 맨 앞의 스파이크로 검증한다. [R1]도 웹앱 구조를 고르면 이 항목을 먼저 검증하라고 권했다.
- **판정.** 사용자가 자기 iPhone에서 직접 써 보고 판정한다. 아이콘에서 입력창까지 걸린 시간과 오프라인 입력의 전송 결과를 기록해 판단 근거로 남긴다.
- **결과에 따른 조치.** 만족스럽지 않으면 네이티브 단계를 앞당긴다.

### 10.2 결제 문자 자동 입력이 실제로 되는지

- **확인할 것.**
  - 사용자의 카드 결제 알림이 문자로 오는지
  - 단축어 자동화가 확인 없이 서버 전송까지 실행되는지
- **시점.** 3단계 전에 실제 iPhone으로 확인한다.
- **왜 위험한가.** 앱 푸시와 카카오 알림톡은 단축어 메시지 자동화에 걸리지 않는다([R1] 작업 보고). 확인 없이 실행되는지도 iOS 버전별 보고가 엇갈린다(3.1).
- **결과에 따른 조치.** 이 문서에서 정하지 않았다.

### 10.3 카드사 엑셀이 상태 모델과 맞는지

- **확인할 것.** 카드사 엑셀 한 달치에서 승인, 매입, 취소, 할부 표기가 이 설계의 상태 모델(PENDING, POSTED, CANCELED와 할부 필드)과 맞는지 확인한다.
- **시점.** 3단계 전에 확인한다.
- **결과에 따른 조치.** 이 문서에서 정하지 않았다.

### 10.4 시각 없는 입력과 짧은 이벤트

- **확인할 것.** 시각 없이 적은 수기 입력이 많을 때 짧은 이벤트(당일 데이트)의 자동 묶기가 쓸 만한지 확인한다.
- **시점.** 2단계 초에 확인한다.
- **왜 위험한가.** 시각이 없는 거래는 날짜만으로 판정하므로(7.1), 같은 날 이벤트 기간 밖에서 쓴 지출도 묶일 수 있다.
- **결과에 따른 조치.** 이 문서에서 정하지 않았다.

## 11. 구현자에게 맡기는 것 [설계자]

다음은 구현자가 정한다.

- API 세부 경로와 페이징 방식. 거래 목록을 50건씩 불러오는 것은 정해졌다(2026-11-18 기능정의서 P-232로 확정).
- React 상태 관리 방식과 UI 라이브러리
- 테이블 인덱스
- 테스트 구성
- 이벤트 재계산의 구현 방식(저장 시 계산 또는 조회 시 계산). 어느 쪽이든 7.1 규칙의 결과는 같아야 한다.

이 문서와 기능정의서에 적히지 않은 그 밖의 세부도 구현자에게 맡긴다(2026-11-18 기능정의서 작성에 따라 고침). 예를 들면 다음과 같다.

- source_key 해시 함수
- 오프라인 입력을 기기에 쌓아 두는 저장 방식
- change_log의 저장 형식과 기기 식별 방법
- recurring_rule과 budget의 필드 구성. 동작 규칙은 정해졌다(2026-11-18 기능정의서 P-230, P-231로 확정).
- 카드사별 엑셀 파서 구성
- 컬럼 이름

처음에 구현자에게 맡겼던 다음 항목은 기능정의서가 정했으므로 위 목록에서 뺐다.

- 한 줄 입력 파서의 문법 세부(2026-11-18 기능정의서 F-210으로 확정)
- 수기 입력 중복 경고의 시간 범위. 같은 날짜로 정했다(2026-11-18 기능정의서 P-218로 확정).
- 초대 링크·코드의 만료 기간과 형식. 만료는 1일, 7일, 30일 중 하나(기본 7일)이고 코드는 8자리 영문 대문자와 숫자다(2026-11-18 기능정의서 P-304로 확정).

처음에 구현자에게 맡겼던 다음 항목은 사용자가 2026-11-23에 정했으므로 위 목록에서 뺐다. [사용자, 2026-11-23]

- 인증 토큰 방식. JWT를 쓴다. access token은 15분 동안 유효하고, refresh token은 서버에 저장하고 HttpOnly 쿠키로 전달한다(5.4).

같은 날 비밀번호 저장 방식(Argon2id, 5.4)과 API 명세 방식(OpenAPI, 운영 환경에서는 문서 화면을 끈다, 5.1)도 정했다. [사용자, 2026-11-23]
