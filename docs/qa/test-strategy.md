# 테스트 전략

기준: main `9a31116`(2026-11-23). 작성: qa 봇.
"지금 있는 테스트 점검"은 코드를 읽기만 했고 테스트를 실행하지 않았다.

## 1. 원칙

- 위쪽 테스트가 실패했는데 그에 맞는 아래쪽 테스트가 없으면, 고칠 때 아래쪽 테스트를 먼저 추가한다. 아래에서 이미 확인한 조건을 위에서 다시 확인하지 않는다.
- 끝에서 끝까지 테스트는 핵심 흐름에만 두고, 계산과 분기는 작은 테스트와 중간 테스트로 내린다.
- 협력 객체는 실제 객체와 실제 DB로 테스트한다. 가짜는 외부 시스템처럼 꼭 필요한 곳에만 쓴다.
- 합격 기준은 명세에 고정한다. 모호하면 추측으로 통과시키지 않고 질문을 남긴다.
- 커버리지 숫자는 목표나 합격 기준으로 쓰지 않는다. 안 덮인 코드를 찾는 데만 쓴다.
- 들쭉날쭉한 테스트는 발견하면 바로 따로 떼어 놓고 기한 1주를 둔다. 다시 돌려서 덮지 않는다. 테스트끼리 서로 영향을 주는지를 먼저 의심한다. web도 같다. web에서는 다음을 지킨다.
  - 처음 본 쪽이 바로 bug 이슈로 올린다. 건너뛰거나 지우지 않는다.
  - 테스트끼리 주는 영향은 전역 정리와 파일 간 순서부터 의심한다.
- 자동 검사가 있어도 탐색 테스트를 없애지 않는다.

## 2. 층별로 보는 것

| 층 | 보는 것 | 넣지 않는 것 |
|---|---|---|
| 작은 테스트 (DB·네트워크·기다림 없음) | 금액 범위, 날짜 범위, 이름 정규화, 합계 부호, 정렬 규칙 같은 순수 계산과 분기 | 스프링 컨텍스트 |
| 중간 테스트 (실제 PostgreSQL, Testcontainers) | 서비스 규칙, 잔액·합계 쿼리, DB 제약, 마이그레이션, 동시 요청(같은 거래 id 두 번, 동시 가입, refresh token 동시 갱신) | 가짜 저장소 |
| API 테스트 (HTTP 요청) | 상태 코드, 오류 응답 형식(ADR 002), 인증 401, 구성원 아님 404, 금액이 JSON 정수인지, OpenAPI 문서에 나오는지 | 아래 층에서 본 계산을 값마다 다시 확인하기 |
| 화면 컴포넌트 (Vitest, `web/tests/`) | 입력 검증 문구, 불러오는 중·데이터 없음·오류·입력 오류 상태, 금액 표시 형식 | 실제 서버 |
| 끝에서 끝까지 (Playwright, `e2e/`) | 핵심 흐름만 | 경계값, 분기 |
| 탐색 세션 (qa) | 조각이 끝날 때와 위험이 큰 PR(금액 계산, 날짜 경계, 권한) | — |

- 지금 서버 테스트 57개는 전부 스프링 전체를 띄우는 중간 크기다. 이것을 고쳐 쓰지는 않는다. 새로 쓰는 계산과 분기는 작은 테스트로 먼저 쓴다.
- 동시성 테스트는 "테스트마다 롤백" 방식으로는 쓸 수 없다. 실제로 커밋하는 테스트 묶음을 따로 두고 테스트마다 고유한 이메일을 쓴다.
- 화면 테스트는 getByRole, getByLabelText, getByText, getByTestId 순서로 찾는다. role로 찾지 못하면 접근성 결함으로 보고한다.

## 3. 끝에서 끝까지 테스트 범위 (1A)

1. 가입 → 첫 계좌 만들기 → 지출 입력 → 내역에 보임 → 홈의 이번 달 합계와 계좌 잔액이 맞음
2. 로그아웃 → 로그인 → 같은 데이터가 보임
3. 거래 수정 → 삭제 → 되돌리기 뒤 합계가 원래대로 돌아옴
4. 수입·이체 입력 뒤 잔액이 맞고, 이체가 수입·지출 합계에 들어가지 않음

- Chromium과 WebKit(아이폰 크기) 두 가지로 돌린다.
- 요소는 사용자가 보는 것(role, label, 글자)으로 찾는다.
- 화면이 생긴 뒤에 시작한다(owner 결정 1).

## 4. 테스트 데이터

- 끝에서 끝까지 테스트는 테스트마다 새 이메일로 가입해 장부를 따로 쓴다. 테스트 환경에서만 허용 목록에 테스트용 도메인을 넣는다(owner 결정 3).
- 가맹점과 금액은 지어낸 값만 쓴다. 실제 카드 내역과 개인신용정보는 레포와 테스트 데이터에 넣지 않는다.
- 거래 날짜는 명시해서 넣는다. "오늘", "이번 달"이 걸린 테스트는 서버는 주입한 시계(이슈 #5)로, 브라우저는 Playwright의 시계 고정으로 맞춘다.
- 테스트는 고정 이메일이나 테이블 전체 건수에 기대지 않는다.

## 5. 아이폰 Safari 확인

- 자동: Playwright WebKit. Safari와 같은 엔진이지만 실제 아이폰은 아니다.
- 실기기: 첫 배포 주소가 생긴 뒤 조각이 끝날 때마다 owner 아이폰에서 정해진 흐름을 돈다(owner 결정 2). 임시 터널은 쓰지 않는다.
- 실기기에서만 볼 수 있는 것: 홈 화면 설치(F-120), 키보드가 입력칸을 가리는지, 글자 크기 대응(F-903), 입력 속도 측정(개요서 KPI: 입력 시간 중앙값).
- 추정: refresh token 쿠키가 `Secure`이므로 아이폰에서 맥의 개발 서버를 http로 열면 로그인이 유지되지 않는다. 그래서 실기기 확인은 HTTPS 주소가 있어야 한다.

## 6. 탐색 세션

- 시간을 정한 세션으로 한다. 세션마다 무엇을 알아낼지 한 줄 목표와 기록을 남긴다.
- 예: "말일 23:59에 입력한 지출이 다음 달 합계로 넘어가는지 알아낸다."
- 1A에서 최소 3회: 입력과 합계, 인증과 토큰 만료, 아이폰 화면.

## 8. web 컴포넌트 테스트의 시계

배경: #219, #225, #260이 같은 원인으로 사흘에 세 번 테스트를 흔들었다. 가림막·덮개가 걷히기를 기다리는 곳에서 가짜 시계와 진짜 시계가 섞인 것이다(triage, 2026-11-27). 아래 규칙은 qa와 frontend가 2026-11-27에 합의했다.

1. 가림막(pressGuard)이나 덮개(dialog shield)를 여는 화면을 그리는 파일은 파일 전체에서 같은 시계 설정 하나만 쓴다. 기본은 공용 도우미가 켜는 가짜 타이머이고, userEvent는 `advanceTimers`로 그 타이머에 연결한다. 파일 중간에 `useRealTimers`로 바꾸지 않는다.
   - 대상: `web/tests/support`의 앱 그리기 도우미(`openApp` 등)나 dialog 도우미를 import하는 파일.
   - 정확한 설정은 #260에서 정하고 `web/tests/support`에 둔다.
2. 기다리기는 공용 도우미 하나로 한다. 도우미가 가짜 타이머를 진행시켜 가림막을 걷는다. 실제 시간이 지나기를 기다리지 않는다.
3. 날짜와 시각은 `lib/clock`의 `now()`로 읽는다. 테스트에서는 `tests/support/clock`의 `setDeviceClock`으로 시계를 주입해(`lib/clock`의 `setClock`) 맞춘다. 가짜 타이머의 `setSystemTime`으로 날짜를 맞추지 않는다. 가짜 타이머는 타이머를 진행시키는 데만 쓴다.
   - 시각은 렌더 전에 맞춘다. 대기 중인 타이머가 있을 때 시각을 바꾸거나 뒤로 돌리지 않는다(#225의 원인).
4. 전역 정리는 실제로 기다리지 않는다. 가짜 타이머를 진행시켜 가림막과 덮개를 걷고, 그래도 남으면 남긴 파일과 테스트 이름을 담아 바로 실패한다.
5. 1번 대상 파일에서 `useRealTimers`가 나오면 실패하는 검사를 `web/tests/support`에 둔다. 대상인지는 import로 가린다.
6. 가짜 서버(msw)의 핸들러는 그 테스트에서 보낸 요청이 모두 핸들러에 닿은 뒤에 비운다. 공용 `web/tests/support/mockServer.ts`가 한다. 앞 테스트의 늦은 요청이 다음 테스트의 핸들러에 닿으면 안 된다(#260의 둘째 원인).
7. 확인: 5개 시간대(Asia/Seoul, UTC, America/Los_Angeles, Pacific/Kiritimati, Pacific/Pago_Pago)에서 각각 10번 돌려 0번 실패하고, CPU 부하를 건 상태에서 한 번 돌린다(#260 수용 기준).
8. 화면을 옮긴 뒤 새 화면을 읽을 때 주소(`router.state`)나 토스트로 그려졌다고 보지 않는다. 새 화면에만 있는 요소를 `findBy…`로 먼저 기다리고, 그런 요소가 없으면 `tests/support/shownScreen.tsx`의 `untilShown(router)`를 쓴다(#291, #336).
9. 앱과 따로 싣는 화면의 코드를 처음 받는 시간은 `findBy…`·`waitFor` 1초 한도에 넣지 않는다. `tests/support/screenCode.ts`가 파일마다 `beforeAll`에서 미리 받는다. 파일(= vitest 프로세스)에서 앱을 처음 그리고 첫 요청을 보내는 비용도 같다. 같은 `beforeAll`에서 `tests/support/firstRun.tsx`가 내역을 따로 띄운 가짜 서버로 한 번 그리고 버린다. 한도를 늘려 덮지 않는다(#291, #336, #363).
