# PR 전 점검표와 버그 보고 양식

기준: main `9a31116`(2026-11-23). 작성: qa 봇.

## 1. PR을 올리기 전에 스스로 보는 점검표 (ledger, frontend)

1. 수용 기준 한 줄마다 테스트 하나가 대응하는지 PR 본문에 표로 적었다.
2. 거부 테스트는 어떤 규칙으로 거부됐는지(오류 값 또는 입력란)와 DB에 남지 않았는지까지 본다.
3. 금액은 0, 1, 9,999,999,999, 10,000,000,000을 각각 따로 테스트했다.
4. 날짜는 2월 말(윤년 포함), 말일, 연말·연초를 넣었고, "오늘"은 주입한 시계로 서울 자정 전후를 봤다.
5. 구성원 아님은 404이고 응답에 남의 값이 없다.
6. 목록은 2건 이상으로 순서를, 합계는 손으로 계산한 리터럴로 확인했다.
7. 한 테스트에 사례 하나. 기대값을 바꾸면 실패하는지 한 번 해 봤다.
8. 테스트가 고정 이메일이나 테이블 전체 건수에 기대지 않는다.
9. 화면은 role과 label로 찾았고, 불러오는 중·데이터 없음·오류·입력 오류 네 가지를 봤다.
10. 지키지 못한 항목은 이유를 PR 본문에 적었다.

## 2. 버그 보고 양식 (triage와 맞춤, 2026-11-23)

### 규칙

- 버그 한 건에 이슈 하나.
- 제목: `[영역] 무엇이 어떻게 잘못되는지 한 줄`. 다시 생긴 버그는 맨 앞에 `REGRESSION:`을 붙인다.
- qa는 `bug` 라벨만 붙인다. `ready`와 영역·심각도·우선순위 라벨은 붙이지 않는다(triage와 owner가 한다).
- 같은 원인으로 보이는 증상도 따로 올리고 본문에 "같은 원인으로 보임: #번호(추정)"를 적는다. 원인이 같다고 확인되면 triage가 묶는다.

### 본문 항목

1. 요약 (한두 문장)
2. 재현 빈도 (예: 5회 중 5회)
3. 재현 단계 (번호, 입력값 그대로)
4. 데이터 조건: 날짜와 시각(월말, 1일, 연말, 자정 앞뒤), 금액, 거래 유형, 계좌 종류
5. 기대 결과 (근거: F-ID, P-ID, 이슈의 수용 기준, 화면설계서 위치)
6. 실제 결과: 오류 문구, 응답 코드를 그대로. 저장된 값이 틀린지 화면 표시만 틀린지 구분한다
7. 환경: 커밋 또는 PR 번호, 브라우저·기기·OS, 화면 크기, 계정 역할
8. 일어난 시각(Asia/Seoul)과 요청 id(있으면)
9. 증거: 스크린샷, 요청과 응답. 토큰, 비밀번호, 개인신용정보는 넣지 않는다
10. 심각도 (qa 판단): 치명(S1) / 높음(S2) / 보통(S3) / 낮음(S4)
11. 우선순위 제안 (qa 의견. 라벨은 triage가 붙인다)
12. 우회 방법이 있는지와 영향 범위
13. 마지막으로 정상이던 커밋 또는 PR (알 때만. REGRESSION이면 필수)
14. 확인 구분(확인/추정/미확인)과 찾은 경로(탐색 세션, 수용 기준 검증, 회귀 점검)

### 심각도 정의 (triage 초안, owner 승인 전)

| 심각도 | 정의 |
|---|---|
| S1 치명 | 금액·잔액이 틀리게 저장된다, 데이터가 사라진다, 남의 장부가 보인다, 아무도 로그인할 수 없다. |
| S2 높음 | 핵심 흐름(가입, 로그인, 거래 입력, 목록, 잔액)이 막히거나 틀린 값이 보이는데 우회가 없다. |
| S3 보통 | 우회가 있거나 부가 기능이다. |
| S4 낮음 | 문구와 보기. |

영역, 심각도, 우선순위 라벨 이름은 triage가 owner 승인을 받은 뒤 확정한다.
