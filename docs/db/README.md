PostgreSQL 17 + Flyway. 이 폴더는 DB 기준이고 dba 봇이 관리한다. 반영은 ledger, 백업 실행은 devops가 한다.

## 결정 기록

| 날짜 | 결정 | 이유 |
|---|---|---|
| 2026-11-26 | 장부 전체 잔액 쿼리의 `account`와 거래 id로 찾는 이력 조회에는 장부 조건을 걸지 않는다(4절의 예외). | 조건을 더하면 계획이 나빠지거나(PR #170) 읽는 양이 줄지 않는다(PR #175). |
| 2026-11-26 | 앱의 DB 연결에 `force_custom_plan`이 들어갔다(PR #189). 한꺼번에 넣는 작업만 되돌릴지 재서 정한다. | 외래키 검사 비용(거래 한 건에 약 0.05ms)보다 큰 장부 조회의 효과가 크다. |
| 2026-11-26 | 확장 통계와 잔액 쿼리에서 `account` 조인을 없애는 안은 넣지 않는다. | perf 측정에서 잔액 계획이 그대로이거나 큰 장부의 버퍼가 2.7배였다(PR #176). |
| 2026-11-26 | 이름, 가맹점, 메모에 NFC·앞뒤 공백류·제어 문자 CHECK를 건다. 거래는 채우지 않는다(V17, V18). | 운영에 거래가 없는 지금이 채우기 없이 걸 수 있는 때다(#123). |
| 2026-11-25 | `change_log`의 순서 번호는 `after_value`의 `version`으로 채운다(V14). | 컬럼의 뜻과 같은 값이고 동점이 없다(PR #175). |
| 2026-11-25 | 앱이 앞뒤 공백을 지워 저장하는 컬럼에는 `CHECK (col = btrim(col))`를 같이 건다. | 공백만 다른 값으로 유니크가 뚫리는 것을 막는다. 앱이 통과시킨 값은 걸리지 않는다(PR #122). |
| 2026-11-25 | 타입 변경을 여러 단계로 나누는 절차는 옛 코드가 깨지는 변경에만 쓴다. | `varchar(n)` → `text`는 테이블을 다시 쓰지 않고 전 버전 앱과 맞는다. 나누면 마이그레이션만 늘어난다(PR #130). |
| 2026-11-25 | 이메일의 CHECK는 ASCII 인쇄 가능 문자에서 대문자를 뺀 정규식 하나로 건다: `(email COLLATE "C") ~ '^[\x21-\x40\x5B-\x7E]+$'`(#20). | 이메일은 ASCII만 받는다(P-101). 공백, 대문자, ASCII 밖 글자를 한 제약으로 막고 `lower()`처럼 로캘에 따라 달라지지 않는다. |
| 2026-11-25 | 인덱스 기준의 "3컬럼 이하"는 키 컬럼 수로 센다. `INCLUDE` 컬럼은 2개까지, 측정 근거가 있을 때만 쓴다. | 인덱스만 읽는 계획을 후보로 잴 수 있어야 하고, 제한이 없으면 인덱스가 테이블만큼 커진다. |
| 2026-11-25 | 앱의 DB 연결에 `plan_cache_mode = force_custom_plan`을 건다(#112). | pgJDBC가 같은 문장을 여러 번 실행하면 일반 계획을 쓸 수 있고, 계좌 하나에 라인 20만 건인 큰 장부에서 계좌 하나 잔액이 284ms에서 1.8~2.0초가 된다(PR #111). 계획을 매번 세우는 비용은 데운 상태에서 1ms 미만이다. |
| 2026-11-25 | 라인·거래의 장부 단위 인덱스는 지금 넣지 않고 2단계 시작 전에 다시 판단한다(#113). 잔액 쿼리는 #58에서 장부 조건으로 바꾼다. | 1단계 규모는 DB 전체가 메모리에 들어가 상한 안이다. 인덱스는 300만 건에서 약 450MB가 들고 넣기 시간도 늘어난다(대략 35~52%, 다시 잴 값). |
| 2026-11-24 | 키는 UUID를 유지한다. identity 컬럼을 쓰지 않는다. | 거래 id를 클라이언트가 만들고(오프라인 입력 P-225, 재전송), 주소에 id가 드러난다. |
| 2026-11-24 | transaction_line에 ledger_id와 복합 FK를 넣어 장부 경계를 DB로 강제한다(#58). | 다른 장부의 행을 가리킬 수 없게 하기 위해서다. |
| 2026-11-24 | 1단계 백업 목표는 시점 복구 없이 최대 유실 24시간, 복구 4시간 이내. 시점 복구는 2단계 시작 전(다른 사람의 데이터가 들어오기 전)에 시작한다. | 마지막 백업 뒤의 입력은 사라질 수 있다. owner가 받아들인 위험이다(2026-11-24). |
| 2026-11-24 | 백업 보관은 매일 7개, 매주 4개, 가장 오래된 것이 35일. | 탈퇴·영구 삭제된 데이터가 백업에 남는 최장 기간이 35일이 된다. |
| 2026-11-24 | 변경 이력: 장부를 영구 삭제하면 이력도 지운다. 거래를 완전히 지우면 이력에는 누가 언제 지웠는지만 남기고 내용 값은 지운다. 탈퇴한 사람의 actor_id는 NULL(#60). | 이력의 전후 값에 가맹점과 메모가 들어 있어, 지운 데이터가 이력에 계속 남지 않게 하기 위해서다. |
| 2026-11-24 | "공개 뒤 규칙"은 owner가 운영 DB에 실제 지출을 넣기 시작하는 날부터 적용한다. | 그 전에는 데이터가 적어 잠금과 긴 검증이 문제 되지 않는다. |
| 2026-11-23 | 잔액은 저장하지 않고 라인 합으로 계산하는 지금 구조를 유지한다. 잔액 스냅샷은 측정으로 필요가 확인될 때만, "스냅샷 + 이후 합 = 전체 합" 대조 검사와 함께 넣는다. | 잔액 컬럼이 없으면 잔액과 라인 합이 어긋날 일이 없다. 변경 내용은 change_log에 전후 값으로 남는다. |

## 스키마 PR 검토 절차

1. ledger가 스키마나 쿼리를 바꾸는 PR을 올리고 dba에게 검토를 요청한다.
2. dba는 [schema-standards.md](schema-standards.md)와 [migration-standards.md](migration-standards.md)의 점검표로 본다.
3. 머지는 owner가 한다.
