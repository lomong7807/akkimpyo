PostgreSQL 17 + Flyway. 이 폴더는 DB 기준이고 dba 봇이 관리한다. 반영은 ledger, 백업 실행은 devops가 한다.

## 결정 기록

| 날짜 | 결정 | 이유 |
|---|---|---|
| 2026-11-24 | 키는 UUID를 유지한다. identity 컬럼을 쓰지 않는다. | 거래 id를 클라이언트가 만들고(오프라인 입력 P-225, 재전송), 주소에 id가 드러난다. |
| 2026-11-24 | transaction_line에 ledger_id와 복합 FK를 넣어 장부 경계를 DB로 강제한다(#58). | 다른 장부의 행을 가리킬 수 없게 하기 위해서다. |
| 2026-11-24 | 1단계 백업 목표는 시점 복구 없이 최대 유실 24시간, 복구 4시간 이내. 시점 복구는 2단계 시작 전(다른 사람의 데이터가 들어오기 전)에 시작한다. | 마지막 백업 뒤의 입력은 사라질 수 있다. owner가 받아들인 위험이다(2026-11-24). |
| 2026-11-24 | 백업 보관은 매일 7개, 매주 4개, 가장 오래된 것이 35일. | 탈퇴·영구 삭제된 데이터가 백업에 남는 최장 기간이 35일이 된다. |
| 2026-11-24 | 변경 이력: 장부를 영구 삭제하면 이력도 지운다. 거래를 완전히 지우면 이력에는 누가 언제 지웠는지만 남기고 내용 값은 지운다. 탈퇴한 사람의 actor_id는 NULL(#60). | 이력 처리 기준은 #60에 있다. |
| 2026-11-24 | "공개 뒤 규칙"은 owner가 운영 DB에 실제 지출을 넣기 시작하는 날부터 적용한다. | 공개 전과 뒤의 마이그레이션 규칙을 가르는 기준일이다. |
| 2026-11-23 | 잔액은 저장하지 않고 라인 합으로 계산하는 지금 구조를 유지한다. 잔액 스냅샷은 측정으로 필요가 확인될 때만, "스냅샷 + 이후 합 = 전체 합" 대조 검사와 함께 넣는다. | 현재 구조 유지. 스냅샷은 측정으로 필요가 확인될 때만 넣는다. |

## 스키마 PR 검토 절차

1. ledger가 스키마나 쿼리를 바꾸는 PR을 올리고 dba에게 검토를 요청한다.
2. dba는 [schema-standards.md](schema-standards.md)와 [migration-standards.md](migration-standards.md)의 점검표로 본다.
3. 머지는 owner가 한다.
