# 스키마 기준

PostgreSQL 17 + Flyway 기준이다. 마이그레이션 규칙은 [migration-standards.md](migration-standards.md), 결정 배경은 [README.md](README.md)의 결정 기록을 본다.

## 1. 타입

- 기록 시각(`created_at`, `updated_at`, `deleted_at` 등)은 `timestamptz`. 시간대 없는 `timestamp`를 쓰지 않는다.
- 거래의 날짜와 시각은 `date`와 `time`으로 변환 없이 저장한다(P-202). 시간대를 붙이지 않는다.
- 문자열은 `text` + `CHECK (char_length(col) BETWEEN a AND b)`. `varchar(n)`, `char(n)`을 쓰지 않는다.
- 금액은 `bigint` 원 단위 정수. `money`, 부동소수점 금지. 범위는 CHECK로 건다(±9,999,999,999, P-201).
- 키는 `uuid`. `serial`, identity를 쓰지 않는다(결정 기록 참고).
- 열거형 값은 `text` + `CHECK (col IN (...))`. PostgreSQL enum 타입을 쓰지 않는다. Java enum에 값을 더하면 CHECK를 바꾸는 마이그레이션을 같이 올린다.
- 상태 표시는 boolean보다 `..._at timestamptz NULL`을 먼저 검토한다(예: 숨긴 시각).

## 2. 제약

- 지킬 수 있는 규칙은 앱 검사보다 DB 제약(NOT NULL, CHECK, FK, UNIQUE)으로 먼저 건다. 앱 검사는 사용자에게 보여 줄 오류를 위해 같이 둔다.
- 유일해야 하는 것은 UNIQUE로 건다. 앱의 "있는지 보고 저장"만으로는 동시 요청에 중복이 생긴다. 유니크 위반은 제약 이름으로 구분해 사용자 오류로 바꾼다.
- 제약 이름으로 오류를 구분하려면 DB 서버의 오류 메시지가 영어여야 한다. Hibernate가 제약 이름을 영어 메시지에서 뽑는다(PR #153). 운영 DB의 `lc_messages`를 영어로 둔다. 공식 `postgres:17` 이미지의 기본은 `LANG=en_US.utf8`이다(확인, #52).
- NULL이 들어가는 컬럼을 포함한 유니크는 `UNIQUE NULLS NOT DISTINCT`를 검토한다.
- 소프트 삭제 테이블의 고유성은 `WHERE deleted_at IS NULL` 부분 유니크 인덱스로 건다.
- 장부에 속한 테이블끼리의 참조는 `ledger_id`를 포함한 복합 FK로 건다(다른 장부의 행을 가리킬 수 없게).
- FK의 삭제 동작은 기본값(거부)으로 둔다. `ON DELETE CASCADE`는 기획이 "함께 지운다"고 정한 곳에만 쓴다(지금은 거래 → 라인, P-203).
- 시간이 지나면 달라지는 조건(예: "오늘부터 1년 뒤까지")은 CHECK로 걸지 않는다. 앱 검사로 둔다.
- 앱이 앞뒤 공백을 지워 저장하는 컬럼(이름 등)에는 `CHECK (col = btrim(col))`를 같이 건다. 공백만 다른 값이 DB에서는 다른 값이라, 앱의 정리를 거치지 않는 경로가 생기면 유니크가 뚫린다. `btrim`은 일반 공백(U+0020)만 지운다. 그 밖의 공백류와 제어 문자는 #123에서 다룬다.
- 소문자로 저장하는 값의 CHECK는 `lower()`를 쓰지 않고 `COLLATE "C"`의 글자 범위로 건다. `lower()`의 결과는 DB 로캘에 따라 달라져, 앱이 통과시킨 값을 DB가 거부할 수 있다. 이메일은 `(email COLLATE "C") ~ '^[\x21-\x40\x5B-\x7E]+$'`다(#20, V7).

## 3. 이름

- 테이블과 컬럼은 snake_case, 새 테이블은 단수. 기존 `users`, `transaction`은 바꾸지 않는다.
- 제약과 인덱스에 이름을 붙인다.

| 종류 | 형식 |
|---|---|
| 기본키 | `pk_<테이블>` |
| 유니크 | `uq_<테이블>_<뜻>` |
| 외래키 | `fk_<테이블>_<대상>` |
| 체크 | `ck_<테이블>_<뜻>` |
| 인덱스 | `ix_<테이블>_<뜻>` |

- V1의 이름 없는 제약은 그대로 둔다.

## 4. 인덱스와 쿼리

- 복합 인덱스는 등호로 늘 쓰이는 컬럼(대개 `ledger_id`)을 맨 앞에 둔다.
- 유니크가 아닌 인덱스는 키 컬럼 3개 이하. `INCLUDE` 컬럼은 2개까지, 측정 근거가 있을 때만 쓴다.
- 쿼리를 그대로 두고 인덱스만 더하지 않는다. 인덱스를 넣는 PR에는 대상 쿼리와 `EXPLAIN (ANALYZE, BUFFERS)` 결과를 붙이고, 예상 행 수와 실제 행 수를 같이 본다. 쓰기 쿼리는 `BEGIN`과 `ROLLBACK`으로 감싸서 본다.
- 시각과 날짜 구간은 `BETWEEN` 대신 `>=`와 `<`로 쓴다.
- FK 컬럼으로 조회하거나 부모 행을 지우는 경로가 있으면 그 컬럼에 인덱스를 둔다.
- 성능 기준은 제안값이다. 측정은 `docs/perf/results/`에 있다(perf). 여러 장부가 섞인 DB(장부 1,000개 300만 건) 안의 큰 장부 5만 건을 기준으로 판정한다(DB 실행 시간, 중앙값).

| 쿼리 | 제안값 |
|---|---|
| 거래 목록 50건 | 50ms |
| 월별 통계 | 100ms |
| 장부 전체 잔액 | 200ms |

- 이 세 쿼리의 실행 계획에 transaction, transaction_line 전체 훑기가 없어야 한다.
- 전체 훑기 판정은 여러 장부가 섞인 DB에서만 한다. 장부가 하나뿐인 DB에서는 거의 모든 행을 읽으므로 전체 훑기가 옳은 계획이다.
- 장부에 속한 테이블을 읽는 쿼리는 테이블마다 `ledger_id` 조건을 직접 건다. 조인으로만 장부를 좁히면 큰 장부에서 라인 수만큼 흩어진 블록을 읽는다(측정: 큰 장부의 장부 전체 잔액 1,923ms → 137ms, PR #111).
- 예외: 조건을 더하면 계획이 나빠지는 쿼리가 있다. 계획기는 장부 조건들을 서로 독립으로 보고 곱해 예상 행 수를 지나치게 작게 잡는다. 그래서 장부 조건을 더하는 쿼리는 하나씩 잰다(PR #170, #176).
  - 장부 전체 잔액 쿼리는 `account`에 장부 조건을 걸지 않는다. 300만 건 DB에서 더하면 보통 장부가 약 30ms에서 1초 이상이 됐다(PR #170). 그 대신 `account`를 전부 훑는 것(약 7,500행)을 받아들인다.
  - 거래 id로 찾는 이력 조회(`change_log`의 `transaction_id`)에는 장부 조건을 걸지 않는다. 거래 id가 전체에서 하나라 읽는 양이 줄지 않는다(PR #175).
- 앱의 DB 연결은 `plan_cache_mode = force_custom_plan`으로 둔다(#112). 장부 크기가 장부마다 크게 달라, 값과 무관한 일반 계획은 큰 장부에서 느리다.
- 한꺼번에 많이 넣는 작업(가져오기 같은)은 그 트랜잭션만 `SET LOCAL plan_cache_mode = auto`로 둘지 재서 정한다. 외래키 검사도 검사마다 계획을 세워, 거래 한 건에 약 0.05ms가 는다(PR #189).
- 쿼리를 잴 때는 값을 직접 넣은 계획과 `PREPARE` 뒤 일반 계획을 둘 다 본다.

## 5. 변경 이력(change_log)

- 살아 있는 거래(휴지통에 있는 거래 포함)의 이력은 추가만 한다. 형식과 삭제 때 처리는 [ADR 007](../adr/007-change-log-format.md)이 정한다.
- 이력 행을 지우는 경로는 둘뿐이다: 거래 완전 삭제(그 거래의 기존 이력 행을 모두 지우고 완전 삭제 기록 행 하나만 남긴다), 장부 영구 삭제(그 장부의 이력을 모두 지운다).
- 이력 행을 고치는 경로는 하나뿐이다: 탈퇴 정리(`actor_id`, 전후 값 JSON 안의 `createdBy`·`paidBy`, 그 사람 행의 `device_id`를 비운다). `actor_id`와 `device_id`는 같은 문장에서 비운다.
- 순서는 `created_at`이 아니라 거래 `version`으로 정한다. `UNIQUE (transaction_id, version)`을 건다(#60). 완전 삭제 기록 행의 `version`은 마지막 `version` + 1이다.
- 완전히 지운 거래의 id는 다시 쓸 수 없다. DB 제약으로는 걸 수 없어 만들기 경로가 완전 삭제 기록을 확인한다.
- `actor_id`가 NULL인 행은 action이 서버 동작이면 자동 삭제, 사람 동작이면 탈퇴한 사람이다.
- 행마다 `format_version`을 둔다(1부터). 지난 행은 다시 쓰지 않는다.
- 공개 뒤에는 DB 역할을 나눠, 일반 요청 경로는 `change_log`에 추가만 할 수 있게 한다([migration-standards.md](migration-standards.md) 3절).

## 7. 스키마 PR 점검표

- [ ] 타입 금지 목록(`varchar(n)`, `char(n)`, `money`, 부동소수점, 시간대 없는 `timestamp`, `serial`, identity, PostgreSQL enum)의 타입이 없다.
- [ ] 새 규칙이 DB 제약으로 걸려 있다.
- [ ] 제약과 인덱스에 이름이 있다.
- [ ] 장부에 속한 테이블 사이의 참조는 복합 FK다.
- [ ] 유니크가 아닌 인덱스는 키 컬럼 3개 이하(`INCLUDE`는 2개까지)이고, 새 인덱스에는 `EXPLAIN (ANALYZE, BUFFERS)`가 첨부돼 있다.
- [ ] 장부에 속한 테이블을 읽는 쿼리가 테이블마다 `ledger_id` 조건을 건다.
- [ ] Java enum과 CHECK 값이 일치한다.
- [ ] 앱이 정리해 저장하는 값(앞뒤 공백, 소문자)에 같은 뜻의 CHECK가 있다.
- [ ] `ddl-auto=validate`를 통과한다.
