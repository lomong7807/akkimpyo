# 마이그레이션 기준

Flyway 마이그레이션(`server/src/main/resources/db/migration/`) 기준이다. 타입과 제약은 [schema-standards.md](schema-standards.md)를 따른다.

## 1. 지금부터 지킨다

- main에 들어간 V 파일은 고치지 않는다. 고칠 것은 새 파일로 앞으로 고친다. 예외는 복원 절차뿐이다([restore-runbook.md](restore-runbook.md) 4번).
- 파일 이름은 `V<다음 번호>__<동사>_<대상>.sql`. 번호는 PR을 올리기 직전 main 기준으로 잡고, 다른 PR과 겹치면 나중에 머지되는 쪽이 번호를 올린다.
- schema-standards의 타입과 제약 기준을 따른다.
- 기존 데이터를 채우는 문장은 스키마 변경과 다른 파일에 둔다.
- V 파일에 `BEGIN`과 `COMMIT`을 쓰지 않는다. Flyway가 파일마다 트랜잭션을 연다. `COMMIT`은 그 트랜잭션을 먼저 끝내, 뒤 문장이 실패해도 앞 문장의 변경이 남는다. Flyway는 되돌렸다고 알리고 이력에 그 파일을 남기지 않아, 다시 돌리면 남은 변경에 걸려 실패한다(확인, Flyway 12.11.0). PR 본문의 되돌리는 SQL을 V 파일로 낼 때 뺀다(qa·ledger 메모, PR #170·#175).
- 컬럼 삭제, 이름 변경, 타입 변경은 추가 → 양쪽 쓰기 → 읽기 전환 → 옛 컬럼 제거로 나눈다. 새 스키마는 바로 전 버전 앱과 맞아야 하고, 새 앱은 옛 스키마와 맞아야 한다.
- 위 절차는 옛 코드가 깨지는 변경에 쓴다. `varchar(n)` → `text`처럼 테이블을 다시 쓰지 않고 바로 전 버전 앱이 읽고 쓰는 값이 그대로 맞는 변경은 한 문장으로 한다(V2).
- 첫 운영 배포 전에는 예외로, 전 버전 앱이 새 스키마에서 쓰지 못하거나 뜨지 못하는 변경을 한 번에 낼 수 있다(V10~V12, V13~V15, V16). **첫 배포 뒤에는 이 예외를 쓰지 않는다.**
- NOT NULL 컬럼 추가는 NULL 허용으로 추가 → 채움 → NOT NULL 순서로 한다.
- 운영에서 되돌릴 때는 거꾸로 돌리지 않는다. 앱 이미지만 이전 버전으로 돌리고, 스키마는 새 마이그레이션으로 앞으로 고친다. Flyway undo와 clean은 쓰지 않는다. repair는 owner 승인 때만 쓴다.
- 큰 변경은 작게 나눠 하나씩 적용하고, 적용 전후에 옛 데이터와 새 데이터가 같은지 보는 검증 쿼리를 PR에 적는다.
- 확장(`CREATE EXTENSION`)은 owner와 devops 확인 뒤에만 넣는다. 측정 도구(`pg_stat_statements` 등)는 마이그레이션에 넣지 않는다.

## 2. 공개 전에만 허용

- 한 이슈의 변경은 여러 테이블을 건드려도 한 파일에 묶을 수 있다. (V1도 한 파일에 여러 테이블을 만들었다. 새 테이블 생성뿐이라 그대로 둔다.)
- 일반 `CREATE INDEX`, 바로 검증되는 FK·CHECK를 써도 된다.

## 3. 공개 뒤부터 지킨다

시작 시점: owner가 운영 DB에 실제 지출을 넣기 시작하는 날.

- 한 파일(한 트랜잭션)은 기존 테이블 하나만 건드린다.
- DDL 앞에 짧은 `lock_timeout`을 건다(예: `SET lock_timeout = '3s';` 값은 그때 정한다).
- 인덱스는 `CREATE INDEX CONCURRENTLY`로 만든다(트랜잭션 밖에서 실행해야 한다).
- FK와 CHECK는 `NOT VALID`로 건 뒤 다른 파일에서 `VALIDATE CONSTRAINT` 한다.
- 채우기는 나눠서 실행한다.
- 마이그레이션을 앱 기동에서 떼어 배포의 별도 단계로 두고, DB 역할을 마이그레이션용(소유자)과 앱용(DML만)으로 나눈다. devops, security와 맞춘다.

## 4. 배포 순서

devops와 맞춘 순서다.

1. 직전 백업
2. 마이그레이션
3. 새 앱

- 마이그레이션이 실패하면 앱을 올리지 않고 멈춘다.
- 늘리기(추가)는 새 앱과 같이 나가고, 줄이기(삭제, 이름·타입 변경의 마지막 단계)는 옛 코드가 사라진 다음 릴리스에 나간다.
- 덤프 복원은 데이터가 망가졌을 때만 쓰는 마지막 수단이다. [backup-restore.md](backup-restore.md)를 본다.

## 5. 스키마 PR 본문에 적을 것

- 무엇을 왜 바꾸는가
- 바로 전 버전 앱과 맞는가
- 적용 전후 검증 쿼리
- 잘못됐을 때 앞으로 고치는 방법
- 새 쿼리나 인덱스의 `EXPLAIN (ANALYZE, BUFFERS)`
