# 실제 복원 절차서

실제 장애 때의 복원이다. 훈련이 아니다. 훈련은 [backup-restore.md](backup-restore.md) 9절을 본다.

- 절차의 DB 쪽은 dba가 정한다. 서버 명령은 운영 문서(#54)와 `deploy/backup.md`(PR #129)가 갖는다.
- 복원은 사람이 시작한다([ADR 008](../adr/008-backup-and-restore.md) 결정 7).
- 서버 접속과 운영 데이터를 바꾸는 단계는 owner가 하거나 owner의 OK를 받고 한다.
- 1번부터 11번의 순서는 ADR 008 결정 7과 같다.
- 침해 때문에 복원할 때의 비밀값 교체는 #54의 몫이다.
- "확인"은 2026-11-25에 로컬의 일회용 `postgres:17`(17.12) 컨테이너에서 해 본 것이다. 운영 서버, 실제 백업 파일, age 복호화, 다른 기기에서 서버로 흘려 넣는 것은 미확인이다.
- `<DB이름>`과 `<관리 역할>`은 운영의 값으로 바꿔 쓴다.

## 0. 전체 복원인지 부분 복구인지 먼저 정한다

| 상황 | 할 일 |
|---|---|
| 일부 행만 망가졌고(잘못된 UPDATE, 잘못된 채우기) 나머지 데이터가 멀쩡하다 | 부분 복구. 전체를 되돌리지 않는다 |
| DB나 서버를 잃었거나 망가진 범위를 알 수 없다 | 전체 복원. 아래 1번부터 한다 |
| 앱만 문제다 | 앱 이미지를 이전 버전으로 되돌린다. 복원하지 않는다 |

부분 복구는 이렇게 한다.

- 전체 복원은 백업 뒤의 모든 입력을 잃는다. 그래서 하지 않는다.
- 백업을 옆의 DB에 복원해 필요한 값을 찾는다.
- 고치는 SQL이나 새 마이그레이션으로 앞으로 고친다.
- 고치는 SQL은 그 사고에 맞춰 dba가 쓰고 owner가 승인한다.
- 옆의 DB는 고친 결과를 확인하면 지운다. 늦어도 35일 안에 지운다. 지우는 것은 owner가 한다.

## 1. 무엇이 망가졌는지 확인한다

- [integrity-checks.sql](integrity-checks.sql)의 점검 쿼리와 명세표 쿼리를 읽기 전용으로 돌려 결과를 남긴다.
- 읽기 전용 세션은 환경변수 `PGOPTIONS='-c default_transaction_read_only=on'`을 주고 `psql`을 연다. 이 세션의 `DELETE`는 거부된다(확인).
- 망가지기 시작한 시각을 찾는다. 그보다 앞선 백업을 골라야 한다.

## 2. 쓰기를 막는다

- 앱을 멈춘다. 멈춘 시각을 적어 둔다.
- 백업 타이머도 멈춘다. 타이머를 두면 복원 도중의 상태가 백업으로 올라가거나 실패 알림이 난다.

## 3. 지금 상태도 남긴다

- 덤프 한 벌을 암호화해 둔다(ADR 008 결정 7).
- 덤프는 `deploy/bin/backup`으로 받지 않는다. 서버에서 DB 컨테이너의 `pg_dump -Fc`를 age 공개키로 암호화해 표준 출력으로 내보내고, owner의 기기가 ssh로 받아 파일로 둔다. 평문이 디스크에 놓이지 않고, 버킷의 `daily/`, `weekly/`와 `last-success`를 건드리지 않는다. 명령은 #54가 정한다(미확인).
- 원래 DB는 지우지 않는다. 5번에서 이름을 바꿔 보존한다.
- 이 둘에도 지운 데이터가 들어 있다. 백업과 같은 상한(35일) 안에 owner가 지운다. 지우는 것은 운영 데이터 삭제라 owner가 정한다.
- 덤프의 파일 이름을 기록한다. 망가진 상태의 덤프를 나중에 복원 대상으로 고르지 않게 하기 위해서다.
- 서버를 잃어 이 단계를 못 하면 건너뛰고 11번에 적는다.

## 4. 복원할 백업을 고른다

- 망가지기 시작한 시각보다 앞선 것 가운데 가장 새것을 고른다.
- 백업 이름을 서버가 기록한 마지막 성공 객체 이름이나 owner가 알림으로 받은 이름과 대조해 고른다(ADR 008 결정 7). 어느 쪽인지는 #54가 정한다.
- `last-success`에는 마지막 이름 하나만 남는다. 그보다 앞선 백업의 이름을 무엇과 대조할지 #54가 정한다.
- 서버가 뚫렸을 수 있으면 두 값도 믿지 않는다. 저장소가 기록한 올린 시각이 침해 시점보다 앞선 백업을 고른다. 그 시각을 서버 자격으로 바꿀 수 없다는 것은 security가 문서로 확인했고 실제 버킷에서는 미확인이다(PR #147 검토).
- `meta.txt`가 `manifest=failed`인 백업은 명세표가 있는 더 앞선 백업이 있으면 쓰지 않는다. 그것밖에 없거나 잃는 구간이 너무 크면, 점검 쿼리 0건과 owner의 승인(테이블별 행 수를 보고)이 있을 때만 쓴다.
- 덤프 시각(`meta.txt`의 `dumped_at`)과 명세표(`manifest.txt`)의 Flyway 버전을 적어 둔다.
- 앱 버전은 이 Flyway 버전과 맞춰 고른다.

### 마이그레이션이 원인일 때

- 그 마이그레이션이 든 앱을 붙이면, 서버가 뜨거나 마이그레이션 단계를 돌리면서 같은 마이그레이션을 다시 적용한다. 서버가 뜨는 쪽은 확인했다(V5까지 적용된 백업에 V6이 든 앱을 붙이면 V6이 적용된다). 마이그레이션 단계는 아직 없어 미확인이다.
- 서비스는 그 마이그레이션이 없는 이전 버전 앱으로 먼저 연다.
- 다음 배포 전에 그 V 파일을 고치는 것을 예외로 허용한다. 새 파일로만 고치면 문제의 V가 복원한 DB에 다시 적용되기 때문이다. 조건은 셋이다.
  1. 운영에서 쓰는 DB 어디에도 그 V가 적용돼 있지 않다(복원으로 없어졌다).
  2. owner가 승인한다.
  3. 로컬과 시험 DB는 다시 만든다(체크섬이 달라진다).
- 그 V가 적용된 뒤의 백업은 이 뒤로 복원 대상으로 쓰지 않는다.

## 5. 새 DB에 복원한다

### 파일 준비

- 복호화는 owner의 기기에서 한다. 개인키를 서버에 두지 않는다. 푸는 명령은 `deploy/backup.md`에 있다.
- 파일이 온전한지 먼저 확인한다. 암호화 파일은 같이 올린 sha256으로, 풀어낸 파일은 묶음 안의 `SHA256SUMS`로 본다.
- 평문 덤프를 서버 디스크에 두지 않는다. owner의 기기에서 복호화한 `db.dump`를 표준 입력으로 흘려 넣는다. `pg_restore`는 표준 입력의 `-Fc`를 받는다(확인).
- owner의 기기에 푼 평문은 복원이 끝나면 바로 지운다.

### 같은 클러스터에 복원할 때

먼저 서버 디스크의 여유가 DB 크기(`SELECT pg_size_pretty(pg_database_size('<DB이름>'))`)보다 큰지 본다. DB가 두 벌이 된다.

1. 새 이름의 DB를 원래 DB와 같은 소유자로 만든다. `postgres` DB에 붙어서 한다. 원래 DB의 소유자는 `psql`의 `\l`로 본다.

   ```sql
   CREATE DATABASE <DB이름>_restore OWNER <원래 DB의 소유자>;
   ```
2. 표준 입력으로 복원한다. 역할은 이미 있으므로 `globals.sql`을 적용하지 않는다.

   ```
   pg_restore --exit-on-error -U <관리 역할> -d <DB이름>_restore < db.dump
   ```
3. `ANALYZE`를 돌린다.

   ```
   psql -U <관리 역할> -d <DB이름>_restore -c ANALYZE
   ```
4. 6번 점검을 한다.
5. 점검을 통과한 뒤 이름을 바꾼다. `postgres` DB에 붙어서 한다. `<날짜>`는 `20261125`처럼 적는다.

   ```sql
   ALTER DATABASE <DB이름> RENAME TO <DB이름>_broken_<날짜>;
   ALTER DATABASE <DB이름>_restore RENAME TO <DB이름>;
   ```

- 이름 바꾸기는 그 DB에 붙은 연결이 없어야 된다. 앱이 붙어 있으면 `is being accessed by other users`로, 바꿀 DB에 붙어서 하면 `current database cannot be renamed`로 실패한다(확인).
- `OWNER`를 빼면 DB의 소유자가 관리 역할이 된다. PostgreSQL 15부터 `public` 스키마의 소유자가 `pg_database_owner`라, 원래 소유자 역할로 도는 마이그레이션이 `public`에 테이블을 만들지 못할 수 있다.
- 확인(관리 역할과 DB 소유자가 다른 클러스터): `OWNER` 없이 복원하면 복원과 점검은 통과하지만, 소유자 역할의 `CREATE TABLE`과 `ALTER TABLE ... ADD ... UNIQUE`가 `permission denied for schema public`으로 실패했고 V6도 적용되지 않았다. `OWNER`를 주면 모두 됐다.
- 이 방법은 DB 자체의 설정(`ALTER DATABASE ... SET`)과 DB에 준 권한(`GRANT`, `REVOKE ... ON DATABASE`)을 옮기지 않는다(확인). 원래 DB에 있으면 이름을 바꾸기 전에 새 DB에 다시 건다. `psql`의 `\drds`(설정)와 `\l`(권한)로 본다. 테이블에 준 권한은 덤프에 들어 있어 따라온다(확인).

### 새 클러스터에 복원할 때(서버를 잃었을 때)

1. `--data-checksums`로 initdb한다. 관리 역할의 이름은 `globals.sql`에 없는 것으로 한다(훈련 스크립트는 `drill_admin`을 쓴다).
2. `globals.sql`을 먼저 적용한다. 비밀번호 해시가 들어 있으니 표준 입력으로 흘려 넣고 파일로 남기지 않는다.

   ```
   psql -X -v ON_ERROR_STOP=1 -U <새 관리 역할> -d postgres < globals.sql
   ```
3. 표준 입력으로 복원한다. 훈련 스크립트처럼 `--create`로 DB까지 만든다.

   ```
   pg_restore --exit-on-error --create -U <새 관리 역할> -d postgres < db.dump
   ```
4. `ANALYZE`를 돌린다.

   ```
   psql -U <새 관리 역할> -d <DB이름> -c ANALYZE
   ```
5. 6번 점검을 한다. 이름을 바꿀 것은 없다.

- `globals.sql`에는 백업한 클러스터의 관리 역할이 들어 있다. 같은 이름의 관리 역할로 initdb하면 `role "..." already exists`로 멈춘다(확인, `psql` 종료 코드 3).
- `globals.sql`을 먼저 적용하지 않으면 `pg_restore --create`가 `role "..." does not exist`로 멈춘다(확인).
- `--create`는 DB의 소유자, 설정, 권한까지 복원한다. 빈 DB를 만들어 `--create` 없이 복원하면 소유자가 새 관리 역할이 된다(확인).
- 새 관리 역할은 나중에 지울 수 없다. 다음 백업의 `globals.sql`에도 들어가므로, 이 백업을 다시 새 클러스터에 복원할 때는 또 다른 이름을 쓴다(확인).

### ANALYZE를 돌리는 이유

- `pg_restore`(17)는 통계를 복원하지 않는다. 그대로 열면 실행 계획이 틀려 느려질 수 있다.
- 확인: 복원 직후 `pg_stats`에 우리 테이블의 행이 없었고, 2,500행이 나오는 조건을 30행으로 추정했다. `ANALYZE` 뒤에는 2,500행으로 추정했다.

## 6. 점검한다

앱을 붙이기 전에, 백업 때의 스키마 그대로 본다.

- 백업 안의 쿼리 파일(`integrity-checks.sql`)로 명세표를 다시 만들어 백업 안의 명세표(`manifest.txt`)와 같은지 본다. 출력 형식과 시간대를 백업 때와 맞춘다(`deploy/bin/backup-lib.sh`의 `manifest_script`).
- 명세표가 다르면 복원이 백업과 같지 않은 것이다. 서비스를 열지 않고 새 DB에 한 번 더 복원한다(5번). 또 다르면 더 앞선 백업을 고른다(4번).
- 점검 쿼리가 모두 0건인지 본다.
- 0건이 아니면 그 백업이 이미 망가진 뒤의 것일 수 있다. 4번으로 돌아간다.

확인: 복원한 DB(같은 클러스터, 새 클러스터)에서 명세표가 같고 점검 13개가 모두 0건이었다. 일부러 이체 라인 하나의 금액을 바꾼 DB에서는 명세표가 다르고 점검 1이 1건이었다.

## 7. refresh token 행을 모두 지운다

- 앱을 붙이기 전에 SQL 한 문장으로 한다(ADR 008 결정 10).
- 테이블은 #26에서 만들어진다. 이름은 그때 적는다(미확인).
- 그 테이블이 없던 때의 백업이면 건너뛴다.

## 8. (2단계부터) 백업 시점 뒤의 정리 작업과 탈퇴 신청, 탈퇴 취소를 다시 적용한다

- SQL로 하지 않고 서버의 관리 명령으로 한다(ADR 008 결정 8).
- 1단계에는 삭제 기록이 없다. owner가 서비스를 연 뒤 앱에서 다시 지운다.

## 9. (2단계부터) 토큰이 든 주소를 모두 폐기한다

열람 링크, 초대, 3단계의 문자 전송 주소 전부다(ADR 008 결정 10 (나)).

## 10. 서비스를 연다

1. 앱을 붙인다. 서버가 뜰 때 Flyway가 백업 뒤의 마이그레이션을 적용하고 `ddl-auto=validate`를 한다(확인: V5까지 적용된 백업에 V6이 든 앱). 마이그레이션이 배포의 별도 단계가 된 뒤에는 앱을 붙이기 전에 그 단계를 먼저 돌린다(ADR 005 결정 4).
2. 로그에서 Flyway validate와 적용된 마이그레이션을 확인한다. `Successfully validated ... migrations`, `Migrating schema "public" to version ...`, `Successfully applied ... migration` 줄이다(확인).
3. 바로 백업을 한 번 돌려 성공을 확인한다.
4. 백업 타이머를 다시 켠다.

복원 뒤 첫 백업은 다시 적용(8번, 2단계부터)이 끝난 다음에 받는다. 먼저 받으면 되살아난 데이터가 새 백업에 들어가 보관 기간이 다시 시작된다.

1단계에는 owner가 앱에서 다시 지우기 전에 첫 백업을 받으므로 되살아난 데이터가 들어간다. 그대로 둔다. owner 데이터뿐이고 백업 없이 오래 여는 쪽이 더 위험하다.

## 11. 보고한다

owner에게 보고하고 다음을 남긴다.

- 시작과 끝 시각(복구 4시간 목표의 근거)
- 쓴 백업
- 잃은 구간(덤프 시각부터 쓰기를 막은 시각까지)
- 점검 결과
- 보존한 옛 DB와 덤프의 이름과 지울 날짜
- 되돌아간 폐기와 변경(ADR 008 결정 10의 목록)
- 서버를 잃어 3번을 건너뛰었으면 그 사실

2단계부터는 사용자에게도 알린다.

## 하지 않는 것

- 원래 DB에 덮어쓰는 복원(`pg_restore --clean`)
- Flyway clean, undo
- 점검 전에 앱 붙이기
- 서버에 개인키 두기
- 원인을 모른 채 가장 새 백업 고르기

## 남은 것

- refresh token 테이블 이름(#26)
- 서버 명령(#54). 3번의 덤프를 받는 명령도 여기에 든다
- `last-success`보다 앞선 백업의 이름을 무엇과 대조할지(#54)
- 삭제 기록과 다시 적용 명령(#140, 2단계 전, ADR 008 결정 8)
- 시점 복구(#141, 2단계 전, ADR 008 결정 9)
