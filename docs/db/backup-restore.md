# 백업·복원 설계

설계는 dba, 실행은 devops가 한다. 이 문서는 1단계 설계다. 스크립트는 `deploy/bin/backup`과 `scripts/restore-drill`이다(PR #129). 기획 P-229와 연결된다.

## 1. 목표 (1단계)

- 최대 유실 24시간, 복구 4시간 이내.
- 시점 복구는 없다. 매일 `pg_dump`만으로는 시점 복구가 안 되므로, 마지막 백업 뒤의 입력은 사라질 수 있다.
- 이것은 owner가 받아들인 위험이다(2026-11-24).

## 2. 시점 복구 계획

- 2단계 시작 전(다른 사람의 데이터가 들어오기 전)에 기본 백업 + WAL 보관을 시작한다.
- 그때 목표 제안은 유실 5분, 복구 1시간이다(제안값, 미결).
- 도구 선택은 devops가 한다.

## 3. 무엇을

- DB 전체를 `pg_dump -Fc`로 받는다. Flyway 이력 테이블을 포함하고, 테이블 제외 옵션은 쓰지 않는다.
- 역할은 `pg_dumpall --globals-only`로 따로 받는다.
- 설정 파일은 Git이 원본이다. 비밀값은 따로 둔다(devops).

## 4. 얼마나 자주

- 매일 새벽(KST) 1회.
- 배포 직전(교체하기 전) 1회(ADR 008 결정 2).

## 5. 어떻게

- `pg_dump`는 DB 컨테이너 안의 것을 쓴다(버전 불일치 방지).
- `-Fc`는 이미 압축된다. 따로 압축하지 않는다.
- 성공 판정: 종료 코드 0, 크기 0 초과, 암호화 전에 `pg_restore --list`와 전체를 한 번 더 읽는 확인(`pg_restore --file=/dev/null`)을 통과한다. `--list`는 목차만 읽어 뒤가 잘린 덤프를 잡지 못한다. 임시 이름으로 쓰고 끝나면 이름을 바꾼다. sha256을 같이 올린다.
- 백업할 때 명세표를 같이 만든다([integrity-checks.sql](integrity-checks.sql)의 "명세표" 쿼리 결과 + 덤프 시각). 명세표는 덤프와 같은 스냅샷에서 만든다(`pg_export_snapshot`을 내보낸 세션을 열어 두고 `pg_dump --snapshot`). 명세표만 실패하면 덤프는 올리고 백업은 실패로 끝내 알린다.
- age 공개키로 암호화한다. 복호화 키는 owner만 가진다. CI에 두지 않는다.

## 6. 어디에

- OCI Object Storage.
- VM의 자격으로는 새 객체를 올리기만 할 수 있고 읽기, 덮어쓰기, 지우기는 할 수 없게 한다(ADR 008 결정 3). 실제 버킷에서는 미확인이다.
- 월 1회 복원 훈련 때 내려받은 암호화 파일 1개를 OCI 계정 밖(owner 맥)에 사본으로 둔다. 훈련 때마다 새것으로 바꾸고 앞의 것은 지운다. 훈련을 걸렀더라도 35일이 지난 사본은 지운다.

## 7. 얼마나 보관

- 매일 7개, 매주 4개, 가장 오래된 것이 35일(owner 결정). 버킷 수명 주기 규칙으로 daily 7일, weekly 33일로 건다. 지워지는 시각의 지연 때문에 남는 개수는 daily 7~9개, weekly 4~5개이고 가장 오래된 것은 35일을 넘지 않는다(근거는 `deploy/backup.md`).
- 탈퇴·영구 삭제된 데이터가 백업에 남는 최장 기간도 35일이다. 개인정보 처리방침에 이 값을 적는다(#23).

## 8. 알림

- 백업 파일이 26시간 넘게 안 올라오면 알린다.
- 직전 대비 크기가 20% 넘게 줄어도 알린다.

## 9. 복원 훈련

- 주기: 월 1회, 그리고 조각(1A, 1B, 1C)이 끝날 때. 첫 훈련은 owner가 실제 지출을 넣기 전에 통과해야 한다.
- 장소: 운영과 떨어진 환경. owner 맥의 로컬 Docker에서 스크립트 한 줄로 실행한다. 흐름은 내려받기 → 복호화 → 빈 `postgres:17` 컨테이너에 `pg_restore --exit-on-error` → 점검 → 컨테이너와 평문 삭제 → 결과 출력이다. 스크립트는 devops, 점검 SQL은 dba가 맡는다.
- 통과 조건:
  - 복원 종료 코드 0
  - Flyway validate 통과
  - 명세표가 백업 때와 일치
  - [integrity-checks.sql](integrity-checks.sql)의 점검 쿼리가 모두 0건
  - 서버가 복원 DB에 붙어 기동(`ddl-auto=validate`)
  - 걸린 시간 기록(복구 4시간 목표의 근거)
- 결과는 owner에게 보고하고 아래 "훈련 기록" 표에 한 줄 남긴다.

## 10. 복원 절차

1. 무엇이 망가졌는지 확인한다.
2. 쓰기를 막는다.
3. 지금 상태도 덤프로 남긴다. 이 덤프도 암호화하고 35일 안에 지운다(ADR 008 결정 7).
4. 복원할 백업을 고른다. 이름을 서버가 기록한 마지막 성공 객체 이름이나 owner가 알림으로 받은 이름과 대조한다(어느 쪽인지는 #54가 정한다). 서버가 뚫렸을 수 있으면 두 값도 믿지 않고, 저장소가 기록한 올린 시각이 침해 시점보다 앞선 백업을 고른다(ADR 008 결정 7).
5. 새 DB에 복원한다.
6. 점검한다.
7. refresh token 행을 모두 지운다(ADR 008 결정 10).
8. 백업 시점 뒤의 정리 작업과 탈퇴 신청, 탈퇴 취소를 다시 적용한다(2단계부터, ADR 008 결정 8).
9. 토큰이 든 주소를 모두 폐기한다(2단계부터, ADR 008 결정 10).
10. 서비스를 연다.
11. owner에게 보고한다. 2단계부터는 사용자에게도 알린다(ADR 008 결정 10).

자세한 절차는 [restore-runbook.md](restore-runbook.md)를 본다. 다시 적용과 주소 폐기는 2단계부터다.

## 11. 남은 설계 과제

- 백업 뒤에 영구 삭제된 것(탈퇴, 장부 삭제, 거래 완전 삭제)은 복원하면 되살아난다. 다시 지우는 데 쓰는 삭제 기록의 방법은 ADR 008 결정 8이 정했고 2단계 시작 전에 만든다. 기록은 그것이 필요한 백업보다 먼저 지워지지 않게 한다. 1단계에는 만들지 않는다.
- 운영 DB를 처음 만들 때 initdb에 `--data-checksums`를 켠다(PostgreSQL 17은 기본이 꺼져 있고 나중에 켜려면 DB를 내려야 한다).
- 휴지통은 삭제 사고의 첫 방어선일 뿐이다. integrity-checks.sql의 점검 쿼리를 훈련 때만이 아니라 정기적으로 돌리는 방법(devops 실행)을 정한다.
