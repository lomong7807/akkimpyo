# 백업·복원 설계

설계는 dba, 실행은 devops가 한다. 이 문서는 1단계 설계이고 아직 구현되지 않았다. 기획 P-229와 연결된다.

## 1. 목표 (1단계)

- 최대 유실 24시간, 복구 4시간 이내.
- 시점 복구는 없다. 매일 `pg_dump`만으로는 시점 복구가 안 되므로, 마지막 백업 뒤의 입력은 사라질 수 있다.
- 이것은 owner가 받아들인 위험이다(2026-11-24).

## 2. 시점 복구 계획

- 2단계 시작 전(다른 사람의 데이터가 들어오기 전)에 기본 백업 + WAL 보관을 시작한다.
- 그때 목표 제안은 유실 5분, 복구 1시간이다(제안값, 미결).
- 도구 선택은 devops가 한다.

## 3. 무엇을

- DB 전체를 `pg_dump -Fc`로 받는다. Flyway 이력 테이블을 포함하고, 테이블 제외 옵션은 쓰지 않는다.
- 역할은 `pg_dumpall --globals-only`로 따로 받는다.
- 설정 파일은 Git이 원본이다. 비밀값은 따로 둔다(devops).

## 4. 얼마나 자주

- 매일 새벽(KST) 1회.
- 마이그레이션 직전 1회.

## 5. 어떻게

- `pg_dump`는 DB 컨테이너 안의 것을 쓴다(버전 불일치 방지).
- `-Fc`는 이미 압축된다. 따로 압축하지 않는다.
- 성공 판정: 종료 코드 0, 크기 0 초과, 암호화 전 `pg_restore --list` 통과. 임시 이름으로 쓰고 끝나면 이름을 바꾼다. sha256을 같이 올린다.
- 백업할 때 명세표를 같이 만든다([integrity-checks.sql](integrity-checks.sql)의 "명세표" 쿼리 결과 + 덤프 시각).
- age 공개키로 암호화한다. 복호화 키는 owner만 가진다. CI에 두지 않는다.

## 6. 어디에

- OCI Object Storage.
- VM의 자격은 올리기만 되고 지우기·덮어쓰기가 안 되게 한다(가능 여부 미확인, devops 확인 중).
- 월 1회 복원 훈련 때 내려받은 암호화 파일 1개를 OCI 계정 밖(owner 맥)에 사본으로 둔다.

## 7. 얼마나 보관

- 매일 7개, 매주 4개, 가장 오래된 것이 35일.
- 탈퇴·영구 삭제된 데이터가 백업에 남는 최장 기간도 35일이다. 개인정보 처리방침에 이 값을 적는다(#23).

## 8. 알림

- 백업 파일이 26시간 넘게 안 올라오면 알린다.
- 직전 대비 크기가 20% 넘게 줄어도 알린다.

## 9. 복원 훈련

- 주기: 월 1회, 그리고 조각(1A, 1B, 1C)이 끝날 때. 첫 훈련은 owner가 실제 지출을 넣기 전에 통과해야 한다.
- 장소: 운영과 떨어진 환경. owner 맥의 로컬 Docker에서 스크립트 한 줄로 실행한다. 흐름은 내려받기 → 복호화 → 빈 `postgres:17` 컨테이너에 `pg_restore --exit-on-error` → 점검 → 컨테이너와 평문 삭제 → 결과 출력이다. 스크립트는 devops, 점검 SQL은 dba가 맡는다.
- 통과 조건:
  - 복원 종료 코드 0
  - Flyway validate 통과
  - 명세표가 백업 때와 일치
  - [integrity-checks.sql](integrity-checks.sql)의 점검 쿼리가 모두 0건
  - 서버가 복원 DB에 붙어 기동(`ddl-auto=validate`)
  - 걸린 시간 기록(복구 4시간 목표의 근거)
- 결과는 owner에게 보고하고 아래 "훈련 기록" 표에 한 줄 남긴다.

## 10. 복원 절차 개요

1. 무엇이 망가졌는지 확인한다.
2. 쓰기를 막는다(앱 정지).
3. 지금 상태도 덤프로 남긴다.
4. 복원 대상을 고른다.
5. 새 DB에 복원한다.
6. 점검한다.
7. 백업 뒤 영구 삭제된 것을 다시 지운다.
8. 앱을 연결한다.
9. owner에게 보고한다.

## 11. 남은 설계 과제

- 백업 뒤에 영구 삭제된 것(탈퇴, 장부 삭제, 거래 완전 삭제)은 복원하면 되살아난다. 다시 지우려면 삭제 기록(대상 id와 시각)이 DB 밖에도 남아야 한다. 1단계는 owner 데이터뿐이라 급하지 않다.
- 운영 DB를 처음 만들 때 initdb에 `--data-checksums`를 켠다(PostgreSQL 17은 기본이 꺼져 있고 나중에 켜려면 DB를 내려야 한다).
- 휴지통은 삭제 사고의 첫 방어선일 뿐이다. integrity-checks.sql의 점검 쿼리를 훈련 때만이 아니라 정기적으로 돌리는 방법(devops 실행)을 정한다.
